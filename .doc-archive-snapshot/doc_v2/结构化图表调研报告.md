# 结构化图表生成能力扩展 — 深度调研报告

> 调研日期:2026-07-10 | 调研维度:5(DSL 生态 / LLM 生成 / 现有 MCP / 架构方案 / 渲染引擎)
> 适用场景:为 media-gen-mcp 体系扩展"结构化图表生成"能力,覆盖架构图、流程图、时序图、ER 图等

---

## 一、执行摘要(TL;DR)

**一句话结论(已修正,见 §6.0):扩展 media-gen-mcp 加 `generate_diagram` 工具(方案 A 改进版),以"用户心智=生图"为第一原则,diagram 作为独立模块(不进 Provider 抽象)与 AI 生图共处一个 MCP;主力 DSL 选 Mermaid、辅以 D2、Graphviz 兜底,渲染栈全部默认 SVG 且彻底避开 Java 与 Chromium。**

### 核心决策矩阵

| 决策项 | 选定方案 | 决定性理由 |
|---|---|---|
| **DSL 选型** | Mermaid(主)+ D2(辅)+ Graphviz(兜底)+ PlantUML(复杂 UML 备用) | Mermaid 是唯一有学术 benchmark(MermaidSeqBench)、7-8B 模型语法正确率 91-92% 的 DSL;D2 视觉最佳且零运行时依赖;Graphviz 是最轻的单一 C 二进制 |
| **架构选型** | **方案 A 改进版:扩展 media-gen-mcp(diagram 独立模块)** | 产品视角:"生图"是用户统一心智,一个 MCP 入口 > 两个;diagram 独立模块(不进 Provider)实现技术分离 + 产品统一(见 §6.0 修正) |
| **渲染栈** | isomorphic-mermaid(进程内)+ D2 Go 二进制(spawn CLI)+ Graphviz dot(spawn CLI),全 SVG | JS 原生引擎走进程内、非 JS 二进制走 spawn,两者都远优于"内嵌一个浏览器" |
| **MCP 策略** | 优先复用,不自建渲染引擎 | diagram/chart MCP 生态已成熟拥挤;10 分钟配齐两个 MIT/本地渲染的 server 覆盖 90%+ 需求 |
| **输出格式** | 默认 SVG(矢量高清、可缩放、文件小) | 仅需位图时才出 PNG,且走 Graphviz/dot 原生 PNG 或 D2 SVG→resvg 转换,全程无浏览器 |

### 分层推荐(按诉求)

- **LLM 生成正确率最高** → Mermaid(训练语料碾压,有 benchmark,token 最省)
- **最干净的本地渲染管线** → D2(单 Go 二进制,一行 `d2 in.d2` 出 SVG)
- **最轻的兜底引擎** → Graphviz dot(单一 C 二进制,`dot -Tsvg` 即出)
- **统一渲染出口(自托管)** → Kroki Docker 镜像(一个容器聚合 25+ DSL)
- **避开(让 LLM 直出源码)** → Excalidraw / draw.io / tldraw / React Flow(本质是 JSON/XML 场景数据,非声明式 DSL)

## 二、问题分析:AI 像素生图 vs 结构图

### 2.1 两种范式根本不同

media-gen-mcp 现有能力是"AI 模型 → PNG/MP4":远程推理、异步轮询、API key、厂商限流、videoConstraints。结构图是"DSL 文本 → SVG":本地确定性渲染、同步即时返回、无需 API key、无网络。

| 维度 | AI 像素生图(media-gen-mcp) | 结构图(diagram) |
|---|---|---|
| **生成范式** | 概率性(每次结果不同) | 确定性(相同输入→相同输出) |
| **运行位置** | 远程模型推理 | 本地引擎编译 |
| **调用模式** | 异步:提交→poll→download | 同步:输入→即时返回 |
| **核心抽象** | MediaProvider(厂商/API key/限流) | DiagramEngine(mermaid/d2/graphviz) |
| **产物形态** | 位图/视频像素 | 矢量 SVG(可缩放、可编辑、可 Diff) |
| **复用交集** | 仅 downloadAsset() 存盘 + MCP 通用样板 | — |

**关键洞察:把 `generate_diagram` 塞进 media-gen-mcp 不会复用任何核心抽象。** diagram 不调 `getProvider`、不碰 `registry/poll/config/videoConstraints`,与 provider 抽象零交集。强行造一个假的 `DiagramProvider` 去平行 `ImageProvider` 是"抽象摆拍"——diagram 引擎没有"厂商/API key/限流"概念,它是本地确定性的渲染库。

### 2.2 为什么结构图必须走 DSL 而非"让 AI 直接画"

1. **确定性**:AI 像素生图无法保证两次画出同一张架构图;DSL 保证幂等。
2. **可编辑/可迭代**:架构图是演进的;SVG 矢量图可二次编辑,DSL 源码可 Git Diff 追溯版本演进。位图一旦生成即冻结。
3. **LLM 擅长产出结构化文本而非描述画面**:让 LLM 写 Mermaid 远比让 LLM 描述"一个蓝色矩形连接一个绿色椭圆"更可靠、更省 token。
4. **高清无损**:矢量 SVG 在 PPT/文档/大屏任意缩放无锯齿;AI 位图放大即糊。
5. **生态原生渲染**:Mermaid 在 GitHub/Notion/Obsidian/GitLab Markdown 里直接内联渲染,无需额外工具链。

### 2.3 DSL vs 画布应用的硬分界

**真正适合 LLM 生成的"图即代码 DSL"(文本→图)只有 5 个:Mermaid、D2、PlantUML、Graphviz/DOT、Structurizr。**

Excalidraw / draw.io / tldraw / React Flow 本质是"画布/白板应用",其源格式是 JSON/XML 场景数据而非声明式 DSL。让 LLM 手写这种冗长结构正确率低、token 浪费大;它们更适合做渲染后的可视化前端或交互编辑层。**这是本报告最重要的分类判断,后续所有选型都基于此。**

## 三、图表 DSL 对比

### 3.1 声明式 DSL(适合 LLM 直出源码)— 5 个

| DSL | 语言/运行时 | LLM 正确率 | 本地渲染依赖 | 许可证 | 输出 | 核心优势 | 核心短板 |

### 3.2 画布/编辑器应用(不适合 LLM 直出源码)— 4 个

| 工具 | 格式 | LLM 生成适合度 | 许可证 | 定位 |
|---|---|---|---|---|
| **Excalidraw** | JSON 场景数据 | 低(冗长嵌套 JSON,易错) | MIT | 手绘风白板,适合非正式/教学 |
| **draw.io / diagrams.net** | XML | 低(冗长 XML,LLM 易出错) | Apache 2.0 | 功能最全通用画图工具,适合人工拖拽 |
| **tldraw** | JSON 场景数据 | 低 + **非 OSI 开源**(商用需付费授权) | source-available(非商用免费) | React 无限画布 SDK,交互体验一流 |
| **React Flow** | 编程式 API(JSON 节点/边) | 中(作为可视化层而非 DSL) | MIT | 节点式 UI 库,适合构建交互式查看前端 |

### 3.3 统一渲染聚合层 — 1 个

| 工具 | 定位 | 许可证 | 核心价值 |
|---|---|---|---|
| **Kroki** | HTTP 网关聚合 25+ 后端 DSL | MIT(Kroki 本体) | 一个 Docker 容器统一 `/mermaid/svg` 路径返回 SVG,完美解耦"生成"与"渲染";自托管完全本地 |

### 3.4 DSL 选型推荐

```
主力 = Mermaid(LLM 正确率最高,生态最广)
辅力 = D2(架构图/最简依赖,审美最佳)
兜底 = Graphviz dot(经典 DAG/ER/依赖图,最轻)
备用 = PlantUML(仅复杂 UML:嵌套 state/activity/复合 class 时)
架构文档专精 = Structurizr(C4 场景,配 few-shot)
```

**应避开让 LLM 直出的:Excalidraw / draw.io / tldraw / React Flow。** 它们更适合做"渲染后的可视化/编辑前端"。

## 四、LLM 生成策略

### 4.1 哪个 DSL LLM 最可靠?——Mermaid,证据最强

Mermaid 是 LLM 时代唯一"既可靠又有完整开源生态 + 官方 MCP"的图表 DSL。四大证据:

1. **训练数据碾压**:Mermaid 是 GitHub/Notion/Obsidian/GitLab Markdown 原生支持的 DSL,LLM 暴露量最大。
2. **唯一有正式学术 benchmark**:IBM Research 的 **MermaidSeqBench**(NeurIPS 2025,arXiv 2511.14967),132 样本、6 维评估(syntax/logic/completeness/activation/error-tracking/usability),实测 Qwen2.5-7B 与 Llama3.1-8B 语法正确率 91-92%;Claude/GPT-4o 级近满分。DeepSeek-V3 vs GPT-OSS 双裁判揭示模型间显著能力差与裁判严格度差异。
3. **Token 效率最高**:Markdown 启发语法,比 PlantUML 的 Java 风格轻量。
4. **生态最完整**:Claude/MCP、npm、渲染器、官方 Mermaid Chart MCP。

对比:D2 视觉更精致但训练数据少、语法错误率明显更高、**无任何正式 benchmark**;PlantUML 在复杂 UML 上仍占优,但 token 重、Java 依赖。

### 4.2 DSL 准确率排序

```
Mermaid > PlantUML > D2 > Structurizr
```

- **Mermaid**:最高。MermaidSeqBench 实证;唯一有 benchmark。
- **PlantUML**:语法一致性最佳(各种图共享同一套对象/箭头语义),跨图类型不易出错。
- **D2**:语法最现代简洁、容错好,但训练语料少,零样本正确率略低,建议给 1-2 个 few-shot 示例。

### 4.3 Prompt 工程:四招叠加把错误率压到很低

| 招式 | 做法 | 效果 |
|---|---|---|
| **结构化 NL 输入** | 按 Purpose / Main Components / Interactions 三段提供结构化自然语言(源自 MermaidSeqBench 方法论) | 让 LLM 理解图意图而非自由发挥 |
| **Few-shot 示例(2-3 个)** | 在 prompt 中给出 2-3 个正确 DSL 示例(覆盖目标图类型) | 对 D2 等语料少的 DSL 尤其关键 |
| **Chain-of-Thought** | 要求"先列出实体与关系,再写代码";或直接给带推理链的 few-shot 示例(few-shot CoT,最强组合) | 降低逻辑错误与遗漏 |
| **硬约束输出** | 明确指令"只输出 Mermaid 代码块,不要解释" | 避免 LLM 把代码包在散文里污染解析 |

### 4.4 兜底校验:渲染-校验-回贴迭代闭环

把"渲染是否成功"作为 LLM 输出的**客观判据**,而非主观判断:

```
LLM 生成 DSL → mmdc/MCP validate_and_render → 成功则返回 SVG
                                       → 失败则把语法错误(行列)回喂 LLM → 自动重试
```

- mmdc/MCP 的 `validate_and_render` 工具能直接拦截语法错误。
- 可用多模态模型看渲染图自检(把 SVG/PNG 回喂模型,检查是否与意图一致)。
- MermaidSeqBench 的 6 维评估(syntax/logic/completeness/activation/error-tracking/usability)可作为自检 rubric。

### 4.5 现有可复用工具(按推荐度)

| 工具 | 类型 | LLM 适配 | 推荐场景 |
|---|---|---|---|
| **claude-mermaid 插件**(veelenga) | Claude Code 本地插件(MIT) | 内建最佳实践 skill(相当于内建 few-shot/约束) | Claude Code 内最顺滑方案;本地 live reload + 导出 SVG/PNG/PDF |
| **Mermaid Chart MCP**(官方) | 远程 HTTP/SSE MCP | validate_and_render 免鉴权,闭环最完整 | 通用/远端;无需自建渲染服务 |
| **mermaid-cli(mmdc)** | CLI 渲染器 | 配合 LLM 形成自动重试闭环 | 自建管线,最轻量可控 |
| **Eraser.io / DiagramGPT** | SaaS + MCP(付费) | 自然语言→图能力强,但输出 Eraser 私有 DSL(锁定) | 企业级,不建议作通用底层 |
| **Napkin.ai** | SaaS(闭源) | 偏内容/商业叙事,技术准确性弱 | 营销/教学,不适合精确技术架构图 |
| **MermaidSeqBench** | Benchmark 数据集(IBM Research) | 可作自检 rubric 或评测自家 prompt/模型的标尺 | 评估用,非生产工具 |

## 五、现有 MCP 调研:复用还是自建?

### 5.1 核心发现

diagram/chart MCP server 生态在 2026 年已相当成熟且拥挤。所有方案遵循同一模式:**LLM 生成 DSL 文本,MCP 工具负责渲染为 SVG/PNG。** 不存在"自动从零生成 DSL"的 MCP(那是 LLM 的职责)。"接收 DSL → 渲染 SVG"这一环已被多个成熟项目实现。

### 5.2 七个 diagram MCP Server 对比

| MCP Server | 图表语言 | 活跃度 | 渲染路径 | 许可证 | LLM 适配 |
|---|---|---|---|---|---|
| **jgraph/drawio-mcp**(官方) | draw.io(XML/CSV/Mermaid) | **24,565/周**(最活跃) | 4 路径:内联渲染/浏览器 URL/.drawio 文件/CLI 导出;无云光栅化 | Apache-2.0 | 中(XML 冗长;search_shapes 覆盖 1万+ 图形) |
| **hustcc/mcp-mermaid** | Mermaid only | **10,896/周**(AntV 团队背书) | Node 本地;URL 模式走 mermaid.ink 公网 | MIT | **极高**(Mermaid 语料最充分;内置 validation 多轮纠错) |
| **i2y/d2mcp** | D2 only | 活跃(Go 项目,v0.5.0) | **D2 Go 引擎内嵌本地编译**(无 Chromium/无 Java/无云) | MIT | 高(Oracle API 支持**增量编辑**,逐元素构建降低出错率) |
| **antoinebou12/uml-mcp** | **30+ 类型**(Mermaid/D2/Graphviz/PlantUML/C4/BPMN/TikZ...) | 活跃(Smithey/Vercel) | 默认 **Kroki 云**(kroki.io);可自建 Docker 全栈 | MIT | 高(一站式 + uml:// 资源供 LLM 参考) |
| **peng-shawn/mermaid-mcp-server** | Mermaid only | 低(455/周) | Puppeteer+Chromium(重) | MIT | 高(单工具 generate 入参清晰) |
| **plantuml/plantuml-mcp**(官方) | PlantUML | **MVP 阶段**(仅 1 个返回版本号的工具,不能渲染图) | 暂无渲染能力 | 待确认 | 中(当前不可用于生产) |
| **i-tozer/excalidraw-mcp** | Excalidraw | 低(个人项目) | Node/TS,文件存储 | MIT | 低-中(Excalidraw 无 DSL,须构造 JSON 元素) |

### 5.3 渲染路径关键差异(决定选型)

| 渲染路径 | 代表 | 依赖 | 离线 | 评价 |
|---|---|---|---|---|
| **本地原生编译** | i2y/d2mcp(D2 Go 引擎) | 无 | 完全离线 | **最干净** |
| 进程内 JS 渲染 | isomorphic-mermaid | jsdom | 完全离线 | 最轻(延迟最低) |
| 无头浏览器 | peng-shawn(Puppeteer+Chromium) | Chromium | 离线但重 | 依赖重 |
| 云渲染代理 | uml-mcp 默认(kroki.io) | 网络 | **不离线**(DSL 明文出本机) | 隐私敏感场景必须自建 |
| 本地桌面 CLI | @drawio/mcp PNG/SVG | draw.io Desktop CLI | 离线 | 需装桌面端 |

### 5.4 复用 vs 自建:决策树

**结论:复用,不自建渲染引擎。生态已拥挤且成熟,无需重复造轮子。**

```
你的诉求?
│
├─ 纯"LLM 生成 DSL → 本地 SVG"、零云/零浏览器依赖
│  → 首选 i2y/d2mcp(D2 Go 二进制本地编译,Oracle API 增量编辑)
│
├─ 日常通用、生态最大、LLM 最熟
│  → hustcc/mcp-mermaid(1.1万/周,AntV 背书,Docker 即用)
│
├─ 单 server 覆盖最多图表类型(30+)
│  → antoinebou12/uml-mcp(全包,但默认走 Kroki 云,数据敏感时必须 docker compose 自建)
│
├─ 要交互式可编辑产物、企业级
│  → @drawio/mcp 官方(2.4万/周,4 种集成,1万+ 图形)
│
└─ 同时满足:(a) 单一统一 server + 100% 离线 + Mermaid+D2+PlantUML 全覆盖
            (b) 需定制输出嵌入你的文档管线(固定主题/品牌色/直接写入 markdown)
   → 仅此时才自建,且应写**薄 facade MCP**包一层 D2+Mermaid 库,而非从零造渲染引擎
```

### 5.5 对写作/文档场景的落地建议

**直接配 i2y/d2mcp(主,出高质量架构图)+ hustcc/mcp-mermaid(辅,快速序列图/流程图)。** 两者皆 MIT、皆 stdio、皆本地渲染,10 分钟配齐,覆盖 90%+ 需求,无需写一行 MCP 代码。

## 六、架构推荐:A vs B vs C

### 6.0 修正(2026-07-13,产品视角)—— 推荐改为方案 A 改进版

> 原报告(6.1-6.4)推荐 B(新 diagram-mcp),基于**技术视角**(共享抽象≈0)。经产品视角深度分析后,**修正为 A 改进版**(扩展 media-gen-mcp,diagram 独立模块)。

**核心修正理由**:用户心智是"生图"(无论 AI 像素图还是矢量结构图,都是"出一张图"),不是"管理多个 MCP"。"合 ≠ 必须抽象" —— 一个 MCP 内部可以**模块化但不共享接口**(generate_diagram 独立,不进 Provider)。产品先例(Notion / Figma / Claude 统一入口 + 内部技术分离)证明这是成功范式。

**升维**:media-gen-mcp 的产品定位不只是"AI 生图 + 结构图",而是 **"Claude Code 的统一生图工具"** —— 覆盖 AI 像素图、结构图、数据可视化(Vega-Lite)、QR 码、数学公式(KaTeX)、OG 图/文字卡片(Satori)、图标(Iconify)。这些对用户都是"出一张图",一个 MCP 全覆盖 > 多个 MCP 分治。

**A 改进版设计**:
```
media-gen-mcp(一个 MCP,用户一个入口)
├── generate_image   → Provider 体系(agnes/zhipu,AI 模型)
├── create_video     → Provider 体系
├── get_video        → Provider 体系
└── generate_diagram → 独立 diagram 模块(DSL→SVG,不进 Provider)
```

> 以下 6.1-6.4 保留原技术分析(B 的论据),但**最终推荐以 6.0 修正为准**。

### 6.1 三方案对比

| 维度 | 方案 A:扩展 media-gen-mcp | **方案 B:新建 diagram-mcp** | 方案 C:插件化重构 |
|---|---|---|---|
| **类型** | 同 MCP 增工具(单体扩展) | 独立 MCP(按范式分治) | provider + capability 插件 |
| **范式边界** | 混杂(diagram 与 AI-gen 塞进一个包) | **清晰**(AI 像素-gen vs 确定性矢量渲染各自独立) | 用元层掩盖范式冲突 |
| **provider 抽象** | 被稀释(需硬造假的 DiagramProvider) | **保持纯粹** | 插件框架逼出漏水接口 |
| **diagram 抽象** | 受限(无法自然表达 DiagramEngine) | **拥有自己天然的 DiagramEngine**(mermaid/d2/graphviz/plantuml) | 退化成 B 却多一层间接 |
| **依赖树** | diagram 渲染依赖污染 AI 包 | **依赖隔离最干净** | 与 A 相近 |
| **演进节奏** | 渲染引擎迭代缠 AI provider 变更 | **各自独立** | 重构风险高 |
| **用户配置成本** | 装一个 MCP | 装两个(仅多两行配置,一次性) | 装一个但需理解插件 |
| **LLM 友好度** | 中(同 server 内需区分两种语义) | **最高**(工具集语义内聚单一,职责边界清晰) | 短期无增益 |
| **MCP 哲学契合** | 违背(god-server) | **符合**("一 server = 一连贯能力域") | 过度工程 |
| **推荐度** | 不推荐 | **推荐** | 不推荐 |

### 6.2 推荐方案 B:新建 diagram-mcp

**决定性理由:共享抽象面 ≈ 0。**

把 `generate_diagram` 塞进 media-gen-mcp(方案 A),它不调 `getProvider`、不碰 `registry/poll/config/videoConstraints`,与 provider 抽象零交集——所谓"一个 MCP"实质只是把两套不相关的依赖与范式塞进同一个 npm 包,是**文件摆放不是架构**。强行造一个 `DiagramProvider` 去平行 `ImageProvider` 是**抽象摆拍**(diagram 引擎没有"厂商/API key/限流"概念,它是本地确定性的渲染库)。

方案 C(插件化)是用更大的过度工程去掩盖同一个范式冲突:在 **2 provider / 4 tool** 的规模上引入 capability 插件元层是 **YAGNI**,且 provider 抽象本身已经是插件点;插件框架会逼出一个漏水的最小公倍数接口来硬捏 AI-gen 与确定性渲染,最终仍会退化成 B 的分离,只是多了一层间接 + 重构风险。

**方案 B 尊重范式边界**,让 provider 抽象保持纯粹,让 diagram-mcp 拥有自己天然的 `DiagramEngine` 抽象(mermaid/d2/graphviz/plantuml),依赖树与演进节奏各自独立。多 MCP 的唯一真实成本是一次性的两行安装配置——CC 原生聚合多 server 工具,消费侧看到的是扁平工具列表,UX 无损耗。

### 6.3 分工:LLM 在哪一侧?

把"NL → DSL"留在 **host agent 侧**(它本就是 LLM),diagram-mcp 只管**确定性渲染**(DSL 文本进、SVG/PNG 出、同步即时返回)。这一分工反而强化了 B 的分离正确性——diagram-mcp 不需要也不应该内置 LLM 调用。

### 6.4 唯一选 A 的场景

你极度重视"单 MCP 极简"且接受范式耦合(例如仅个人用、diagram 引擎只有一个、永不演进)。但这以污染一个已经干净的设计为代价,不划算。

## 七、渲染引擎推荐:轻量本地渲染栈

### 7.1 结论先行

**主栈 = D2(SVG)+ isomorphic-mermaid(SVG,MCP 进程内)+ Graphviz dot(SVG 兜底),全部默认 SVG,彻底避开 Java 和 Chromium。**

原则:**进程内渲染优先**(Mermaid 走 isomorphic-mermaid),**原生二进制 spawn 次之**(D2/dot),全部默认 SVG,彻底避开 Java 和 Chromium。

### 7.2 六引擎依赖矩阵

| 引擎 | 运行时 | 渲染路径 | SVG | PNG(无浏览器) | 依赖重量 | 评价 |
|---|---|---|---|---|---|---|
| **D2** | Go 单二进制 | spawn CLI `d2 in.d2 --stdout` | 原生零依赖 | 需 Playwright/Chromium,**或用 resvg 绕开** | 最轻 | 首选 |
| **Mermaid(isomorphic-mermaid)** | Node(jsdom) | **进程内** `require('isomorphic-mermaid')` | 原生无需浏览器 | 需额外光栅化 | 轻 | Mermaid 最佳路径 |
| Mermaid(mmdc) | Node+Puppeteer+Chromium | spawn CLI | 原生 | 原生 | **最重**(冷启动 ~2-3s + 数百 MB) | **避用** |
| **Graphviz dot** | C 单二进制 | spawn CLI `dot -Tsvg` | 原生 | **原生(无浏览器)** | 轻 | 兜底首选 |
| PlantUML | Java jar | spawn CLI `java -jar plantuml.jar -tsvg` | 原生 | 原生 | 重(JVM ~100-200MB + dot) | 仅复杂 UML |
| Excalidraw | React/浏览器 | 多走 headless 浏览器 | 原生 | 需浏览器 | 中-重 | 仅手绘风 |
| Kroki | Docker 聚合 | HTTP API | 统一 | 统一 | 重(Docker 栈) | 统一出口(自托管) |

### 7.3 MCP server 进程内渲染 vs spawn CLI

| 引擎类型 | 推荐路径 | 理由 |
|---|---|---|
| JS 原生引擎(Mermaid) | **进程内**(isomorphic-mermaid) | 直接 require 渲染 SVG,省掉浏览器 spawn 成本,延迟最低 |
| 非 JS 原生二进制(D2/dot) | **spawn CLI** | 独立原生二进制,spawn 开销 ms 级,比内嵌浏览器轻得多 |
| 浏览器/Java(PlantUML/mmdc/Excalidraw) | 默认不选 | 违背"轻量本地"目标 |

**核心洞察:Mermaid 的官方 mmdc 走 Puppeteer+Chromium(每次渲染 ~2-3s 冷启动 + 数百 MB),是最重的;但社区方案 isomorphic-mermaid 用 jsdom DOM shim 在纯 Node 里直接产 SVG,无需浏览器,是"MCP server 进程内渲染 Mermaid"的关键路径。**

### 7.4 SVG vs PNG

| 格式 | 推荐场景 | 理由 |
|---|---|---|
| **SVG(默认)** | MCP/CLI 场景、PPT、文档、大屏 | 矢量高清、可缩放、文件小、三家(D2/dot/Mermaid)零/低依赖产出 |
| PNG(仅位图时) | 贴不支持 SVG 的环境 | 避免 Chromium 的 PNG 路径:Graphviz dot 原生 PNG,或 D2 SVG→**resvg**(svg-to-png-cli,Rust)转换 |

### 7.5 渲染栈建议(自建 diagram-mcp 时)

```
generate_diagram(dsl, engine, format, ...)
│
├─ engine=mermaid → 进程内 require('isomorphic-mermaid') → SVG
│                                                   └─ PNG: resvg 转换
├─ engine=d2       → spawn `d2 --stdout` → SVG
│                                  └─ PNG: resvg 转换(避开 Playwright)
├─ engine=graphviz → spawn `dot -Tsvg` → SVG
│                              └─ PNG: `dot -Tpng` 原生(无浏览器)
└─ engine=plantuml → spawn `java -jar plantuml.jar -tsvg`(仅复杂 UML,可选)
```

**PlantUML / Kroki(Docker)/ Excalidraw(browser)仅在确需其特定能力(UML 深度/20+ DSL 聚合/手绘美学)时引入——它们都会带回 Java 或 Chromium/Docker 依赖,违背"轻量本地"目标,默认不选。**

### 8.2 描述协议设计(generate_diagram 工具 schema)

这是 diagram-mcp 的核心接口设计。原则:**DSL 文本进、SVG 出、同步即时返回、引擎可切换、错误结构化**。

#### 工具 1:generate_diagram(核心渲染)

```jsonc
// input
{
  "dsl": "graph TD; A-->B; B-->C",   // 必填,DSL 源码文本
  "engine": "mermaid",                // 默认 "mermaid",可选 d2|graphviz|plantuml
  "diagram_type": "flowchart",        // 可选,提示性:flowchart|sequence|class|state|
                                      //   er|architecture|dag(帮助引擎选布局)
  "format": "svg",                    // 默认 "svg",可选 png|pdf
  "theme": "default",                 // 可选,引擎主题名
  "output_mode": "inline"             // 默认 "inline",可选 file
  // "output_path": "/abs/path/x.svg" // output_mode=file 时必填
}

// output (成功)
{
  "ok": true,
  "engine_used": "mermaid",
  "format": "svg",
  "content": "<svg>...</svg>",        // inline 模式:SVG 文本 或 PNG base64
  "width": 800, "height": 600,        // 可选,渲染尺寸(矢量时为 viewBox)
  "warnings": []                      // 可选,非致命警告(如布局降级)
}

// output (失败)
{
  "ok": false,
  "error": {
    "code": "SYNTAX_ERROR",           // 见错误码表
    "message": "Parse error on line 2",
    "line": 2, "column": 5            // 可选,定位信息
  }
}
```

#### 工具 2:validate_diagram(快速语法校验,不渲染)

```jsonc
// input
{ "dsl": "...", "engine": "mermaid" }
// output
{ "valid": true } 
// 或
{ "valid": false, "errors": [ { "line": 2, "message": "..." } ] }
```

**价值**:校验比完整渲染快,适合在 LLM 生成后立即前置校验、或在"生成-校验-重试"闭环中快速拦截。

#### 工具 3:list_engines(声明能力)

```jsonc
// output
{
  "engines": [
    {
      "name": "mermaid",
      "version": "11.x",
      "healthy": true,                 // 引擎是否就绪
      "diagram_types": ["flowchart","sequence","class","state","er","gantt","mindmap","c4"],
      "formats": ["svg","png"],
      "notes": "进程内渲染,延迟最低"
    },
    { "name": "d2", "healthy": true, "diagram_types": ["architecture","flow"], "formats": ["svg","png"] },
    { "name": "graphviz", "healthy": true, "diagram_types": ["dag","er","state"], "formats": ["svg","png"] }
  ]
}
```

**价值**:让 host agent(LLM)在生成 DSL 前查询可用引擎与能力,据 `diagram_type` 选最合适的 `engine`。

#### 错误码表

| 错误码 | 含义 | 处置建议 |
|---|---|---|
| `SYNTAX_ERROR` | DSL 语法错误 | 回喂 LLM 自动重试(附行列定位) |
| `UNSUPPORTED_TYPE` | 引擎不支持该 diagram_type | 切换引擎(如 state 图切 PlantUML) |
| `ENGINE_UNAVAILABLE` | 引擎未安装/启动失败 | 检查依赖,降级到可用引擎 |
| `LAYOUT_TIMEOUT` | 布局超时(大图) | 拆分图表或降级布局算法 |
| `INVALID_OUTPUT_PATH` | output_mode=file 但路径不可写 | 修正路径或改 inline |

#### 设计要点(为什么这么设计)

1. **engine 与 diagram_type 分离**:`engine` 是渲染后端(确定性选择),`diagram_type` 是图类型(提示性,帮助引擎选布局)。LLM 先按 `list_engines` 的 `diagram_types` 匹配需求,再选 `engine`,再产出对应 DSL。
2. **默认 SVG**:矢量优先,位图按需。
3. **同步即时返回**:diagram 渲染是确定性的本地操作,无需 media-gen-mcp 那套 poll/registry 异步机制——这正是两种范式的分界,也是方案 B 正确性的体现。
4. **validate 独立工具**:比 generate 轻,适合闭环校验;generate 内部也会校验,但独立工具让"只校验不渲染"成为可能。
5. **错误结构化**:code + line + column 让 LLM 能精确修正,而非面对一个模糊报错。
6. **warnings 字段**:非致命问题(如布局降级、主题缺失回退)走 warnings,不阻断 ok=true,但让 LLM/host 感知。

### 8.3 diagram-mcp 目录结构建议


## 九、风险与边界

### 9.1 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **Mermaid mmdc 的 Chromium 依赖** | 安装体积大(~300MB)、冷启动慢(2-3s) | 用 isomorphic-mermaid 进程内渲染绕开;或 Rust 渲染器 mmdr/mmdflux(500-1000x 快,但较新) |
| **D2 训练语料少,LLM 零样本错误率高** | 生成的 D2 语法错误多于 Mermaid | 给 1-2 个 few-shot 示例;或让 LLM 先出 Mermaid 结构再翻译成 D2 渲染 |
| **Graphviz 大图布局慢/交叉多** | 复杂 DAG 渲染超时 | 拆分图表;LAYOUT_TIMEOUT 错误码 + 降级;考虑 ELK 布局 |
| **uml-mcp 默认走 Kroki 云** | DSL 明文出本机(隐私) | 数据敏感时必须 `docker compose` 自建本地 Kroki+PlantUML 栈 |
| **draw.io/tldraw XML/JSON LLM 生成成本高** | token 浪费、格式错误 | 不让 LLM 直出;若要用,让 LLM 出 Mermaid 再导入 |
| **tldraw 非 OSI 开源(商用需付费)** | 生产环境许可成本 | 不作为通用 LLM 生成目标 |

### 9.2 边界(不做什么)

1. **不让 diagram-mcp 内置 LLM 调用**:"NL → DSL"是 host agent 的职责,diagram-mcp 只管确定性渲染。混入 LLM 调用会模糊范式边界,退回方案 A 的问题。
2. **不默认引入 Java/Chromium/Docker**:违背"轻量本地"目标。PlantUML/Kroki/Excalidraw 仅作为"确需特定能力时可选启用",默认关闭。
3. **不追求"单一 server 覆盖 30+ 类型"**:除非有明确的全覆盖 + 100% 离线需求(现状无此组合:uml-mcp 走云,专用 server 只支持单 DSL)。2-3 个引擎覆盖 90%+ 场景已足够。
4. **不把 tldraw/Excalidraw/React Flow 作为 LLM 直出目标**:它们是画布应用,适合做渲染后的编辑前端,不是 DSL。
5. **不在 2 provider/4 tool 规模上做插件化(方案 C)**:YAGNI;provider 抽象本身已是插件点;过度工程会增加重构风险。

### 9.3 决策可逆性

- **阶段 0 → 阶段 1** 是零风险过渡:装现有 MCP 验证工作流,不满意再自建,投入可控。
- **方案 B 本身可逆**:diagram-mcp 独立,若未来 diagram 能力需要与 AI-gen 深度耦合,可再合并;但反之(从 A 拆出 B)重构成本高。B 保留了演进自由度。
- **引擎可插拔**:`DiagramEngine` 接口让新增/替换引擎(如未来 D2 语料丰富后升为主力)不影响工具协议。
