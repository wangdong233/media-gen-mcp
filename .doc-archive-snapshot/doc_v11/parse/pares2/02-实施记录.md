### 2.1 核心入口 `normalizeEngineError`(src/handlers/error-format.ts)

```ts
export function normalizeEngineError(
  engine: NormalizedEngine,
  rawMsg: string,
  ctx: ErrorContext,
  engineHint?: NormalizedEngine,
): string {
  // 优先用结构性 hint 路由(替代旧版"按 rawMsg 内容猜测路由"的脆弱方案)
  const routeEngine: NormalizedEngine = engineHint ?? engine;
  const patterns = knownErrorPatterns[routeEngine] ?? [];
  lastMatched = false;

  // D2 特殊路径:rawMsg 是 JSON 数组字符串,先 try-parse 取首条匹配
  const candidates: string[] = routeEngine === "d2" ? extractD2Errmsgs(rawMsg) : [rawMsg];

  for (const candidate of candidates) {
    for (const p of patterns) {
      const m = p.rx.exec(candidate);
      if (m) {
        lastMatched = true;
        // 不覆盖 ctx.raw —— make 函数内 pickD2Line 需要从原始 rawMsg 提取行号
        // (PRD §4.2.4 骨架写 `{ ...ctx, raw: candidate }` 与 §4.2.3 注释自相矛盾,采 §4.2.3)
        const partial = p.make(m, ctx);
        return formatNormalized({ ...partial, engine: routeEngine });
      }
    }
  }
  // 兜底:未命中任何 pattern,返回原 rawMsg + 标记(反崩溃契约,绝不抛)
  return `[${engine}] ${rawMsg}\n(未识别的错误形态,请把此消息反馈给 media-gen-mcp 维护者补 knownErrorPatterns 表。原始输入前 80 字符:${String(ctx.input).slice(0, 80)})`;
}
```

## 3. 实测发现的 PRD / 分析文档缺陷(实施时订正)

按 01-功能分析.md §0 "如实施中发现分析有误,先修分析文档再继续"原则,以下 4 处缺陷在实施阶段经实测发现并直接订正代码。**未发现需要修分析文档的阻断性错误**。

### 3.1 D2 pattern 1 rx `\w+` 漏掉含连字符属性(stroke-width)

- **症状**:实测 `expected "stroke-width" to be a number between 0 and 15` 不匹配 pattern 1 的 `/expected "(\w+)" to be a number between (\d+) and (\d+)/`,落入兜底"未识别错误"。
- **根因**:JS `\w` 等价 `[A-Za-z0-9_]`,不含 `-`。`stroke-width` 在 `\w+` 处停在 `stroke`,正则期望紧跟 `"` 但遇到 `-`,失配。
- **影响**:D2 数值属性大量含连字符(stroke-width / font-size / border-radius / stroke-dash),原 rx 全部漏匹配 —— 与 PRD §4.2.2 pattern 3 同款 bug(那里已用 `[\w-]+` 修复)。
- **订正**:`/expected "([\w-]+)" to be a number between (\d+) and (\d+)/`。代码注释标记为实施时实测发现。

### 3.2 D2 pickD2Line 行号索引基准错误

- **症状**:实测真实 D2 输出 `[{"range":"index,0:25:25-0:28:28","errmsg":"index:1:26: ..."}]`,按 PRD §4.2.3 原 pickD2Line(只解析 range 字段)得到 line=0,但 errmsg 实际显示 line 1。
- **根因**:D2 range 字段是 **0-indexed**(L=0 表示第一行),errmsg 是 **1-indexed**(L=1 表示第一行)。同一行在两处差 1。PRD §4.2.3 的样本 `index,1:22:29-1:25:32` 是**假设性样本**(range L=1 应表示第 2 行,但 PRD 称 "line 1"),与真实引擎输出格式不一致。
- **影响**:用户看到的 "line 0" 与 D2 errmsg 内的 "line 1" 矛盾,LLM 困惑。
- **订正**:pickD2Line 优先从 errmsg 字段 `index:(\d+):` 提取 1-indexed 行号(在 JSON 字符串里 errmsg 部分唯一可识别 —— range 字段用 `index,L:C` 逗号分隔,不会冲突);fallback 才用 range 字段并 +1 修正。

### 3.3 resvg pattern 2 字体错误 rx `[^']` 排除单引号,反而漏匹配

- **症状**:实测 `default font-family '' not found` 不匹配 pattern 2 的原 rx `/default font-family[^']{0,5}not found/`,落入兜底。
- **根因**:resvg 真实消息中间**就有** `''` 引号(`default font-family '' not found`)。PRD §4.2.2 用 `[^']{0,5}` 排除单引号的意图已不可考(可能想避免贪婪),但实际效果是排除掉了真实消息必需的字符。
- **影响**:resvg 字体加载失败场景完全未覆盖。
- **订正**:`/default font-family.{0,15}not found|No match for.{0,30}font-family|.../i`(`.` 允许引号 + 短距离上限防贪婪)。同样修第二条 `No match for.{0,30}font-family`。

### 3.4 normalizeEngineError 主函数 ctx.raw 覆盖矛盾

- **症状**:PRD §4.2.4 骨架写 `const partial = p.make(m, { ...ctx, raw: candidate });`,把 ctx.raw 覆盖为单条 candidate errmsg。但 §4.2.3 helper 注释明确写 "raw 是整个 e.message(JSON 数组字符串),取第一个 entry.range"。两处自相矛盾。
- **根因**:覆盖后 pickD2Line 在 candidate(单条 errmsg 字符串)里找不到 `"range":"..."` JSON 壳,行号永远 undefined。
- **订正**:不覆盖 ctx.raw(make 函数从 ctx.raw 取原始 JSON 提取行号;candidate 仅用于 rx 匹配)。代码内注释明确说明 PRD 自相矛盾,本实现采 §4.2.3。

> **以上 4 处订正均未偏离分析文档 §0 plan_ok 的执行路径**,都是 PRD/分析内部矛盾的局部修复,不影响整体架构。01-功能分析.md §10 步骤核对表无需更新。
