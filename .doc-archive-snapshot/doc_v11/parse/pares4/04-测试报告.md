### 2.4 设计裁决(测试设计层)

| 决策 | 理由 |
|---|---|
| ② 静态验证 fatal 守卫数(11)+ 动态调 assertOutputClean 而非 prototype-patch handler | ESM live binding 限制 + 不改 dist/ 代码(立场红线)。改用两层证据:(a)静态 grep 11 个 `if "fatal" in checked) return err(` 守卫都在;(b)直接调 assertOutputClean(zero.png) 验证返 fatal 结构 → handler 接到这个结构必走 err() 路径(代码静态可证) |
| ③ 用 valid.gif(<1KB 阈值)触发 min-size warning | 这是 pares4 R5 + 03-审查 R1-P5 接受的"已知 warning",作为 warning 透传契约的最便宜触发器 |
| ⑤ margin=4 而非 margin=2(默认) | qrcode lib 自身在 margin<4 时会产 `静默区 N 模块低于 ISO 18004 推荐` warning,会污染"无 warning 时响应无 warnings 字段"断言。margin=4 让 qrcode lib 也不出 warning,真正验证 byte-identical |

### 5.3 warnings 字段条件展开(byte-identical 兼容)

src/index.ts 11 个 handler 钩子全部用以下两种条件展开模式之一:
- **已有 warnings 字段的工具**(qrcode/chart/card/render_svg 等):
  ```ts
  const mergedWarnings = [...(rendered.warnings ?? []), ...checked.warnings];
  return ok({ format, local_path: fp, ...(mergedWarnings.length ? { warnings: mergedWarnings } : {}) });
  ```
- **原本无 warnings 字段的工具**(diagram/formula/icon/render_video):
  ```ts
  ...(checked.warnings.length ? { warnings: checked.warnings } : {})
  ```

两种模式都保证:**无 warning 时响应结构 byte-identical**(无 warnings 字段)。

## 7. 无法自动验证项(诚实标注)

### 7.1 prototype-patch 劫持 handler 验证 fatal → isError 端到端

- **测试设计原意**:用 `--import preload.mjs` 把 `dist/checks/output-checker.js` 的 `assertOutputClean` monkey-patch 成"永远返 fatal",然后 spawn server,调 handler 验证响应 isError:true。
- **无法自动验证的根因**:ESM `import { assertOutputClean }` 是静态绑定 + module 缓存,preload 里改 export 对已 import 的 `dist/index.js` 不生效(live binding 仅对 namespace 对象生效,对解构导入不生效)。要让劫持生效需直接改 `dist/index.js`(违反"不改编译产物"立场红线)或侵入式地在 output-checker.ts 加测试钩子(违反"不改源码做测试"原则)。
- **替代证据三层**:
  1. **静态证据**:grep 验证 `src/index.ts` 11 个钩子都有 `if ("fatal" in checked) return err(checked.fatal.message)` 守卫(实际 11/11 命中);
  2. **动态证据(单元层)**:`test/check-render-output.test.mjs:188` `assertOutputClean handler entry > zero.png → {fatal, quality}(任何 profile throw)` 直接调 assertOutputClean(zero.png),验证返 `{ fatal: Error, quality: ... }` 结构(即 handler 接到的契约);
  3. **静态代码路径**:handler 拿到 `{ fatal: Error }` 后,`if ("fatal" in checked) return err(...)` 是 TypeScript narrowing 必走路径,无任何分支可绕过。
- **结论**:三层证据合并等价于"end-to-end fatal 拦截"验证。**不阻断 P0-4 收尾**。

### 7.2 generate_image / create_video / get_video / render_video 真实 provider 调用

- **测试设计原意**:对这 4 个需要联网(Agnes AI / Zhipu)或 Chrome 的工具做端到端真实 handler 调用。
- **无法自动验证的根因**:
  - generate_image / create_video / get_video 需要 API key + 网络访问外部 provider,本测试环境无可靠网络 + key 供给;
  - render_video 需要 Chrome headless + ffmpeg 实跑,环境依赖重。
- **替代证据**:
  1. **钩子接通静态证据**:src/index.ts:629(generate_image)+ :785(create_video)+ :806(get_video)+ :1186(render_video)4 个钩子都已插入,与本地工具同等模式;
  2. **handler 行为契约**:这 4 个工具的钩子用 `if (localPath)` / 循环 per-image check 守卫,downloadAsset 失败时 localPath 为空不校验(R1-P4 + R10 守住"空路径不阻断")。
- **结论**:钩子在 src/index.ts 已静态接通(与本地工具同模式),真实 provider 调用留用户测试环境做最终验收。**不阻断 P0-4 收尾**。
