## 1. 背景与目标

### 1.1 解决什么盲区

media-gen-mcp 把"同输入同输出可入 git"作为核心立场,但**没有任何产物侧守门员**:

- `scripts/` 目录下只有一个 `check-schema.mjs`(`scripts/check-schema.mjs:1-62`,62 行),它只做 3 个 inputSchema 枚举断言(`numFrames/frameRate.enum === provider.videoConstraints()`、19 工具名清单、mode/resolution 三值),**完全不触达渲染产物字节**。
- 每个 generate_*/render_* handler 的成功路径就是"调 `renderXxx()` → `writeLocalRender()` 落盘 → 返回 `local_path`"(`src/index.ts:516-535`、`src/index.ts:938-1094`),**对落盘文件零校验**:零字节 PNG、全透明 PNG、SVG 含 `NaN/undefined`、MathJax 输出空 `<svg>`、QR 编码成功但解码不回原文、Provider 返回 HTML 错误页被当成功字节落盘——这些 bug 全部会以 `isError:false` 静默返回。
- MEMORY 已记载真实代价:**"OCR 渲染必崩(pdfjs v6 未导出 NodeCanvasFactory)被 text-layer-only 测试盲区掩盖"**——正是缺产物侧守门员的直接后果。
- AI provider 工具(`generate_image`/`create_video`/`get_video`)下载的产物格式契约完全缺失:Provider 返回空 body、半截 dataURI、HTTP 错误页被当成功返回的 bug 都可能发生。

### 1.3 不做什么(明确边界)

- **不做**渲染前的输入校验(DSL/schema/pre-flight lint)——那是 P0-2 / P1-1 / P1-2 的范围。
- **不做**像素级 golden byte-compare——那是 P0-3 的范围。P0-4 只做"产物本身的物理合法性校验",不与任一基线比。
- **不做**截图视觉评分(pHash/SSIM)——P0-4 只关心"能不能打开/有没有内容",不关心"漂不漂亮"。
- **不做**对 `extract_text`/`extract_table`/`analyze_chart`/`describe_image`/`extract_pdf`/`get_pdf`/`list_models`/`list_vision_capabilities` 这 8 个非渲染工具的产物校验——它们返回的是 JSON 文本,无字节级产物可守。本 P0 只覆盖 11 个有 `local_path` 或字节产物的工具(generate_image / create_video / get_video / generate_diagram / generate_qrcode / generate_chart / generate_formula / generate_icon / generate_card / render_svg / render_video)。

### 3.2 借鉴/不借鉴的边界

**借鉴(纯范式,1:1 平移)**

| 借鉴项 | 原因 |
|---|---|
| `addCheck(name, ok, details)` wrapper 模式 | 结构统一,便于消费方(P0-5 viewer / CI / handler)解析 |
| `{ok, file, checks[], composition{}}` 输出 schema | 已被 Archify 9 个测试用例锁死,成熟结构 |
| CLI 黑盒测试范式(`execFileSync` + `JSON.parse(stdout)`) | 与 `check-schema.mjs` 同构,团队熟悉 |
| profile 双轨思想(standard 警告 / strict 阻断) | 让同一份 checker 服务不同质量档;对应到 media-gen-mcp 改为 standard 默认 / strict 环境变量切换 |
| LLM 友好错误契约(每条 issue 带 code + severity + 可读 details) | 消费方是 LLM,不是人 |

**不借鉴(立场/场景不同)**

| 不借鉴项 | 理由 |
|---|---|
| Archify 的 7 类检查**内容**(single_svg/finite_svg/orthogonal_arrows/crossings/border_runs/rhythm/legend_clearance) | Archify 守的是 HTML/SVG **DOM 结构语义**(箭头几何、frame 边框、legend 避让);media-gen-mcp **没有关系几何这层**,DOM 级检查不适用。**只复用 wrapper 和 schema,不复用检查项**。 |
| Archify 的 `data-quality-profile` SVG 属性驱动 profile | media-gen-mcp 的 PNG/MP4 产物无 DOM 属性。**改为环境变量 `MEDIA_GEN_CHECK_PROFILE=standard|strict`**(对齐 config.ts 已有模式) |
| `composition.metrics` 12 字段 / `suggestedLimits` 4 字段 | Archify 这些字段全是几何度量(properCrossings/maxBends/maxStretch/minSegmentPx 等),media-gen-mcp 无对应物。**裁剪为 `{ pngPixels, svgDrawNodes, mp4DurationMs }` 等本域度量** |
| Archify geometry.mjs 670 行(properSegmentIntersection/collectBorderRuns 等) | 完全用不到,不引用不 reimplement |

**核心映射**:Archify 守"DOM 级布局是否漂亮",media-gen-mcp 守"二进制产物的可解码性 + 物理合法性"。**可复用的是 wrapper 范式而非检查内容**——三层(addCheck 模式 + 输出 schema + CLI 黑盒测试)都能 1:1 平移。

### 4.2 `src/checks/output-checker.ts` 接口与检查矩阵

#### 4.2.1 顶层类型与输出 schema

```ts
// src/checks/output-checker.ts
export type Profile = "standard" | "strict";
export type Severity = "fatal" | "error" | "warning";  // fatal=任何 profile throw → isError:true;error(hard-fail)=strict profile throw;warning=永不 throw(对齐 §4.4 真相源三档)

export interface CheckIssue {
  severity: Severity;
  code: string;            // e.g. "png/magic-bytes", "svg/has-content"
  message: string;         // 人类可读 + 阈值 + 修复动词(Archify 范式)
  details?: Record<string, unknown>;
}

export interface CheckResult {
  name: string;            // 检查名 e.g. "magic_bytes"
  ok: boolean;
  details: string[];       // 人类可读,带 [code] 前缀
}

export interface OutputReport {
  schemaVersion: 1;
  profile: Profile;
  status: "pass" | "fail";             // fail 当且仅当 fatals > 0(任何 profile)或 errors > 0(strict profile)
  ok: boolean;                         // === (status === "pass")
  file: string;                        // 绝对路径
  kind: "png" | "jpeg" | "webp" | "svg" | "mp4" | "gif" | "webm" | "unknown";
  checks: CheckResult[];
  summary: { fatals: number; errors: number; warnings: number };
  metrics: {
    bytes?: number;
    width?: number;
    height?: number;
    svgDrawNodes?: number;             // <path>/<use>/<rect>/<circle> 等绘制节点数
    mp4DurationMs?: number;
    mp4HasVideoTrack?: boolean;
  };
  issues: CheckIssue[];
}

export interface AssertOptions {
  tool: string;                        // "generate_qrcode" 等,用于 issue 定位
  format?: string;                     // 工具声明的 format,用于交叉验证
  profile?: Profile;                   // 默认 standard;strict 从 env 读取
  originalInput?: unknown;             // QR 解码回原文时的比对待值
}
```

#### 4.2.2 检查矩阵(完整)

**fatal 检查(任何 profile 都阻断 `ok`,对应 Archify container_border_runs 的硬错误非对称性)**

| kind | code | 断言 | 失败消息(LLM 友好:阈值 + 修复动词) |
|---|---|---|---|

```ts
export async function checkOutput(
  filePath: string,
  opts: { tool?: string; format?: string; profile?: Profile; originalInput?: unknown } = {},
): Promise<OutputReport> {
  const profile: Profile = opts.profile ?? (process.env.MEDIA_GEN_CHECK_PROFILE as Profile) ?? "standard";
  const buf = await fs.readFile(filePath);
  const kind = detectKind(filePath, buf, opts.format);
  const checks: CheckResult[] = [];
  const issues: CheckIssue[] = [];
  const metrics: OutputReport["metrics"] = { bytes: buf.length };

  // 按分派执行检查矩阵(伪代码,实际按 kind 分派到 checkSvg/checkPng/checkMp4 等子函数)
  await runFatalChecks(checks, issues, metrics, filePath, buf, kind, opts);
  await runKindSpecificChecks(checks, issues, metrics, filePath, buf, kind, opts, profile);
  await runToolSpecificChecks(checks, issues, metrics, filePath, buf, kind, opts, profile);

  const fatals = issues.filter((i) => i.severity === "fatal").length;
  const errors = issues.filter((i) => i.severity === "error").length;
  const warnings = issues.filter((i) => i.severity === "warning").length;
  const status: "pass" | "fail" = (fatals > 0 || (errors > 0 && profile === "strict")) ? "fail" : "pass";
  return { schemaVersion: 1, profile, status, ok: status === "pass", file: path.resolve(filePath),
           kind, checks, summary: { fatals, errors, warnings }, metrics, issues };
}

/** handler 钩子:fatal=任何 profile throw → isError:true;error(hard-fail)=strict profile throw;warning=永不 throw(对齐 §4.4 真相源三档,见 §9 未决点 16) */
export async function assertOutputClean(
  filePath: string,
  opts: AssertOptions,
): Promise<{ warnings: string[]; quality: OutputReport } | { fatal: Error; quality: OutputReport }> {
  const report = await checkOutput(filePath, opts);
  // fatal 错误(任何 profile)Day 1 即 throw —— 必须先判,否则 standard 档下零字节 PNG(file/readable)/HTML 伪装 PNG(magic-bytes)会被降级为 warning,handler 永远看不到 fatal 键 → §4.4 "fatal 自 Day 1 即 isError:true" 落空
  const fatals = report.issues.filter((i) => i.severity === "fatal");
  if (fatals.length > 0) {
    return { fatal: new Error(fatals.map((i) => `[${i.code}] ${i.message}`).join("; ")), quality: report };
  }
  // hard-fail(error)仅在 strict profile 升 isError;standard 档降级为 warning
  const hardFails = report.issues.filter((i) => i.severity === "error");
  if (hardFails.length > 0 && report.profile === "strict") {
    return { fatal: new Error(hardFails.map((i) => `[${i.code}] ${i.message}`).join("; ")), quality: report };
  }
  // 永不 throw:warning + (standard 档下)hard-fail 降级项
  const warnings = report.issues
    .filter((i) => i.severity === "warning" || (i.severity === "error" && report.profile === "standard"))
    .map((i) => `[${i.code}] ${i.message}`);
  return { warnings, quality: report };
}
```

### 4.4 profile 双轨 + warning-only 灰度两周再升 fail 策略

| 阶段 | profile 默认 | fatal 错误(file/readable、magic-bytes、container-decodable) | hard-fail 错误(decodable、dimensions-sane、svg/*) | warning(non-blank、tracks-present) |
|---|---|---|---|---|
| **Week 1-2 灰度期**(默认) | `standard` | **throw → isError:true**(这类无歧义,直接 fail) | warning 写到响应 `warnings[]`,`isError:false` 不变 | warning 写到响应 `warnings[]` |
| **Week 3+ 稳定期**(默认) | `standard` | throw → isError:true | **warning 写到响应 `warnings[]`**(维持,不升)——理由:resvg 跨版本、MathJax 字体更新等可能合法触发 | 同上 |
| **CI/发版强制档**(`MEDIA_GEN_CHECK_PROFILE=strict`) | `strict` | throw | **throw → isError:true** | warning |

**为什么 fatal 直接 fail 而 hard-fail 要灰度**:

- fatal 类(file/readable、magic-bytes、container-decodable)**无歧义**:0 字节 PNG 一定是 bug,不可能"勉强能用"。这类自 Day 1 即 `isError:true`。
- hard-fail 类(decodable、dimensions-sane、svg/has-content)**有歧义**:resvg 跨版本可能让 PNG 重编码失败但人眼可见;MathJax 字体更新可能让 SVG 暂无 path 但渲染器下次修复。**先 warning-only 跑两周,统计真实误报率,再决定哪些升 fail**。
- 严格档(`strict`)只在 `npm test`/CI 跑,把所有 hard-fail 升 `isError`,防回归。生产调用方默认不感知。

**灰度退出标准**(两周后评估):

- 若 warning 触发率 < 1% 且无合法产物被误报 → hard-fail 升 `isError`(默认 standard 档)。
- 若某条 hard-fail 误报率 > 5% → 该条降级为 warning,加 caveats 说明。
- 决策记录到 `doc_v11/P0-4-产物守门人脚本实施规划.md` 的 §9(本文档维护)。

## 7. 风险与缓解(含 license 风险)

### 7.1 误报风险(hard-fail 升 isError 后拦截合法产物)

- **风险**:resvg 跨版本 PNG 重编码失败、MathJax 字体更新让 SVG 暂无 path,可能让合法产物被判 fail。
- **缓解**:§4.4 灰度策略——默认 standard 档只 warning,两周统计真实误报率,误报 > 5% 的检查降级 warning。
- **回滚**:`MEDIA_GEN_CHECK_PROFILE=standard`(已是默认)+ `MEDIA_GEN_CHECK_DISABLE=1`(灾难档)。

### 7.2 ffmpeg-static 调用阻塞风险

- **风险**:`ffmpeg -i <file> -f null -` 在大 MP4 上可能跑几秒,阻塞 handler 返回。
- **缓解**:① 用 `spawnSync` 加 timeout(5s),超时视为 `mp4/container-decodable` warning(不 fail);② render_video 产物通常 <10s 时长,5s 足够;③ CI 档(strict)可放宽到 30s。
- **代码骨架**:
  ```ts
  const r = spawnSync(ffmpegPath, ["-i", filePath, "-f", "null", "-"], { timeout: 5000, encoding: "utf-8" });
  if (r.signal === "SIGTERM") issues.push({ severity: "warning", code: "mp4/timeout", message: "..." });
  ```

### 7.3 **license 风险:ffmpeg-static 是 GPL-3.0-or-later(必须点名)**

- **事实**:`node_modules/ffmpeg-static/package.json` 的 `"license"` 字段 = `"GPL-3.0-or-later"`(我实地核实,**不是调查报告说的 LGPL**)。
- **当前状态**:`render-video.ts` 已用 ffmpeg-static 作为 dependencies(`package.json:42`),这个 license 暴露**今天已存在**,P0-4 不新增暴露,只是复用已有二进制。
- **立场评估**:media-gen-mcp 自身是 MIT,通过 npm install 分发 GPL 静态二进制**存在 license 温床问题**——严格意义上,下游用户分发媒体产物时可能受 GPL 传染(法律灰区:ffmpeg 二进制是独立作品,但静态链接 build 的 ffmpeg 含 GPL 编解码器)。
- **P0-4 决策**:**不新增 ffmpeg-static 依赖**(复用已有),但 P0-4 文档(本文)必须点名这个 pre-existing 风险,建议维护者单开 issue 评估迁移到 `ffprobe-static`(LGPL-2.1)或纯 wasm 解码器。**这不是 P0-4 范围,但必须列在 open points**。
- **替代方案**(P0-4 内可选项):若不愿复用 ffmpeg-static,改用 `@napi-rs/canvas` loadImage 探测 MP4 首帧(不支持),或只做 magic-bytes 检查(ftyp box 前 8 字节)、放弃 container-decodable。**推荐还是复用 ffmpeg-static**,因为不新增暴露。

### 7.4 sharp 不引入(最少新增原则)

- **调查报告建议**引入 `sharp ^0.33`(Apache-2.0)替代 pngjs/jpeg-js/webpdecoder 三件套。
- **本规划不采用**,理由:① sharp 是原生编译包,跨平台 install 慢且某些 ARM/Alpine 环境装不上;② pngjs(纯 JS)+ @napi-rs/canvas(已 optionalDep)已覆盖 PNG/JPEG 解码;③ WebP 解码暂用 magic-bytes + 文件大小启发式(精度低但够),若实际有需求再单开 issue 引 sharp。
- ** stance**:严守"最少新增依赖",只用 pngjs(纯 JS、MIT、已传递存在)+ jsqr(Apache-2.0,QR 解码刚需)+ @xmldom/xmldom(MIT,SVG XML 解析)。

### 7.5 jsqr 解码失败 ≠ 编码失败(伪反例)

- **风险**:jsqr 对小尺寸或低对比度 QR 解码失败,但 qrcode 编码本身没错。
- **缓解**:qrcode/decode-roundtrip 失败时,**warning 而非 error**(对齐 §4.4 灰度),details 写明"jsqr 解码失败可能是阈值问题,肉眼扫码确认即可"。
- **未来**:可加 retry(放大 PNG 后再解)或换 decoder(zbar wasm)。

### 7.6 Archify license 未明(立场检查)

- **事实**:Archify bundle 中未明确 LICENSE 文件。
- **决策**:本规划**全部 reimplement**,不抄 Archify 651 行 check-render-output.mjs 代码,只用其 wrapper 范式(addCheck 模式 + 输出 schema + CLI 黑盒测试),这些是通用工程范式不受 license 约束。`src/checks/output-checker.ts` 是从零自研的产物侧检查器,与 Archify 守 DOM 几何的检查器**内容完全不重叠**(见 §3.2)。

### 7.7 handler 钩子漏装风险

- **风险**:维护者后续新增工具(generate_interactive_diagram 等)忘记插入 assertOutputClean。
- **缓解**:① `test/check-render-output.test.mjs` 加一条"工具覆盖完整性"测试:遍历 tools/list 返回的所有 generate_*/render_* 工具,断言每个都在 `src/index.ts` 里有对应 assertOutputClean 调用(正则扫源码);② SKILL.md / CONTRIBUTING 写明"新增渲染工具必须插入 assertOutputClean 钩子"(对齐 Archify "never edit renderer" 硬规则的精神)。

## 9. 未决问题(open_points,诚实列)

1. **`@napi-rs/canvas` optionalDependencies 是否一定随 npm install 装上**:用户环境 `npm install --no-optional` 会跳过。**当前规划**:pngjs 是主解码路径(PNG),@napi-rs/canvas 仅作 JPEG/WebP 解码增强;若 napi 缺失,JPEG/WebP 退化为只做 magic-bytes 检查并 warning("未装 @napi-rs/canvas,JPEG/WebP 像素解码跳过")。**待验证**:P0-4 实现时跑 `npm install --no-optional && npm test` 看是否仍绿。

2. **Vega-Lite `view.toSVG()` 输出是否真字节级稳定**:本 P0-4 不做 byte-compare(那是 P0-3 范围),但 svg/has-content 依赖"Vega 至少输出几个 `<path>/<rect>` 节点"。**待验证**:P0-4 实现时跑 2 次 renderChart 看 SVG 节点数稳定;若 Vega 偶发输出空 SVG,svg/has-content 触发 warning 但不阻断(standard 档)。

3. **resvg PNG 输出是否含 tEXt 时间戳 chunk**:若含,跨 resvg 版本 PNG golden byte-compare 会失败(影响 P0-3,不影响 P0-4——P0-4 只关心 PNG 能解码即可)。**本 P0-4 范围外**,但列在 open_points 提醒 P0-3 团队。

4. **ffmpeg-static 是 GPL-3.0-or-later(不是 LGPL)**:`render-video.ts` 已用,P0-4 复用。**严肃的 pre-existing license 问题**,建议维护者单开 issue 评估迁移路径。**P0-4 本身不新增暴露,但必须点名**。

5. **MP4 时长/帧率/编码精准校验**:本 P0-4 只做 container-decodable + tracks-present,不做 duration/fps/codec 精准检查。若需要,引入 `ffprobe-static`(LGPL-2.1)——但**本规划倾向不引入**,保持依赖最小化。待实际有产物被误放行再升级。

6. **WebP 解码深度检查**:本 P0-4 用 magic-bytes + 文件大小启发式,不做像素解码(@napi-rs/canvas 不支持 WebP 解码,sharp 不引入)。**待验证**:WebP 产物实际出错率;若高,引入 sharp 单独评估。

7. **generate_card 的 emoji CDN 路径(generate_card loadAdditionalAsset twemoji CDN)产物校验**:本 P0-4 只守"产物本身合法",不守"emoji 是否渲染"。若 Satori 因 CDN emoji 失败输出残缺 SVG,svg/has-content 仍 pass(因为有其他 path)。**待补**:mock fetch 或预置 emoji data URI fixture——但这是 P0-3 golden 的子问题,不在 P0-4 范围。

8. **profile=strict 触发是否只走环境变量**:Archify 由 SVG 根属性驱动,media-gen-mcp PNG/MP4 无 DOM 属性。本规划用 `MEDIA_GEN_CHECK_PROFILE` env。**open**:是否需要在工具入参加 `_qualityProfile` 内部字段(不暴露给 LLM,只供测试/CI 用)?倾向 NO(env 已够),但需在团队内确认。

9. **handler 钩子的并发开销**:11 工具每次调用多 1-2 次 fs.readFile + 1 次(可能)spawn ffmpeg。**待测**:对 MCP stdio 调用延迟影响;若 render_video 路径加 5s ffmpeg 探活太慢,改异步 fire-and-forget(只 log warning 不阻塞返回)。倾向同步,因为产物没校验完就返回违背 P0-4 初衷。

10. **generate_image 多张图(n=8)的校验耗时**:`localPaths.map((fp) => assertOutputClean(fp, ...))` 用 `Promise.all` 并发,8 张图 8 次解码。**待测**:pngjs 解码单张 1024×1024 PNG ~50ms,8 张 ~400ms,可接受;若大图 OOM 改串行 + 限流。

12. **调查报告冲突**:inv:p04-archify-checker 称 ffmpeg-static 是 "GPL/LGPL 二进制",但我实地核实 package.json 是 `GPL-3.0-or-later`。**已按实地核实为准**,但提醒读者调查报告的 license 标注不准。

13. **[已解决 2026-07-21] pngjs devDependency 版本与 P0-3 冲突 + §4.6 注释事实错误**

    **原问题**:P0-4 §4.6(line 436)曾写 `"pngjs": "^3.4.0"`(注释:"原传递依赖会被 npm prune 裁"),P0-3 §4.3(line 222)写 `"pngjs": "^5.0.0"`。当前 `package.json` 三块 dependencies 均未显式声明 pngjs(纯传递依赖),node_modules 实际装的是 5.0.0。同 PR 落地会触发 git 合并冲突;先后落地会触发 lockfile 漂移 + npm 嵌套两份 pngjs 共存。

    **裁决**:**统一为 `^5.0.0`,P0-4 是修改方**。已在 §4.6 line 436、§4.8 step 2(line 464)修正。P0-3 §4.3、line 86/630 无需改版本号(line 630 风险概率已下调,见 P0-3 §7.1)。

    **理由**:
    - 与现有传递版本对齐:`node_modules/pngjs/package.json:3` 是 `5.0.0`,`package-lock.json:2378-2386` 也是 `5.0.0`,`npm ls pngjs` → `media-gen-mcp-server@0.11.0 ... └─┬ qrcode@1.5.4 └── pngjs@5.0.0`。
