# doc_v4: 离线图片/视频生成技术深度调研

> 起因:Remotion / HyperFrames 等开源工具是否具备离线图片+视频生成能力?之前的模型调研是否不充分?
> 方法:3 个 agent 并行调研(Remotion/HyperFrames 生态 + 本地 AI 模型 + React-to-media 全景),2024-2026 最新数据。
> 日期:2026-07-17

---

## 核心发现

**Remotion / HyperFrames 是确定性渲染器(代码→像素),不是 AI 生成器(prompt→新图像)。两者不可互换。** 但它们确实能离线生成图片和视频——只是产出的是**设计驱动**的图(布局/动画/特效),不是**语义驱动**的写实图(猫/风景/人像)。

### 三个层面的结论

| 层面 | 能否离线? | 替代/补充当前架构? |
|---|---|---|
| **AI 写实图/视频** | ❌ 本地 SD/SVD 需要 GPU + 多GB 模型 + 分钟级延迟,不实用 | **保持 Agnes/Zhipu 云端** |
| **确定性视频**(动效/动画/字幕) | ✅ HyperFrames/Revideo/FFCreator 可离线 | **新增能力**(当前缺失) |
| **确定性图片**(卡片/海报/SVG) | ✅ 已有(Satori+resvg+Chrome) | **已有,可不换** |

## 一、Remotion vs HyperFrames vs Revideo

### 对比

| 维度 | Remotion | HyperFrames | Revideo |
|---|---|---|---|
| 图片输出 | ✅ `renderStill()` | ✅ `snapshot` | ⚠️(帧序列) |
| 视频输出 | ✅ `renderMedia()` | ✅ MP4/GIF/WebM | ✅ `renderVideo()` |
| 渲染引擎 | Headless Chrome + FFmpeg | Headless Chrome + FFmpeg | Canvas + FFmpeg |
| 自带浏览器 | ✅(Chrome Headless Shell 装进 node_modules) | ✅(同) | ⚠️(需 Vite/browser) |
| 创作模型 | React + JSX | 纯 HTML + data-attributes | TS generator functions |
| **License** | **❌ 自定义(自动化=$0.01/render + $100/月)** | **✅ Apache 2.0** | **✅ MIT** |
| npm 可嵌入 | ✅ `@remotion/renderer` | ✅ `@hyperframes/engine` | ✅ `@revideo/renderer` |
| Agent 友好 | ⚠️(React 有学习成本) | ✅("Built for agents",19 个 Claude Code skills) | ⚠️ |
| 成熟度 | ★★★★★(成熟,Lambda 生产级) | ★★★(新,35.6k star 但主在 HeyGen 内部) | ★★(小社区) |

### 结论:HyperFrames 最适合 media-gen-mcp

理由:
1. **Apache 2.0**(Remotion 对自动化按渲染收费,对 MCP 这种按需渲染场景是致命问题)
2. **Agent 原生设计**(HTML 是 LLM 天然产出的格式,比 React/JSX 学习成本低)
3. **与 render_svg 的 Chrome 引擎同类**(我们已经有 puppeteer-core + Chrome 依赖,不引入新依赖类别)
4. **图片+视频双支持**(一个引擎覆盖 `render_svg` 升级 + 新增确定性视频)
5. **隐患**:较新,`snapshot` 多场景有已知 bug(#1047),需 spike 验证后再全面采用

## 二、本地 AI 图片生成可行性

### 进程内(Node.js 直接跑 SD)——❌ 不实用

| 路径 | 可行? | 原因 |
|---|---|---|
| Transformers.js (@xenova/transformers) | ❌ | 不支持扩散模型(仅 NLP/vision encoder) |
| onnxruntime-node + SD | ⚠️ 实验性 | 需要打补丁的 GPU native build;CPU 3-4 分钟/张 |
| dakenf/stable-diffusion-nodejs | ⚠️ PoC | 未发布稳定版;无 GPU 加速基准 |

### 性能现实(2025-2026 数据)

| 硬件 | 模型 | 每张耗时 |
|---|---|---|
| CPU(笔记本) | SD 1.5 @ 512² | **3-4 分钟** |
| 消费级 GPU | SD 1.5 @ 512² | ~5 秒 |
| 服务器 GPU(A100) | SDXL @ 1024² | 8-10 秒 |

**模型体积**:SD 1.5 ~2GB / SDXL ~6GB / FLUX.2 ~4GB。无法打包进 npm 包,首次下载多 GB。

### Sidecar 模式(调用本地 ComfyUI/Ollama)——✅ 可选补充

| 方案 | 状态 | MCP 先例 |
|---|---|---|
| **ComfyUI sidecar** | 成熟 | `alecc08/comfyui-mcp`(TS MCP server → ComfyUI REST API,已生产级) |
| **Ollama 图片生成** | 实验性(2025 末新增 Z-Image/FLUX.2,仅 macOS) | 无直接 MCP 先例 |

### 结论:本地 AI 作为可选 provider,不替代云端

- **进程内**:不实用(多 GB 模型 + GPU 依赖 + 分钟延迟,与 MCP 轻量按需本质冲突)
- **Sidecar**:ComfyUI/Ollama 自动探测(`localhost:8188` / `localhost:11434`),有就提供,没有就走 Agnes/Zhipu
- **内容过滤**:本地 SD/FLUX 无过滤(绕过 Agnes 武器词等问题),但延迟/硬件代价大
- **视频**:本地更差(SVD 14-25 帧 vs Agnes 241-441 帧,短且慢)

## 三、对 media-gen-mcp 架构的影响

### 不变的(保持现状)

| 层 | 为什么不改 |
|---|---|
| Agnes AI + 智谱(AI 图/视频) | 本地 AI 不实用(需 GPU + 多 GB 模型) |
| D2 + Graphviz(结构图) | 领域 DSL(自动布局),无代码到媒体的替代 |
| Vega-Lite(图表) | 图表语法,无替代 |
| MathJax(公式) | 专用引擎,无替代 |
| Satori + resvg(卡片) | 轻量快速,大部分卡片够用 |

### 可新增的

| 能力 | 方案 | 价值 |
|---|---|---|
| **确定性视频**(动效/动画/字幕视频) | HyperFrames(Apache 2.0,HTML→MP4) | 当前完全缺失:用户要"做个产品介绍视频"只能走 AI 或手写 ffmpeg |
| **高保真渲染升级** | render_svg 已有(Chrome 后端);HyperFrames 可统一图片+视频路径 | 可选收敛,非必需 |
| **本地 AI provider**(可选) | ComfyUI/Ollama sidecar 自动探测 | 给高级用户提供离线/无过滤选项 |

### 不建议的

| 方案 | 为什么不 |
|---|---|
| Remotion 替换 Satori | 按 render 收费 + React 依赖,Satori 更轻 |
| 进程内 SD/SVD | 多 GB 模型 + GPU + 分钟延迟,不适合 MCP |
| html2canvas + jsdom | 纯浏览器库,Node.js 不工作 |

## 四、推荐路线(优先级排序)

### P1(当前已有,不急改)
- Satori + resvg + Chrome render_svg:卡片/SVG/酷炫图已覆盖
- Agnes + 智谱:AI 写实图/视频已覆盖

### P2(潜在新能力——确定性视频)
- 调研 HyperFrames 是否可嵌入 MCP server 做 `render_video` 工具
- Spike:HyperFrames `snapshot`(单帧) + `render`(视频)是否可靠
- 如果可行 → 新增 `render_video`(HTML/动画 → MP4),填充"确定性视频"空白

### P3(高级用户选项——本地 AI sidecar)
- 自动探测 ComfyUI(`localhost:8188`),有就加 `local-comfyui` provider
- 用户无需改配置,有本地 GPU + ComfyUI 就自动可用
- 绕过 Agnes 内容过滤、完全离线
