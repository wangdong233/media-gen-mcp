## 一、v1.2 方案最终形态(澄清后固化,作实施基线)

经多轮澄清,识别集成方案定为:

| 维度 | 决策 |
|---|---|
| **运行时形态** | 所有识别 provider = **HTTP 客户端**(用户自配 baseUrl),与 Agnes/Zhipu 同构;**不内置 docker-compose**,README 给手册 |
| **tesseract** | **保留**,进程内 WASM,仅 extract_text 零配置兜底(数字/验证码/拉丁,中文弱);不参与表格/图表/描述 |
| **PaddleocrProvider** | HTTP 调用户自起的 paddleocr-mcp --http;全能主力(extract_text/table/chart + describe 基础) |
| **VLMProvider** | HTTP 调用户自起的 vLLM(Qwen2.5-VL-7B);describe_image VQA 增强 + analyze_chart fallback |
| **DashScope** | **去掉**(付费,违反纯免费立场) |
| **License** | Apache 全栈;避开 AGPL(DocLayout-YOLO)/GPL(Marker)/阈值(Surya)/署名(MinerU)/商用申请(Qwen 3B/72B) |
| **定位** | media-gen-mcp 从「生成 MCP」扩为「生成+识别 MCP」(用户已确认 R-DRIFT-02 演进迁移) |

**核心抽象**:能力袋 MediaProvider(TS 组合类型),image/video/vision 三能力组并列可选(采纳审查 finding-2)。

## 二、M0 改动范围(4 文件,纯重构)

### 1. `src/providers/types.ts`
- **新增 vision 类型**:Modality 扩 `"vision"` / VisionTask(4 值)/ ExtractTextHints(语义级:segmentation/languages BCP-47/digitOnly,**采纳 finding-1 去引擎词**)/ ExtractTableHints / AnalyzeChartHints / DescribeImageHints / VisionRequest / TextBlock / TableOut / ChartOut / VisionResult / VisionConstraints(**采纳 finding-4 去 tasks**)/ VisionProvider
- **新增 MediaProviderBase**:提取共享 meta(name/listModels/capabilities/health/tier/notifyUnavailable)
- **改 MediaProvider**:`interface` → `type = MediaProviderBase & Partial<ImageProvider> & Partial<VideoProvider> & Partial<VisionProvider>`(采纳 finding-2,消解 R-INT-03 god interface + R-CI-08 双声明)
- **ProviderCapabilities 加 vision 维度**:`vision: Record<VisionTask, boolean>`
- ImageProvider/VideoProvider 现有签名**不动**(向后兼容,组合后 name/listModels 收敛为必选,TS 无冲突)

### 2. `src/providers/registry.ts`
- 新增 `isVisionProvider(p)` / `asImageProvider(p)` / `asVideoProvider(p)` / `asVisionProvider(p)` 类型守卫(能力断言 + 友好报错,非原样转发,R-DEP-03 安全)
- `resolveProvider`:modality 联合扩含 vision;targetName 加 vision 分支(`config.defaultVisionProvider`);owns() 加 `p.listVisionModels?.()`。**第 4 参 task 不加**(task 过滤交 handler,R-ABS-01 安全)
- `capableOf`:加 vision 分支(`isVisionProvider(p) && p.visionTasks().includes(req?.task)`)
- `getFallbackProvider`:modality 扩;req 加 `task?: VisionTask` 字段(对称 mode/images/keyframes)
- `buildListModelsDetail`:每 provider 块加 `visionTasks/visionModels/visionConstraints`(条件输出)

### 3. `src/config.ts`
- 加 `defaultVisionProvider` 字段(回退 defaultProvider)

### 4. `src/index.ts`
- 抽 `isImageUri` 顶层常量(消除 line 370/451 两处重复正则,R-CI-01)
- 8 处 provider 方法 callsite 加 asXxxProvider 守卫(line 58/380/394/472/496/503/513/530/591)— 因 generateImage/videoConstraints/createVideo/getVideo/estimateGenerationSeconds 变可选,TS 编译要求窄化

## 三、组合类型可行性验证(关键不明确点)

**疑问**:`MediaProvider` 从 `interface` 改 `type = ... & Partial<...>`,现有 `class AgnesProvider implements MediaProvider` 还成立吗?

**验证**:TS 允许 `class implements <交叉类型 type alias>`(只要该 type 是 object type)。`MediaProviderBase & Partial<ImageProvider> & Partial<VideoProvider>` 是 object type,class 可 implements。Partial 的字段对 class 是可选实现的(不实现也满足,因 Partial)。

**结果**:
- AgnesProvider / ZhipuProvider 现有 `implements MediaProvider` **零改动**(它们已实现 image+video 全部方法 + 4 个 optional meta,满足组合类型)
- registry 字典 `Record<string, MediaProvider>` 类型不变
- 所有现有 callsite 只要加守卫窄化(或 `!` 断言,但守卫更安全)即编译通过

## 四、callsite 守卫清单(index.ts,8+ 处)

| 行 | 调用 | 守卫 |
|---|---|---|
| 58 | `getProvider(defaultVideoProvider).videoConstraints()` | asVideoProvider |
| 380 | `p.generateImage(...)` | asImageProvider(在 generate_image 入口) |
| 394 | `fb.generateImage(...)`(fallback) | asImageProvider(fb)(fb 已是 image provider,fallback 链保证) |
| 472 | `p.videoConstraints()` | asVideoProvider |
| 496 | `p.estimateGenerationSeconds(...)` | asVideoProvider |
| 503/530 | `p.createVideo(...)` / `fb.createVideo(...)` | asVideoProvider |
| 591 | `p.getVideo(...)` | asVideoProvider |

**守卫语义**:`asVideoProvider(p)` 若 p 无 video 能力,抛清晰错误「provider X 不支持 video」(非裸 `!` 断言 crash)。在 handler 入口 resolveProvider 之后守卫一次,后续用窄化变量。

**TS 自纠正**:任何遗漏的 callsite,videoConstraints 变可选后裸调编译失败 → M0 build 零错即证明守卫全覆盖。

## 五、不处理(留后续 / 不影响 M0)

1. **buildProviders 的 videoMinIntervalMs 对 vision provider 是 noise**(审查清单外):vision provider 不用此字段,但通用化下会得到默认值。**M0 不改**(零改动 buildProviders 是设计优势),M2 接 paddle 时若需可加 modality-aware 过滤或文档说明。不影响正确性。
2. **子接口瘦身**(ImageProvider/VideoProvider 去 name/listModels):审查 finding-2 的极致版。M0 **保留子接口现状**(最小破坏),仅 MediaProvider 改组合类型已消解 god interface。子接口瘦身非阻断,留作未来优化。
3. **provider 字典暂不加 vision provider key**:M0 无 provider 实现,M1 起加 tesseract。
