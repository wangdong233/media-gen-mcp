## 1. Surya (Surya OCR 2)
- **URL**:https://github.com/datalab-to/surya
- **verifiedStars**:21.1k stars / 1.5k forks / 129 watching(2026-07-18 实测 GitHub live 页面)。85 个 release,最新 release 日期 2026-07-15。Hugging Face datalab-to/surya-ocr-2 月下载 40.6 万。PyPI 当前版本 surya-ocr 0.14.x。
- **verifiedLicense**:双协议(2026-07 实测 GitHub README 与 MODEL_LICENSE):【代码】Apache-2.0(完全商业友好);【模型权重】modified AI Pubs Open RAIL-M license — 免费 for 研究/个人使用/融资或营收 <500 万美元的初创;超过阈值需购买商业授权(见 datalab.to pricing)。注: v1 历史上曾用 GPL-3.0(强 copyleft),v2 已改 Apache+OpenRAIL-M。
- **freeCommercialUse**:分两层:【代码 Apache 2.0】完全免费可商用,无传染性限制。【模型权重 modified AI Pubs Open RAIL-M】有条件——研究/个人/初创企业(融资或营收 <500 万美元)免费;超过 $5M 阈值的商业用途需向 Datalab 购买商用授权。注意历史: v1 曾为 GPL-3.0(强 copyleft),v2 已改为 Apache+OpenRAIL-M 双层。
- **whatItDoes**:一个 650M 参数的单一 VLM 统一处理:OCR(90+ 语言)、版面分析(table/image/header/section/equation/caption/code/form 等 18 类标签)、阅读顺序(reading order)、表格识别(行列 + 跨格 + HTML)。整页 OCR 直接输出带 `<math>`/`<table>` 标签的 HTML,数学公式以 KaTeX 兼容 LaTeX 内联,无需独立 LaTeX OCR pass。附带独立的小型 EfficientViT 文本行检测模型和 OCR 错误检测模型。典型输入:ArXiv 论文、教科书、税表、公司文档、手写笔记、报纸;输入可为图像/PDF/文件夹。
- **howItWorks**:端到端 OCR-free VLM(非传统 Tesseract 式字符识别)。架构: 单个视觉语言模型(Qwen3-VL/Qwen3.5 风格,约 650M 参数),按 prompt 不同输出布局 JSON 或整页 HTML(数学包在 <math>..</math>、表格包在 <table>..</table>);layout/OCR/table_rec 三个任务共享同一 VLM。文本行检测(detection)是独立的 EfficientViT-based segformer(torch 模型,从零训练)。训练基于多样化的文档图像。推理通过 OpenAI 兼容 HTTP API:GPU 走 vllm(NVIDIA),CPU/Apple Silicon 走 llama.cpp(llama-server + Metal)。可选 JSON-schema 约束的布局解码(SURYA_GUIDED_LAYOUT=true)提升结构化输出可靠性。
- **benchmarks**:olmOCR-bench(标准文档解析基准): 83.3%, 在 <3B 参数模型中最佳 — 击败 GOT OCR (0.6B, 48.3%) 和 olmOCR anchored (8.3B, 77.4%), 接近 dots.mocr (3.0B, 83.9%); 大模型对比: Chandra OCR 2 (5.3B, 85.9%), Infinity-Parser2-Pro (35.1B, 87.6%)。olmOCR-bench default preset 分项(8413 tests): ArXiv 88.3 / Base 99.7 / Hdr-Ftr 92.5 / TinyTxt 93.7 / MultCol 82.4 / OldScan 41.8 / OldMath 81.4 / Tables 86.6。91 语言内部基准(覆盖文本/版面/表格/数学/阅读顺序): 总体 87.2%, 38 种语言 ≥90%, 76 种 ≥80%; 主要语言: 英 92.3 / 意 93.0 / 西 90.7 / 德 89.7 / 俄 88.8 / 法 89.3 / 韩 86.7 / 日 86.2 / 葡 86.1 / 中 82.5 / 印地 82.2 / 越 73.2 / 阿 72.7。吞吐: RTX 5090 + vllm = 5.35 页/秒 (12,884 tok/s, p95=42s); Apple Silicon + llama.cpp/Metal = 仅 0.108 页/秒 (~30W)。
- **specialization**:专精【文档图像】:ArXiv 论文、教科书、税务表单、公司文档、手写笔记、报纸、多栏文档。版面标签覆盖 Caption/Footnote/Equation/ListGroup/PageHeader/PageFooter/Picture/SectionHeader/Table/Text/Figure/Code/Form/TableOfContents/ChemicalBlock/Diagram/Bibliography/BlankPage 等 18 类,且带阅读顺序。表格识别支持行列 + 跨格合并(spanning cells) + 表头(需 predict_full 模式)。数学公式内联在 HTML 的 <math>..</math>(KaTeX 兼容 LaTeX),无需二次 LaTeX OCR。手写: 部分支持(README 列为示例之一,但非强项)。弱点: 中文仅 82.5%(非 CJK 最优);老扫描件 41.8%(最弱项);明确不做自然场景/照片文字。不能按图像类型切换专精——单一 VLM 统一处理所有类型,性能取决于训练分布。
- **integration**:官方仅 Python(pip install surya-ocr),Python 96% / HTML 3.6% / JS 0.4%。无官方 npm 包,无 ONNX,无 wasm。Node.js MCP server 三条路径:(1)【推荐】HTTP 调用——surya 推理后端是 OpenAI 兼容 API (vllm 或 llama-server),Node 直接 POST 到 SURYA_INFERENCE_URL=http://host:port/v1 即可,最干净;(2) Python 子进程——spawn surya_ocr/surya_layout 命令行,解析 results.json;(3) 远程 API——Datalab 托管平台(送 $5 额度)、Replicate 上的 cudanexus/ocr-surya、第三方 @doclo/providers-datalab npm SDK。Apple Silicon 上需先 brew install llama.cpp 取得 llama-server 二进制。
- **pros**:650M 小模型却达到 <3B 档最佳精度。单一 VLM 统一处理 OCR+版面+表格+阅读顺序+数学,管线简洁。输出原生 HTML(数学 KaTeX/LaTeX、表格 <table>),开箱即用。多语覆盖 91 种,38 种 ≥90%。CPU/Apple Silicon 可本地推理(无需 GPU)。代码 Apache 2.0 友好商用。项目活跃(85 个 release,最新 2026-07);Hugging Face 月下载 40 万+。$startup 阈值内的初创可免费商用权重。CLI + Python API + Streamlit GUI 三种用法齐备。
- **cons**:老扫描件极差 (OldScan 仅 41.8%)。中文 82.5% 非 CJK 最优(存在更强中文专精模型)。模型权重并非 Apache,modified Open RAIL-M 含 $5M 融资/营收门槛,超阈值商业部署需付费授权。需额外跑推理后端 (vllm 或 llama.cpp),比纯 Python 重。无官方 JS/npm 包,Node 接入需走 HTTP 或子进程。Apple Silicon 吞吐很低 (~0.1 页/秒)。明确不做自然场景/照片文字识别。表格 HTML 完整模式 (predict_full) 才处理跨列合并/表头。
- **verdict**:最适合: 文档解析管线需要 OCR + 版面 + 表格 + 阅读顺序 + 数学一体化输出 HTML 的场景,尤其资源受限(无 GPU / Apple Silicon / 边缘部署)、面向英文/欧洲语种、且文档来源清晰(ArXiv、教科书、报表、公司文档)。对初创(<$5M 营收/融资)可免费商用权重。避开: 自然场景/照片文字;极老扫描件(OldScan 41.8%);纯中文重投入(CJK 82.5% 非最优);Apple Silicon 高吞吐生产(0.1 页/秒);以及任何 $5M 阈值之上的商业部署未先谈授权。Node.js MCP 接入首选 HTTP 调用自托管 vllm/llama-server。

## 2. MinerU
- **URL**:https://github.com/opendatalab/MinerU
- **verifiedStars**:约 75k stars(2026-07-18 经 shields.io 实时 badge 验证显示 "75k";GitHub REST API 因共享 IP 触发速率限制未能取到精确整数,但 75k 量级已确认)。 forks/语言:主语言 Python。开源、极度活跃(3.4 版发布于 2026/06/18,提交持续)。
- **verifiedLicense**:MinerU Open Source License(Apache 2.0 + 附加条款)。自 3.1.0(2026/04/18)起从 AGPLv3 切换至此。附加条款:① 月活 MAU > 1 亿 或 月总收入 > 2000 万美元 需另购商业许可;② 提供在线服务必须在界面/文档显著标注使用了 MinerU;③ 违反则授权自动终止。已读 LICENSE.md 原文确认(中英文对照)。模型权重(HuggingFace opendatalab/MinerU2.5-2509-1.2B 等)同此许可。注意:部分社区评测提及老版本 pipeline 依赖 PyMuPDF(AGPL-3.0),3.0+ 已移除 doc-layout-yolo / mfd_yolov8(AGPL)与 layoutreader(CC-BY-NC-SA 4.0)模型。
- **freeCommercialUse**:免费且可商用(Apache 2.0 基础)。附加条款:(1) 若你及关联方月活用户 MAU > 1 亿 或 月总收入 > 2000 万美元,需另购商业许可;(2) 若基于 MinerU 向第三方提供在线服务,必须在产品界面或公开文档显著标注使用了 MinerU,否则许可自动终止。模型权重(HuggingFace opendatalab/MinerU2.5-*)与代码同许可。无 AGPL/研究专用限制,2026-04 起已彻底脱离 AGPL。
- **whatItDoes**:把 PDF / 图片 / DOCX / PPTX / XLSX / 网页 转成结构化的 Markdown 与 JSON(LLM/RAG/Agent 就绪)。自动去除页眉/页脚/页码/脚注以保证语义连贯,按人类阅读顺序输出单栏/多栏/复杂版面,保留标题/段落/列表层级,提取图片+图注、表格+表标题,公式自动转 LaTeX、表格自动转 HTML;自动识别扫描件/乱码 PDF 并启用 OCR(支持 109 种语言)。是 OpenDataLab/上海 AI 实验室在 InternLM 预训练过程中孵化、专攻科学文献符号转换的项目。
- **howItWorks**:三后端架构,可在 CLI 一键切换:① pipeline —— 传统模块化(版面检测 + OCR + 公式识别 + 表格识别),基于 PP-OCRv6/UniMERNet/表格结构模型,CPU 可跑,零幻觉,86.47 分;② vlm-engine —— MinerU2.5-Pro-1.2B 视觉语言模型(基于 Qwen2.5-VL 架构,1.2B 参数),OCR-free 端到端 VLM,采用"解耦两阶段"(decoupled coarse-to-fine)策略:Stage I 在下采样图上做版面分析,Stage II 按版面从原图裁剪原生分辨率局部区域做内容识别,规避 O(N²) 视觉 token 爆炸,降低幻觉,vLLM/LMdeploy/mlx 推理,95.39 分;③ hybrid-engine —— VLM + 原生文本抽取结合,高精度低幻觉,95.30 分。后端可按设备/场景切换,还有 effort=medium/high 强度档位在精度与速度间权衡。
- **benchmarks**:OmniDocBench v1.6(最新生产版 MinerU2.5-Pro-2605-1.2B, End-to-End Overall 分):vlm-engine high=95.39、medium=95.26;hybrid-engine=95.30;pipeline=86.47。MinerU2.5 论文(2509.22186, 1.2B):OmniDocBench Overall 90.67(超 dots.ocr 88.41、Gemini-2.5 Pro 88.03、Qwen2.5-VL-72B、GPT-4o);公式 CDM 88.46(dots.ocr 86.78,Gemini 85.71);表格 TEDS 88.22 / TEDS-S 92.38;文本 Edit-Dist 0.047(最低);阅读顺序 Edit-Dist 0.044。Ocean-OCR:中文 F1 0.965、英文 F1 0.945。olmOCR-bench 总分 75.2(超 dots.ocr 73.6),arXiv Math 76.6(超 Qwen2.5-VL-72B 72.2)。速度:端到端 2.12 pages/s、2337 tokens/s(是 MonkeyOCR-Pro-3B 的 4×、dots.ocr 的 7×)。3.4 版 PP-OCRv6 在 OmniDocBench v1.6 上 OCR 精度再提约 11%、速度提约 100%。
- **specialization**:专精【复杂版面文档整体解析】,非纯数字/单图像分类模型。强项:科学/学术论文(含 LaTeX 公式、表格)、多栏排版、跨页表格合并、脚注/页眉页脚清理、阅读顺序还原、中英 + 109 语言 OCR(中文表现尤其强,Ocean-OCR 中文 F1 0.965)。表格输出 HTML(非图片),公式输出 LaTeX,3.1.0+ VLM 还支持图表/插图分析。切换"专精"的方式不是按图像类型,而是按后端 + 强度:CPU/零幻觉选 pipeline,高精度选 vlm-engine high,日常均衡选 hybrid medium。无独立的"纯手写体/纯数字仪表/票据"专精模式(靠通用 OCR 兜底)。
- **integration**:官方 Python 为主,同时有 Go SDK、TypeScript SDK(官方 npm 包 mineru-open-sdk,在 MinerU-Ecosystem 仓库);REST API(FastAPI:同步 /file_parse + 异步 /tasks);CLI(mineru / mineru-api / mineru-router / mineru-gradio);Docker;官方 MCP Server(接 Cursor / Claude Desktop / Windsurf / Cherry Studio);LangChain / LlamaIndex / RAGFlow / Dify / FastGPT 原生集成。Node.js MCP server 接入路径:推荐调用远程 mineru-api(REST / OpenAI 兼容)或直接用官方 MCP server —— 无 ONNX/wasm,纯 JS 不可行(模型数 GB、依赖 PyTorch/vLLM);亦可 Python 子进程。支持 10+ 国产 AI 芯片(昇腾/寒武纪/燧原/摩尔线程/昆仑芯/海光/壁仞 等)。
- **pros**:开源文档解析类目 SOTA(OmniDocBench 90.67/95.4 系列,超 Gemini-2.5 Pro、GPT-4o、Qwen2.5-VL-72B、dots.ocr、MonkeyOCR);三后端灵活切换(CPU 零幻觉 pipeline / 1.2B VLM 高精度 / hybrid 折中);全格式(PDF/图/DOCX/PPTX/XLSX);表格→HTML、公式→LaTeX 结构化输出;中英 + 109 语言 OCR;多栏/跨页表格/扫描件/手写均处理;mineru-router 多 GPU 负载均衡,生产级可扩展;许可证 Apache-based,商用友好;社区极活跃(75k stars);3.0+ 已清除 AGPL 模型依赖。
- **cons**:体积重(Python + PyTorch + vLLM,模型数 GB);VLM/hybrid 后端需 8GB+ VRAM;无 ONNX/wasm/纯 JS,无法在浏览器或轻量 Node 进程内推理;安装依赖(ray/torch/vllm)兼容性常踩坑,Windows 对 Python 3.13 不支持;无专用"手写体"或"纯数字仪表读数"专精模型;在线服务有强制署名义务(对白标 SaaS 不友好);历史上依赖过 PyMuPDF(AGPL)和 doc-layout-yolo/mfd_yolov8(AGPL),3.0+ 已清除 AGPL 模型但部分社区评测仍提醒注意依赖链。
- **verdict**:最适合:复杂文档(尤其学术论文、科研报告、教材、多栏 CJK、含公式/表格)高精度解析为 Markdown/JSON,喂给 RAG / LLM / Agent 工作流;以及批量多 GPU 生产部署。Node.js MCP 接入推荐走远程 mineru-api REST 调用(纯 JS/wasm 不可行)。不适合:轻量端侧/浏览器/纯 JS 场景、专用手写体或票据数字识别、对署名义务敏感的白标 SaaS。URL 有效,项目活跃维护,当前版本 3.4(2026-06),非废弃。

## 3. PaddleOCR PP-StructureV3
- **URL**:https://github.com/PaddlePaddle/PaddleOCR
- **verifiedStars**:GitHub API 在沙箱被拦(返回 None),数据来自 web 检索。PaddleOCR 3.0 技术报告(arXiv:2507.05595,2025-07)记载 "more than 50,000 stars on GitHub as of June 2025"。2026-03 多家媒体(Sciencenet/OSChina/Pandaily)报道 star 数超 73.3k,反超 Google Tesseract OCR(73.2k)成为 GitHub star 数最多的 OCR 项目;2026-06 百度百科记载超 82.2k。仓库当前自述 "70k+ Stars"。实测口径:约 82,000+(2026-06),全球 OCR 类目第一。
- **verifiedLicense**:Apache License 2.0(已读 LICENSE 全文:"Copyright (c) 2016 PaddlePaddle Authors. All Rights Reserved. Licensed under the Apache License, Version 2.0")。arXiv 技术报告(2507.05595)摘要原文再次确认 "Apache-licensed open-source toolkit"。注意:issue #11634 提及个别第三方 bundle 组件可能携带更严 license(如 AGPL-3.0),PaddlePaddle 自研代码与 PP-StructureV3 权重本身均 Apache 2.0,但生产商用前建议扫一遍依赖树。
- **freeCommercialUse**:免费且可商用。代码 + 模型权重均 Apache 2.0(技术报告明确 "Apache-licensed open-source toolkit",HuggingFace PP-StructureV3 集合同样 Apache)。无 AGPL/研究专用/商业授权限制。唯一注意点:issue #11634 提及个别第三方 bundle 组件可能携带更严 license——生产商用前建议扫一遍依赖清单,但 PaddlePaddle 官方出品的 PP-StructureV3 全部模型本身无商用限制。
- **whatItDoes**:把任意 PDF 或文档图像解析为结构化数据(JSON + Markdown),LLM/RAG 就绪。一条流水线同时完成:版面区域划分(文本/标题/图片/表格/图表/印章/公式)、文字 OCR、表格结构识别(输出 HTML)、公式识别(输出 LaTeX)、图表解析(转表格)、印章文字识别、阅读顺序恢复、多篇文章归属(一页报纸多篇报道)。是 PaddleOCR 3.0 三大旗舰方案之一(另两个是 PP-OCRv5 纯文字识别、PP-ChatOCRv4 关键信息抽取)。解决的核心问题:复杂文档→可被大模型消费的结构化数据。
- **howItWorks**:非 OCR-free VLM,非端到端——是显式与 VLM 对比的多模型流水线,每个模型 <100M 参数(论文原话 "fewer than 100 million parameters achieve competitive accuracy...rivaling billion-parameter VLMs")。PP-StructureV3 五模块:(1) Preprocessing——PP-LCNet 方向分类 + UVDoc 去畸变;(2) OCR——PP-OCRv5(关预处理)做全图文字检测+识别;(3) Layout Analysis——PP-DocLayout-plus(PP-DocLayout 增强版,专攻多栏报刊/多表格报告/试卷/手写/日文竖排) + 新提出的 region detection model 解决"一页多篇文章"的阅读顺序归属;(4) Document Items Recognition——按区域类型分派:PP-TableMagic(方向分类+框线分类+单元格检测+结构识别→HTML)、PP-FormulaNet_plus(公式→LaTeX,token 长度扩到 2560,支持多行+中文公式)、PP-Chart2Table(图表→表格)、PP-OCRv4_seal(印章);(5) Postprocessing——输出 JSON + Markdown + 阅读顺序恢复。PP-StructureV3 随 PaddleOCR v3.3.2 于 2025-11-13 发布。
- **benchmarks**:OmniDocBench (CVPR 2025), metric = Edit Distance ↓ lower is better. PP-StructureV3 SOTA among pipeline tools, competitive with billion-param VLMs: Overall EN 0.145 / ZH 0.206. Beats MinerU-0.9.3 (0.150/0.357), MinerU-1.3.11 (0.166/0.310), Marker-1.2.3 (0.336/0.556), Mathpix (0.191/0.365), Docling-2.14.0 (0.589/0.909), Pix2Text (0.32/0.528), Unstructured (0.586/0.716). Beats expert VLMs: GOT-OCR (0.287/0.411), Mistral OCR (0.268/0.439), Nougat (0.452/0.973), OLMOCR (0.326/0.469), SmolDocling-256M (0.493/0.816). Essentially ties Gemini-2.5-Pro (0.148/0.212) — within 0.003 EN. Speed: A100 0.64–1.12 s/page (mobile config 0.89, lightweight 0.61); V100 0.99–1.77 s/page; CPU-only Intel 8350C ~3.74 s/page (lightweight). vs MinerU 1.06 s/page A100 / 1.57 V100 — PP-StructureV3 is faster AND uses far lower VRAM (8–12 GB vs MinerU's 31–77 GB). Serving: 4×A100×1inst = 2.36 s latency @ 1.69 throughput; 4×A100×4inst = 3.87 s @ 4.05 throughput, 100% success. Weak spot: Chinese-formula Edit Dist 0.535 — VLMs (Gemini-2.5-Pro 0.439, Qwen2.5-VL-72B 0.434) edge it on complex CN formulas.

- **cons**:非端到端 VLM——多模型流水线,需要调参/开关模块,活动部件多。JS SDK 不含 PP-StructureV3 全流水线(浏览器仅 PP-OCRv5/v6 检测+识别)。复杂版面阅读顺序恢复偶有瑕疵(Reddit 实测反映)。本地推理依赖 PaddlePaddle 框架(重依赖);CPU 推理慢(默认配置约 4–8 s/页,必须切 lightweight 配置)。部分第三方组件疑似更严 license(issue #11634),商用须自检依赖。无原生 Node SDK。Serving 默认单请求串发(并发需高可用部署配置)。中文复杂公式弱于 Gemini-2.5-Pro / Qwen2.5-VL-72B。

## 4. PaddleOCR

- **howItWorks**:两套并行架构,按场景择一。【1】PP-OCRv6 = 传统 pipeline(非 VLM、非端到端):检测模型(PP-LCNetV3 改进)+ 方向分类 + 识别模型(CRNN 风格 CTC),轻量三档 tiny 1.5M / small 7.7M / medium 34.5M。【2】PaddleOCR-VL-1.6 = OCR-free VLM(端到端):NaViT 风格动态分辨率视觉编码器 + ERNIE-4.5-0.3B 语言模型,仅 0.9B 参数,直出 Markdown/JSON。【3】PP-StructureV3 = 版面 pipeline(版面分析 + 表格识别 + PP-FormulaNet 公式 + PP-Chart2Table 图表),与 VLM 不同的是提供细粒度坐标(表格单元格、文本框)。【4】推理后端可切:Paddle 静态图 / 动态图 / HuggingFace Transformers(3.5 起 20+ 模型支持),ONNX Runtime / OpenVINO / TensorRT 高性能加速。3.5 起核心与可选依赖分离。
- **benchmarks**:PP-OCRv6_medium:检测 Hmean 86.2%、识别精度 83.2%;较 PP-OCRv5_server 检测 +4.6% / 识别 +5.1%,官方称 34.5M 参数即超越 Qwen3-VL-235B 与 GPT-5.5。CPU 推理 5.2×(OpenVINO)、Apple M4 tiny 6.1×、A100 单卡 0.13s。PaddleOCR-VL-1.6 在 OmniDocBench v1.6 取得 96.33%(SOTA,文本/公式/表格三项均刷新),VL-1.5 为 94.5%。PP-OCRv5 多语种:英文模型较主模型 +11%,泰语 82.68%,希腊语 89.28%,部分语种较上代提升 >40%。

- **integration**:Python 为主(`pip install paddleocr`,3.5 起核心/可选依赖分离)。【JS】3.5.0(2026.04)官方发布 PaddleOCR.js 浏览器推理 SDK,基于 ONNX Runtime Web + WebGPU,跑 PP-OCRv5;社区 npm 包 `@paddleocr/paddleocr-js`、`ppu-paddle-ocr`(Node/Bun/Deno/浏览器全运行时)、`paddleocr.js`、`onnx-ocr-js`。【ONNX】官方支持模型导出 ONNX 与 ONNX Runtime 后端推理。【Node.js MCP 可行性】三条路:(A) 直接用官方 Python `paddleocr-mcp` 包,跑成独立 MCP server;(B) Node.js MCP 通过 child_process 调 Python 脚本(参考 dangvinh/mcp-ocr-server 架构模板);(C) 纯 JS 方案:ONNX Runtime Web/npm 包加载 PP-OCRv5 ONNX 权重推理(无需 Python)。另有 C++/C#/Java serving。
- **pros**:①精度 SOTA:PaddleOCR-VL-1.6 OmniDocBench 96.33%,PP-OCRv6 34.5M 即超 Qwen3-VL-235B/GPT-5.5;②全栈一统:文本/版面/表格/公式/图表/印章/古籍/手写/生僻字均有专门模块;③完整模型矩阵:1.5M→34.5M PP-OCR + 0.9B VL,覆盖移动端到服务器;④100+/109/111 语种,中英日 + 拉丁/西里尔/阿拉伯/天城文/泰/藏/孟加拉;⑤Apache 2.0 全商用免费;⑥CPU 5.2× 加速,边缘部署友好;⑦生态成熟(Dify/RAGFlow/Cherry Studio/Pathway 原生集成);⑧活跃维护,2026.06 刚发 3.7.0。
- **cons**:①深度绑 PaddlePaddle 框架,非 Python 用户安装体积大;②并行两套架构(pipeline vs VLM)易造成选型困惑;③Node.js 服务端无官方一等公民支持,JS 方案偏浏览器/社区;④官方 MCP 在 stdio 模式下多页 PDF 仅处理首页的已知 bug(Issue #16755);⑤PP-OCRv6 单一统一模型仅 50 语,完整 109-111 语种需切到 PaddleOCR-VL/PP-OCRv5 多语;⑥预训练模型训练数据第三方版权需自查。
- **verdict**:最适合:中文及多语种文档数字化 + RAG/Agent 数据入池;扫描件/PDF/截图/拍照文档的结构化解析;以及对成本敏感需 CPU/边缘部署的 OCR 场景。选型路径:移动端/边缘场景文字 → PP-OCRv6 tiny/small;高精度端到端文档解析(含表格/公式/印章/古籍)→ PaddleOCR-VL-1.6;需要表格单元格坐标 → PP-StructureV3;纯数学公式 → PP-FormulaNet。Node.js MCP 首选直接用官方 Python `paddleocr-mcp`,纯 JS 部署可用 PaddleOCR.js(目前仅 PP-OCRv5)。URL 有效,项目高度活跃(2026.06.11 发布 3.7.0),无废弃迹象。

## 5. RapidOCR

- **whatItDoes**:把百度 PaddleOCR 的 PP-OCRv4/v5/v6 训练模型统一转译为 ONNX/OpenVINO/Paddle/Torch/MNN/TensorRT 六套推理后端,做成一个纯推理、零训练依赖、开箱即用的离线 OCR 工具包。核心价值:卸掉沉重的 PaddlePaddle 框架,只装一个 onnxruntime 即可在 CPU/GPU/Intel/Nvidia/移动端跑起来,默认捆绑中英文模型(pip 装完直接用)。支持 90+ 语种(含中文繁简/日韩/拉丁/西里尔/阿拉伯/梵文/泰米尔等),用户也可基于 PaddleOCR 微调后转 ONNX 接入。
- **howItWorks**:经典三段式 OCR 流水线,不是 OCR-free VLM,不是端到端模型。流程:文本检测 Det(DBNet 系列骨干)→ 文本行方向分类 Cls(sliding window 朝向分类)→ 文本识别 Rec(CRNN+CTC,SVTR/PP-LCNetV3 等轻量骨干)。三个独立 ONNX 模型串联,前后处理(图像缩放/归一化/NMS/CTC 解码)在工程代码里完成。支持 6 个推理后端:ONNXRuntime(CPU/GPU,默认)、OpenVINO(Intel 加速)、PaddlePaddle、PyTorch、MNN(移动端)、TensorRT(NVIDIA GPU)。v3 版本起通过 default_model.yaml 统一配置,自动从魔搭社区(ModelScope)下载模型。模型分 mobile(轻量)/server(高精)/tiny/small/medium 多档可切换。
- **benchmarks**:无独立 benchmark,继承 PaddleOCR PP-OCRv5 数值:PP-OCRv5 多语种加权平均准确率 80.1%(PP-OCRv4 为 53.0%),参数量约 5M 级,移动端模型约 5-15MB。速度:CPU 端单页约 100ms-1s 级(与图像内容/CPU 型号相关);社区反馈 ONNX Runtime 后端相对原生 PaddleOCR 在文本检测阶段可能略慢(issue #514),但通过去除 PaddlePaddle 框架启动开销和内存占用换取部署便利性。注意:与 OCR-free VLM(如 GOT-OCR2.0、MinerU 2、PaddleOCR-VL)相比,精度在「印刷文字」场景接近,但在复杂版面/手写/公式上明显落后。
- **specialization**:专精【印刷体中文+英文+多语种文本】,默认 mobile/server 模型针对清晰印刷场景调优,中文是强项(PP-OCRv5 中文 CER 业界领先水平)。支持 PP-OCRv6 的 small/medium/tiny 三档和 90+ 语种(日韩/拉丁/西里尔/阿拉伯/梵文等)。**不专精的领域**:手写(无专门手写模型)、数学公式(无公式识别)、复杂表格(需配合 RapidTable)、版面分析(需配合 RapidLayout)。**无法在同一接口按图像类型动态切换专精模型**——Det/Cls/Rec 三段独立配置,需用户手动通过 params 字段切换 ocr_version+model_type+lang_type,本质是「换模型权重」而非「场景自适应」。若主要场景含手写/公式/表格,RapidOCR 单独不够用,需上 PP-StructureV3 或 Docling/MinerU。
- **integration**:官方绑定:Python(主仓库,pip install rapidocr + rapidocr-onnxruntime/rapidocr-openvino)、C++(RapidOcrOnnx 独立仓库)、C#(RapidOCRCSharp)、Java/JVM(RapidOcrOnnxJvm JNI);搜索线索提到的 Go 官方绑定未找到(无官方 Go 包,仅可能存在社区 cgo 封装)。**无官方 JS/npm/wasm 绑定**。Node.js MCP server 三条可行路径:(1) 调 Python 子进程(spawn rapidocr CLI 或 python -c,最稳但需装 Python+onnxruntime);(2) 用 onnxruntime-node 直接加载其发布的 .onnx 权重并自行实现前后处理(工作量大,但纯 JS);(3) 调远程 HTTP API(把 RapidOCR 包装成 FastAPI 服务)。社区有第三方 JS 包(如 areb0s/ocr-browser、dev.to 上的 PaddleOCR JS SDK)复用同款 ONNX 权重,可直接借鉴。Docling 已内置 RapidOCR 适配器可作集成参考。
- **pros**:1. 极致轻量(移动端检测+识别+方向分类三模型合计常小于 15MB);2. 完全离线、无 PaddlePaddle 重框架依赖,pip 一行装好;3. 6 个推理后端覆盖 CPU/GPU/Intel/Nvidia/移动端;4. 90+ 语种开箱即用(经 PP-OCRv5/v6),中文尤其强;5. Apache-2.0 全栈商用免费,模型权重也无限制;6. 多语言绑定(C++/C#/Java)便于嵌入式/桌面/服务端集成;7. 被 Docling、Umi-OCR、LangChain-Chatchat 等知名项目采用,生态成熟稳定。
- **cons**:1. 不是端到端模型,经典三段式流水线在长文本/弯曲文本上仍有上限;2. 不专精手写、数学公式、复杂表格(需另装 RapidTable/RapidLayout 同生态项目或换 Docling/MinerU);3. 无官方 JS/npm/wasm/Go 绑定,Node.js 生态需自建;4. 社区反馈 ONNX 后端检测阶段有时比原生 PaddleOCR 慢;5. 默认配置聚焦中英,小语种识别精度依赖 PP-OCRv5/v6 训练数据质量;6. 模型权重版权归百度,商用法律风险虽低但需关注 PaddleOCR 后续 license 变更。
- **verdict**:最适合:需要离线、轻量、跨平台部署印刷体中文/英文/多语种 OCR 的工程场景——典型如文档数字化、票据/身份证截图识别、PDF 文字提取、内网/边缘设备本地推理。Apache-2.0 + 5M 参数级轻量模型 + 6 个推理后端,是「去 PaddlePaddle 依赖」诉求下的工业首选,被 Docling/Umi-OCR/LangChain-Chatchat 等采用印证其工程价值。**不适合**:手写笔记、数学公式、复杂表格结构化(改选 PP-StructureV3 或 MinerU/Docling);纯 JS/浏览器/wasm 场景(无官方 JS 绑定,需用 onnxruntime-node 自封装或社区包);需要端到端 VLM 风格语义理解(改选 PaddleOCR-VL、GOT-OCR2.0)。对于 Node.js MCP server,推荐「Python 子进程」或「远程 HTTP API」两条路径,纯 JS 实现工作量较大。

## 7. Tesseract OCR
- **URL**:https://github.com/tesseract-ocr/tesseract
- **verifiedStars**:tesseract-ocr/tesseract ≈ 74.9k(GitStarClub 2026-06-21 快照;实测 GitHub REST API 本次被限流未能直接拉到 stargazers_count,但第三方追踪与 README 流量数据一致,数字可靠)。tesseract.js(naptha/tesseract.js)实测 38.5k stars / 2.4k forks / 481 watchers(2026 抓取页面直读)。
- **verifiedLicense**:Apache License 2.0(实测确认,来源:仓库 LICENSE 文件、README 明示、GitHub license badge)。依赖 Leptonica 为 BSD 2-clause。tesseract.js 同样 Apache 2.0。与搜索线索一致。
- **freeCommercialUse**:完全可以免费商用。核心代码 Apache 2.0;官方 traineddata(tessdata / tessdata_best / tessdata_fast)同样 Apache 2.0;依赖 Leptonica 为 BSD 2-clause。无 AGPL、无"仅研究"、无商业授权要求。tesseract.js 也是 Apache 2.0。模型权重与代码均无限制,适合闭源商业产品直接集成。
- **whatItDoes**:最老牌开源 OCR 引擎(C++ 库 libtesseract + CLI tesseract)。把印刷体文字图像转成可检索文本,支持 100+ 语言、UTF-8、35+ 脚本,输出 plain text / hOCR / PDF(含可搜索 invisible-text PDF) / TSV / ALTO / PAGE 多种格式。1985-1994 起源于 HP Lab Bristol 与 HP Greeley,2005 HP 开源,2006-2017 由 Google 维护,现 lead developer 为 Stefan Weil(Ray Smith 至 2017)、maintainer Zdenko Podobny。当前稳定版 5.x(5.0.0 发布于 2021-11-30)。依赖 Leptonica(BSD)做图像解码。解决"印刷体扫描件/截图/文档图像 → 结构化文本"这一经典问题。
- **howItWorks**:传统 OCR 管线,非 OCR-free VLM,非端到端模型。管线:Leptonica 解码图像 → 版面分析(Page Layout Analysis,13 种 PSM 分块模式)→ 文本行切分 → LSTM 神经网络逐行识别 → 输出。Tess 4 起的 LSTM 子系统源自 OCRopus 的 Python LSTM 实现、由 Ray Smith 用 C++ 重写,用 VGSL(Variable Graph Specification Language)描述网络结构(与 TensorFlow 兼容);LSTMRecognizer 把文本行图像转成 WERD_RES 字符序列。两种引擎可切换:--oem 1(LSTM,默认/推荐)、--oem 0(legacy 模式匹配,需 tessdata 含 legacy 模型)。LSTM 计算量约为 legacy 的 10 倍,但用 OpenMP 多核 + SSE/AVX/FMA SIMD 缓解。无 GPU 加速、无 attention/transformer、无视觉-语言对齐,完全是 CNN 之前的"LSTM 行识别器"思路(2016 前后技术)。
- **benchmarks**:官方 Benchmarks 页面(i7-10750H 6 核/16GB,单张英文图,秒/张):Tess 3.05 legacy=2.47s;Tess 4.1.3 AVX:tessdata_best=12.73s / tessdata_fast=2.95s / tessdata=4.09s;Tess 5.0.1:tessdata_best=6.20s / tessdata_fast=2.12s / tessdata=2.91s;Tess 5.0.1+OpenMP:tessdata_best=3.46s / tessdata_fast=1.96s。精度:MDPI Symmetry 2020 论文显示 Tess 4 LSTM 引擎原始准确率约 0.93、配合卷积预处理可达 0.96(legacy 引擎仅 0.38→0.63)。中文是公认短板:多篇学术论文(如 2017 GlobalSIP 端到端中文识别)报告深度学习方法(CTPN+CRNN/DenseNet)在中文上"显著优于 Tesseract";官方 chi_sim 落后于社区重训模型(gumblex/tessdata_chi)。2025 arXiv 论文用 CER 评估页级中文 OCR 时把 Tesseract 当 baseline。注意官方未发布与 PaddleOCR/EasyOCR 的直接 CER 对比数字,结论来自第三方。
- **specialization**:专精【高质量扫描/拍摄的印刷体英文+拉丁字母+数字】,这是它的主场。可按图像类型粗粒度切换专精:用 --psm(Page Segmentation Mode)切换版面假设(0=仅方向检测、1=自动+OSD、3=全自动、6=均匀块、11=稀疏文字、13=单行 raw line 等);用 -l 切换语言/脚本(100+ 种,含 chi_sim/chi_tra/jpn/kor 及竖排);用 tessdata_best(最高精度)/tessdata_fast(速度优先)/tessdata(标准)三套模型按场景取舍;可用 --oem 切换 LSTM/legacy 引擎。明确不擅长:手写体(基本不支持)、数学公式(不支持)、图表/图表轴标(无理解,仅抠零散文字)、复杂表格结构(只给文本和坐标,无表格语义)、中文(公认短板,需社区重训模型如 gumblex/tessdata_chi 补救)。无法像 OCR-free VLM 那样端到端理解版面语义。
- **integration**:多语言绑定齐全。Python:pytesseract(调用本地 CLI)最流行。Node.js/Web:tesseract.js(naptha/tesseract.js,38.5k 星,Apache 2.0,纯 JS via WASM,v7.0.0/2025-12,v7 需 Node 16+),浏览器(script tag/webpack/ESM)与 Node 均原生支持,语言数据 @tesseract.js-data/* 独立安装,v5 中文模型体积减 73%;另有 robertknight/tesseract-wasm。C/C++:libtesseract 官方 API。其他:Java(Tess4J)、Go、Rust、Ruby 等社区绑定。Node.js MCP server 三条可行路径:(1)纯 JS —— 直接 npm install tesseract.js,在 MCP tool 内 createWorker + worker.recognize,零子进程零外部依赖,最干净;(2)调 Python 子进程 pytesseract;(3)调本地 tesseract CLI。推荐路径 1,tesseract.js 即为 Node MCP 的首选封装层。
- **pros**:40 年历史的最成熟开源 OCR,生态无可匹敌(Python/Node/Java/Go/Rust 全绑定);Apache 2.0 完全可商用、模型权重无限制;100+ 语言开箱即用;tessdata_best/fast/best 三档模型可按精度/速度取舍;输出格式丰富(text/hOCR/PDF/TSV/ALTO/PAGE 含坐标);纯 CPU 运行无需 GPU;100% 离线,适合隐私/边缘场景;CJK 竖排自动检测;tesseract.js 让浏览器/Node 零原生依赖集成成为可能;文档完善、issue tracker 活跃。
- **cons**:中文是公认短板(官方模型落后于 PaddleOCR 等);不支持手写体;不理解公式/图表/复杂表格(仅提取文字,不做结构化);对图像质量敏感,低质图常需预处理;LSTM 引擎 CPU 约为 legacy 的 10 倍(虽有 AVX/OpenMP 缓解);非端到端 VLM,架构偏旧;无内置 GUI;中文文档场景常需社区重训模型;v5 后 API/ABI 与 v4 不兼容。
- **verdict**:最适合:印刷体英文/拉丁字母/数字、扫描质量高的文档数字化(发票/合同/书籍/票据/截图文字),以及需要 100% 离线、成熟稳定、可商用的场景;Node.js MCP server 用 tesseract.js 封装是干净路径(纯 JS/WASM,无子进程)。不适合:中文为主、手写体、数学公式、图表/复杂表格语义理解、低质量图像 —— 这些场景应选 PaddleOCR(中文强)、或 OCR-free VLM(如 GOT-OCR、MinerU,版面/公式/表格)、或云 API。中文弱项是硬伤,但拉丁文印刷体场景仍是业界最稳的开源默认选项。URL 有效,项目活跃(当前 stable 5.x,2026 开发计划在 issue #4498 讨论)。

## 8. EasyOCR
- **URL**:https://github.com/JaidedAI/EasyOCR
- **verifiedStars**:约 29.6k–29.8k(GitHub API 速率受限无法直查;star-history/GitStarClub 在 2026-06-21 实测约 29.6k,GitHub Topics 页面显示 29.8k;搜索线索说的"30k+"基本准确但尚未破 30k)。Fork 数 ~3.3k+。Open issues ~700+(有大量过期自动关闭)。最新 release v1.7.2 发布于 2024-09-24,近 2 年无新版本,处于低活跃维护状态。

- **freeCommercialUse**:完全免费且可商用。代码与模型权重均遵循 Apache License 2.0(已直接读取 LICENSE 文件全文核实),允许商业使用、修改、再分发与闭源衍生,无 AGPL/研究专用/需授权等限制。CRAFT 预训练模型与 CRNN 训练管线来自 clovaai,沿用其公开权重(用于科研/商业普遍未受限)。Jaided AI 另售企业版定制服务(实现/微调/部署),但开源版本身无任何商用门槛。
- **whatItDoes**:一个开箱即用的多语言 OCR 库,用 3 行 Python 把图像里的文字读成 [(bbox, text, confidence), ...] 列表:既能识别英文/拉丁文,也能识别中、日、韩、阿拉伯、天城文、西里尔等 80+ 种语言。同时支持自然场景文字(招牌/路牌/车牌)和密集文档文字。要解决的是"非商业 API、自托管、一行命令多语言 OCR"的需求——把检测+识别打包成统一接口,无需自己写预处理或拼装多模型。
- **howItWorks**:经典两阶段(two-stage)OCR 管线,非 OCR-free VLM、非端到端。检测阶段用 CRAFT(Character Region Awareness for Text,2019)—基于热图回归字符区域与亲和力,产出文字框;识别阶段用 CRNN(Convolutional Recurrent Neural Network)—特征提取(ResNet 为主,可换 VGG/RCNN)+ 序列建模(LSTM)+ 解码(CTC 或 Attention,支持 beam search)。PyTorch 后端,权重按所选语言自动下载到 ~/.EasyOCR/model。官方 roadmap 提到未来要支持可插拔检测/识别(如 DB+Transformer),但未落地;手写支持列为"coming next"但未进入主线。GitHub issue #129 确认提供多种 CRNN 变体(TPS/None × VGG/RCNN/ResNet × CTC/Attention)。
- **benchmarks**:无项目方维护的精度基准,数据来自第三方测评:1) WACV 2025 学术对比(GitHub PDF)在困难多语言数据集上 case-sensitive word accuracy 0.2207,低于 Gemini-1.5-pro 的 0.3076;2) 噪声图像实测准确率约 29.0%(对比 PaddleOCR 仅 3.0%,反映其在嘈杂场景反而比 Paddle 更鲁棒,ai.gopubby 实测);3) 清晰扫描/印刷文档上接近零错误、置信度 96.8%(codesota 实测,Tesseract 出现 4 个错误);4) 综合 GigaGPU 横评:PaddleOCR 在弯曲文本上 88.7% vs Tesseract 52.1%,EasyOCR 居中;5) 速度:CPU 上 Tesseract 最快(约 3× EasyOCR,体积仅 ~10MB),EasyOCR 在 GPU 上很快但 CPU 较慢(因 PyTorch+CRNN 较重);6) ResearchGate 收据抽取对比结论:精度排序 PaddleOCR > EasyOCR > Tesseract,综合实用性 EasyOCR 最佳。无官方 CER/F1/秒每页数字。
- **specialization**:不可按图像类型切换专精模型(只有一套 CRAFT+CRNN,无法选"表格模型/数字模型/手写模型")。专精方向:自然场景文字(路牌、店招、车牌、商品包装等英文+多语种横向文字)和规整的密集印刷文档,在嘈杂/噪声图像上反而比 PaddleOCR 更鲁棒(实测 29% vs 3%)。短板:无版面分析(layout analysis)—表格、多栏、复杂版面无能为力(IntuitionLabs 明确指出);公式完全不支持;手写弱(英文手写尚可,中文手写差,且官方 roadmap 中手写仍属"未完成");中文识别(尤其繁体/手写/生僻字)落后于 PaddleOCR;纯数字可识别但并非专为 KDR/单字符优化。需要表格→看 PaddleOCR/PP-Structure;手写→TrOCR/专用模型;公式→Pix2Tex/LaTeX-OCR;中文→PaddleOCR。
- **integration**:官方仅有 Python 库(pip install easyocr)与 CLI(easyocr -l ch_sim en -f img.jpg),并提供 Dockerfile 与 HuggingFace Spaces Web Demo(Gradio)。无官方 JS/npm 包、无官方 ONNX、无 wasm。Node.js 集成的三条路径:1) 纯 JS:不可行——需自行把 PyTorch 权重导出为 ONNX 后用 onnxruntime-node/onnxruntime-web 加载,有社区 OnnxOcrJs/client-side-ocr 等基于 PaddleOCR 模型的替代方案;2) npm 包 node-easyocr 已封装,本质是 spawn Python 子进程调用 easyocr,Node MCP server 可直接用但要求宿主机装好 Python+PyTorch+easyocr;3) 远程 API:把 EasyOCR 包成 FastAPI/Flask 微服务,Node MCP 通过 HTTP 调用最干净。对 Node MCP 实战建议:走"远程 Python 微服务 + HTTP"或"node-easyocr 子进程"路线,纯 JS 路线不现实。

- **whatItDoes**:纯文档版面分析(DLA, Document Layout Analysis)模型:输入一张文档页面图像,输出页面中所有可读区域的边界框 + 类别标签。把一页切成 13 类区域(text / title / figure / figure_caption / table / table_caption / list / page-header / page-footer / footnote / equation / equation_number / reference)。它不识别文字内容、不读公式、不解析表格单元格——只回答"这块区域是什么、在哪"。正是 MinerU 和 PDF-Extract-Kit 的版面检测底座,负责在 PDF 解析管线第一步把页面切块,后续再交给 OCR / 公式识别 / 表格识别等下游模型。
- **howItWorks**:不是 OCR-free VLM,不是端到端文档理解模型,而是纯视觉单模态(unimodal)目标检测器。架构=Ultralytics YOLO-v10(经典 one-stage detector:backbone+neck+head,输出 anchor-free bbox+类别)。两项关键改造:(1)预训练数据——用 Mesh-candidate BestFit 算法把文档合成建模成"二维装箱问题",生成 30 万张多样合成文档 DocSynth-300K 做预训练,显著提升下游泛化;(2)模型结构——提出 Global-to-Local Controllable Receptive Module(全局到局部可控感受野模块),更好处理文档元素的多尺度变化(小 footnote vs 大 figure)。输入图像 → 输出每页 N 个 [bbox + 13 类之一]。管线是开放而非端到端:DocLayout-YOLO 只负责切块,文本识别/公式解析/表格结构识别需要外接模型(这正是 MinerU 的做法——拿 DocLayout-YOLO 切块,再分别送 OCR/formula/table 模型)。
- **benchmarks**:论文报告 mAP:DocBank 70.3% / D4LA 79.7% / DocLayNet 78.8%(均为 SOTA among 单模态视觉方法)。README 训练表(DocSynth300K 预训练后):D4LA imgsz1600 → AP50 82.4 / mAP 70.3;DocLayNet imgsz1120 → AP50 93.4 / mAP 79.7。速度:DocStructBench 上 ~85.5 FPS,约 3.2× 快于 LayoutLMv3 / Detectron2 多模态方法,在保持 80+ FPS 的同时显著缩小与多模态方法的精度差距。OmniDocBench(CVPR 2025,更严苛的多源真实文档集)上 mAP 约 48.71%——说明跨域鲁棒性弱于同源评测。重要坑:Issue #74 实测在 A100 上远低于论文 85.5 FPS,基准条件高度依赖 imgsz/批处理/硬件,需自行复测。
- **specialization**:专精于"版面分块(layout block detection)"——把页面切成 13 类语义区域:text / title / figure / figure_caption / table / table_caption / list / page-header / page-footer / footnote / equation / equation_number / reference。它不识别任何文字内容(不读数字、不读中文、不读手写、不读公式),只给区域类型 + 边界框。因此它对"哪类图像专精"这个问题是反过来的:它专精于"任何版式文档的几何切块",不分中英文、不分图表/表格/公式(这些都能定位,但内容不解析)。不能按图像类型切换专精——单一模型,一套 13 类标签打天下。要真正读公式/表格/纯数字,需后续接专门的公式识别(如 UniMERNet)、表格识别(如 RapidTable)、OCR(PaddleOCR)——MinerU 就是这么组装的。
- **integration**:Python 官方原生:`pip install doclayout-yolo`(或精简推理包 `doclayout-yolo-slim`),SDK 即 `from doclayout_yolo import YOLOv10; model.predict(...)`,也可 `YOLOv10.from_pretrained("juliozhao/DocLayout-YOLO-DocStructBench")` 直连 HF。无官方 JS/npm 包。ONNX 路线可行:社区已有 ONNX 导出(如 HF `wybxc/DocLayout-YOLO-DocStructBench-onnx`、`darknoah99/...-onnx`),配 `onnxruntime-node`(Node.js 原生绑定)或 `onnxruntime-web`(wasm/浏览器)即可,但要自己写预处理(letterbox/resize)+ 后处理(NMS、bbox 解码),工作量中等。Node.js MCP server 三条路:(a)最稳=调 Python 子进程(官方 SDK 直接用);(b)纯 JS=onnxruntime-node + 社区 ONNX 权重(无官方 npm 封装,需移植 inference.py 逻辑);(c)调远程 API(把 MinerU/PDF-Extract-Kit 包成 HTTP 服务)。无 wasm 官方版。
- **pros**:纯视觉版面分块的速度+精度 SOTA,~85 FPS 级吞吐适合大规模批量。经 MinerU(被广泛部署的 PDF 解析器)实战验证为版面底座,稳定性强。pip 一行安装,SDK 极简,HuggingFace from_pretrained 即用。DocSynth-300K 多样化预训练 → 对新文档类型有不错的零样本鲁棒性。支持 CPU/GPU/ONNX 多后端,可批量推理。13 类粒度细(区分 caption / footnote / equation_number),对下游解析管线友好。
- **cons**:AGPL-3.0 网络传染(因衍生自 Ultralytics YOLO)——对闭源 SaaS / 不开源产品是硬性阻断,HuggingFace 上的 Apache-2.0 标签是误导(以 GitHub AGPL-3.0 为准)。只做版面分块,不做 OCR/公式解析/表格结构化/手写识别,要端到端产物必须配下游模型(MinerU 已替你配好)。单一专精,不能按图像类型切换模式。FPS 数字难复现(Issue #74)。仓库自 2025-04 后基本停更,数据加载器存在内存泄漏(README 自认),YOLOv11 之前的批量推理需手动改代码。无官方 JS/npm 绑定。
- **verdict**:最适合:Python 技术栈、需要把 PDF/文档页面切成语义区域、且能接受 AGPL-3.0 开源约束的项目。作为 MinerU/PDF-Extract-Kit 的版面底座已是事实标准,自建文档解析管线的首选 layout 前端。不适合:(a)需要端到端一次出文本/公式/表格内容的场景——它只切块,要配 OCR+公式+表格模型;(b)闭源商业 SaaS——AGPL-3.0 会强制开源整个衍生栈,要么买 Ultralytics 商业授权,要么换 LayoutLMv3(更慢但可换许可)或 PP-Structure(Apache-2.0);(c)需要纯 JS/Node.js MCP 直接集成——无官方 npm 封装,要么调 Python 子进程(推荐),要么用社区 ONNX+onnxruntime-node 自写前后处理。验证备注:项目活跃度偏低(2025-04 后基本停更),但被 MinerU 持续背书,模型本身稳定可用。

- **verifiedStars**:1,159 stars / 130 forks(GitHub REST API 实测;HF 127 likes / 281 downloads)。仓库活跃,最近 push 2026-07-13,最新 release v0.0.35(2026-05-06);搜索线索里提到的 v0.0.19 已是一年前旧版,当前版本更高。

- **freeCommercialUse**:是,免费且可商用。仓库 LICENSE 为完整 Apache-2.0(201 行),Hugging Face 模型卡显式声明 license: apache-2.0 —— 代码与模型权重同一许可证,无 AGPL/非商业/研究专用/商业授权限制。仅需遵守 Apache-2.0 标准条件:保留版权与 NOTICE、注明修改、专利反诉失效条款。底层依赖(Tesseract / ocrmypdf / Poppler)同样为 Apache/BSD 宽松许可。注:VGT 原出自阿里巴巴 Advanced Literate Machinery,亦以 Apache-2.0 发布。
- **whatItDoes**:Docker 化的 PDF 版面分析微服务。输入 PDF 页面 → 输出每个区域的 bbox(left/top/width/height)+ 页码 + 文本 + 类型标签 + 阅读顺序。识别 11 类:Caption / Footnote / Formula / List item / Page footer / Page header / Picture / Section header / Table / Text / Title。除核心版面分析外,还内置 OCR(Tesseract + ocrmypdf,150+ 语言)、TOC 提取、PDF→Markdown/HTML 转换、可视化叠加 PDF、以及通过 Ollama 的多语言翻译。提供 REST API(:5060,10+ 端点)+ Gradio Web UI(:7860)。解决的核心问题:把一页复杂 PDF 切成有语义标签的区域块,供下游分别 OCR/抽取/检索(RAG 入库)使用。
- **howItWorks**:非 OCR-free VLM,是『检测-分类版面 + 后处理』的传统两阶段混合管线。版面模型二选一(请求时用 fast 参数切换):(1) VGT(Vision Grid Transformer,阿里巴巴 Advanced Literate Machinery 出品)——视觉 Transformer,整页成像理解空间关系,DocLayNet 80k+ 页训练,需 5GB+ VRAM;(2) LightGBM——双模型集成(Token Type 分类器 + Segmentation 边界),特征来自 Poppler 的 PDF→XML,CPU only。文字层:数字 PDF 用 Poppler 抽嵌入文本;扫描 PDF 走 Tesseract/ocrmypdf。公式走 LaTeX-OCR→LaTeX,表格走 RapidTable→HTML。阅读顺序:Poppler token 序列 + 类型优先级(Header 先 / 正文 / Footnote 末)。翻译走 Ollama(gpt-oss 默认)。整体是『先切块再分别识别』架构。
- **benchmarks**:VGT 在 PubLayNet 上 Overall F1=0.962(分项:Text 0.950 / Title 0.939 / List 0.968 / Table 0.981 / Figure 0.971,接近 SOTA)。速度(15 页学术 PDF,官方数据):LightGBM @ CPU i7-8700 = 0.42 秒/页(最快);VGT @ GPU GTX 1070 = 1.75 秒/页;VGT @ CPU i7-8700 = 13.5 秒/页(CPU 回退,偏慢)。对比同类:VGT 精度与 DocLayNet/DiT 梯队相当,LightGBM 在 CPU-only 批处理场景速度优于多数视觉模型。
- **specialization**:专精【版面分块/版面分析】,不是通用图识字/读图 VLM。11 类标签:Caption / Footnote / Formula / List item / Page footer / Page header / Picture / Section header / Table / Text / Title。训练集 DocLayNet 以英文为主,覆盖学术/技术/金融/法律/科学/手册类西式文档,故英文/西式版面最强。中文:布局模型本身非中文专精,需依赖 Tesseract 装 chi-sim/chi-tra(容器内 apt 装)做 OCR。手写:不专精(Tesseract 偏印刷体)。公式:作为类别检测 + LaTeX-OCR 转 LaTeX。表格:作为类别检测 + RapidTable 转 HTML。纯数字/图表识别:非其专长。可切换专精:同一服务内可用 fast=true 切到 LightGBM(快但无视觉理解),用 types 过滤类别,用 parse_tables_and_math 开启表/公式增强——但 11 类标签固定,API 不支持即插外部专精模型。
- **integration**:源码 100% Python(Python 3.10+ / FastAPI 后端 / Gradio 前端),无官方 JS/npm 包,无 wasm。交付物是 Docker 镜像(huridocs/pdf-document-layout-analysis,Docker Hub/GHCR,~12GB)。Node.js MCP 接入方案:(1) 纯 JS —— 不可行;(2) spawn Python 子进程 —— 技术可行但很重(12GB 镜像 + 模型 + 依赖);(3) **调远程 HTTP API —— 最佳**:启动 Docker 容器,Node 端仅做多部分表单 POST 到 http://localhost:5060 并解析 JSON,REST API 设计就是为此而建。无 ONNX/wasm 官方捆绑(仓库内 RapidTable 内部可能用 ONNX,但未对外暴露)。
- **pros**:Apache-2.0 全开(代码+权重)可商用;VGT 与 LightGBM 双模型按需切换精度/速度;Clean Architecture 工程质量高;Docker turnkey + Gradio UI 零门槛上手;一个服务通吃版面/OCR/TOC/Markdown-HTML/翻译;VGT F1 0.962 精度强;维护活跃(2026-07-13 仍有 commit,v0.0.35);150+ OCR 语言;返回 bbox+类型+阅读顺序+文本,正是『先切块再识别』中间层理想形态。
- **cons**:镜像重(~12GB,模型依赖大);VGT 需 5GB+ VRAM,CPU 回退慢(13.5 秒/页)。不是端到端 OCR-free VLM,数字 PDF 靠 Poppler 嵌入文字、扫描 PDF 必须单独跑 OCR 才有正文。训练集 DocLayNet 以英文/西式学术报告财报为主,中文/手写/非西式版面较弱。无官方 JS/SDK,只能 HTTP 调用。11 类标签固定,API 不支持即插自定义类别。LightGBM fast 模式无视觉理解。翻译质量取决于所选 Ollama 模型。
- **verdict**:最适合【需要稳定 PDF 版面切块的两阶段管线的中间层】场景:PDF→Markdown/HTML 做 RAG 索引、批量处理英文学术/技术/财报/法律 PDF、要把图/表/公式从正文分离后路由给专用识别器。对用户的图像识别需求:它是『版面分块专家』而非『纯数字/图表/中文/手写/公式专家』——非常适合做预处理切块,但 CJK/手写/图表仍需下游专精模型。Node.js 接入推荐方式:运行 Docker 容器,Node MCP server 作为薄 HTTP 客户端 POST 到 :5060。URL 已验证有效(实测非线索所述的 v0.0.19,当前 v0.0.35,仓库活跃)。

## 15. Qwen2.5-VL
- **URL**:https://github.com/QwenLM/Qwen2.5-VL
- **verifiedStars**:实测 12k stars / 912 forks / 890 open issues(QwenLM/Qwen2.5-VL 主仓库)。72B-Instruct HF 模型 639 likes / 月下载约 39.5 万;7B-Instruct HF 月下载约 100 万(系列最受欢迎变体)、1635 likes;3B 月下载 655 万(受益于轻量)。arXiv 技术报告 2502.13923 被引 7958+ 次。

- **whatItDoes**:阿里通义千问团队 2025.01.28 发布的旗舰开源多模态视觉语言模型(VLM),提供 3B/7B/32B/72B 四个尺寸的 base + Instruct 变体。一台模型同时解决:(1) 通用图像识别(花/鸟/车/名人/商品/IP 等超大规模类别);(2) OCR-free 文档/表格/图表/复杂版面/手写/化学式/乐谱解析,自创 QwenVL HTML 格式可把扫描件(发票/表单/网页/手机截图)直接转结构化 HTML;(3) 精确目标定位(bbox + point,绝对像素坐标 + JSON 输出);(4) 1 小时+长视频理解 + 秒级事件时间定位;(5) Visual Agent —— 直接当手机/电脑 GUI 智能体,点击/输入/操作应用。它是国内开源 VLM 综合能力最强的 workhorse 之一。
- **howItWorks**:端到端 OCR-free VLM(无外部 OCR 引擎,VLM 直接读字)。架构:原生动态分辨率 ViT(从零训练,经 CLIP → 视觉-语言对齐 → 端到端三阶段)+ Qwen2.5 LLM 解码器。ViT 仅 4 层 Full Attention,其余为 Window Attention(最大窗口 8×8,小于 8×8 区域不补边、保留原始尺度),并采用 RMSNorm + SwiGLU 与 LLM 对齐。位置编码用【Multimodal RoPE (MRoPE)】,把位置拆成时间/高度/宽度三维;视频侧引入【动态 FPS 采样 + 绝对时间编码】,MRoPE id 直接对齐真实时间间隔,从而支持小时级长视频 + 秒级事件定位。坐标不归一化、直接用绝对像素值输出。YaRN 可扩展到 64k 上下文(但官方提醒会损害时空定位精度)。
- **benchmarks**:Qwen2.5-VL-72B 官方评测 vs GPT-4o / Claude3.5 Sonnet(全部实测于 HF 模型卡):OCR/文档/图表这一档全面碾压——【OCRBench v1: 885】(GPT-4o 736,Claude3.5 788,InternVL2.5-78B 854;注意搜索线索说的"854+"其实是 InternVL 分,Qwen2.5-VL 真实分是 885);【OCRBench-V2 en/zh: 61.5/63.7】(GPT-4o 46.5/32.3,Claude 45.2/39.6,领先一倍多);【CC-OCR: 79.8】(GPT-4o 66.6);【DocVQA: 96.4】(GPT-4o 91.1);【InfoVQA: 87.3】(GPT-4o 80.7);【ChartQA: 89.5】(GPT-4o 86.7);【MathVista: 74.8】(GPT-4o 63.8);【MMMU: 70.2】(GPT-4o 70.3,基本打平);【MathVision: 38.1】(Claude3.5 38.3)。视频:【VideoMME w/o sub: 73.3】(GPT-4o 71.9);【LVBench: 47.3】(GPT-4o 30.8,大幅领先);【MMBench-Video: 2.02】(GPT-4o 1.63)。Agent/GUI:【ScreenSpot: 87.1】(GPT-4o 仅 18.1,碾压);【AITZ 移动端: 83.2】(GPT-4o 35.3);【AndroidWorld: 35%】(GPT-4o SoM 34.5%,Claude 27.9%);【OSWorld: 8.83】(Claude3.5 Sonnet 14.9 仍最强)。速度参考:vLLM + 单卡 H100,7B bf16 batch=1 约 130-200 tok/s;72B 需多卡;3B 边缘端可跑。
- **specialization**:这是一个统一的多面手 VLM,不是按图像类型切换的专精小模型——所有能力(OCR/图表/表格/版面/中文/手写/公式/视频/GUI)都由同一套权重端到端承担,通过【prompt + 分辨率设置】控制行为。强项排序:【OCR / 文档 / 表格 / 图表】顶级(OCRBench/DocVQA/InfoVQA/ChartQA 均开源 SOTA,且原生支持中文+多语言+竖排+手写+化学式+乐谱);【复杂版面】提供独有 QwenVL HTML 格式,把扫描件(发票/表单/网页/杂志/手机截图)解析为带 bbox 的结构化 HTML;【长视频 + 时间定位】开源少有;【GUI Agent(手机/电脑)】开源领先;【纯数字识别】强但不专精(纯数字场景 PaddleOCR/PaliGemma 等更轻更快);【手写】支持但不如专用 HTR 模型精细化。无法"切换专精",靠 prompt 工程(如 "QwenVL HTML"、"Extract following info...output JSON")和 max_pixels/min_pixels 调分辨率适配不同任务。
- **integration**:Python 一等公民:transformers>=4.51.3、qwen-vl-utils[decord/torchcodec]、vLLM>0.7.2(官方推荐部署,带 OpenAI 兼容 API)、sglang、LLaMA-Factory 微调。Docker:官方 vLLM 镜像 + qwenllm/qwenvl。【JS/npm/ONNX/wasm】:无官方 Qwen2.5-VL ONNX 权重,前置代 Qwen2-VL-2B 有 onnx-community 转换版可走 transformers.js + WebGPU;社区有人手工转 Qwen2.5 系列(已知踩坑,见 transformers.js issue #1415)。GGUF:社区有 samgreen / Mungert 的 72B GGUF,Ollama 上有 7B-Q5_K_M,llama.cpp 已合并支持(issue #11483)。量化:官方发布 AWQ(3B/7B/72B),前代有 GPTQ-Int4/Int8。【Node.js MCP 可行性】:纯 JS 路径不成熟(仅小模型实验性);生产环境推荐两条路——(a)Python 子进程跑 vLLM serve 暴露 OpenAI 兼容 HTTP,Node MCP 客户端 fetch;(b)直接调阿里 DashScope/Qwen 商用 API,Node 侧零模型加载。
- **pros**:1) 开源 VLM 中 OCR/文档/图表理解综合最强,OCRBench-V2 等关键指标成倍领先 GPT-4o;2) 真正的 OCR-free 端到端 VLM,无需外挂 PaddleOCR/Tesseract 等引擎,版面/表格/公式/手写一体处理;3) 原生动态分辨率,复杂版面/小字/高分辨率扫描件不丢细节;4) 1 小时+长视频 + 秒级时间定位(多模态 RoPE + 绝对时间编码),开源少有;5) Visual Agent 能力突出,ScreenSpot/AITZ/AndroidWorld 全面领先 GPT-4o,开源 GUI 自动化首选之一;6) 7B/32B 为 Apache-2.0 真商用免费,3B 可边缘部署、72B 可企业级;7) 生态完整:transformers / vLLM / sglang / Ollama / llama.cpp / LLaMA-Factory / AWQ 全栈支持;8) 中文与多语言 OCR(含阿拉伯语/竖排)效果好,适合国内场景。
