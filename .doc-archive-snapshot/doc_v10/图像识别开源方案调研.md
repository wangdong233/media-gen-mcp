# 免费图像识别开源方案深度调研

> **版本**:v1.0 · **日期**:2026-07-18 · **保存路径**:`media-gen-mcp/doc_10/`
> **调研方法**:8 维度并行 WebSearch → 60 候选去重 → top 15 项目逐个深读 GitHub/HuggingFace/论文/benchmark 验证 → 综合对比。**24 agent · 346 次工具调用 · 1.54M tokens**,license 与商用条款均经实测 GitHub LICENSE / HuggingFace 模型卡核实(非推测)。
> **核心需求(用户)**:免费、可商用、能**按图像类型做专精优化**(纯数字→识别数字、图表→提取数据、复杂版面→分块识别)、可集成到 Node.js MCP server。

---

## TL;DR(5 条核心结论)

1. **2025-2026 是范式分水岭**:传统 OCR 多模型管线(检测+识别+版面+表格+公式分模型)与 **OCR-free VLM**(单一视觉语言模型端到端读图)**按场景互补共存**,不是谁取代谁。整页复杂文档 VLM 已反超(OmniDocBench 96%+);纯数字/验证码/边缘部署轻量管线仍最优。

2. **"按图像类型专精"的两种实现**:① **新一代 VLM 内置多任务**(PaddleOCR-VL-1.6 / MinerU2.5 / Surya / Qwen2.5-VL 用同一权重覆盖文本+表格+公式+图表+版面);② **模块化管线按开关切换**(PaddleOCR PP-StructureV3 用 `use_table_recognition/use_formula_recognition/use_chart_recognition` 逐项开关,Marker 用 PdfConverter/TableConverter/OCRConverter 切换 Converter)。**没有"先分类图像类型再路由专精模型"的现成系统**——这是可自建的架构(见 [§集成路径-决策树](#最终推荐三档--决策树))。

3. **综合最佳(免费+可商用+好集成)= PaddleOCR 全家桶**(Apache-2.0 全栈,82k star,OmniDocBench v1.6 SOTA 96.33%,中文原生最强,有官方 MCP server + JS SDK)。**避开**:MinerU(署名义务)、Surya(>$5M 营收授权)、Marker(GPL-3.0)、DocLayout-YOLO(AGPL-3.0 网络传染)、Qwen2.5-VL 3B/72B(商用须申请,选 7B/32B)。

4. **纯 JS 零 Python 依赖能跑的只有三个**:`tesseract.js`(WASM,拉丁+数字+验证码)、`@paddleocr/paddleocr-js`(ONNX,仅 PP-OCRv5 检测+识别,**不含版面/表格**)、社区 ONNX 封装(RapidOCR/DocLayout-YOLO 权重 + onnxruntime-node,需自写前后处理)。其余全部走 HTTP 调 Python 后端 或 spawn 子进程。

5. **官方 MCP server 已有 4 个**:MinerU / Docling / PaddleOCR(`paddleocr-mcp`)/ Unstructured(支持 Claude Code/Cursor)。Node MCP server 接入 VLM 的关键桥梁是 **vLLM**(暴露 OpenAI 兼容 HTTP,Node 侧 `fetch` 即可)。

## 一、领域全景:两条路线的分野与融合

### 核心范式分裂:传统管线 vs OCR-free VLM

**路线 A:传统多模型管线(Traditional Pipeline)**
- 架构:文本检测(Det)→ 方向分类(Cls)→ 文本识别(Rec)→ [可选]版面(Layout)→ [可选]表格(Table)→ [可选]公式(Formula)→ 后处理
- 代表:Tesseract、EasyOCR、RapidOCR、docTR、OpenOCR、PaddleOCR PP-OCRv6/PP-StructureV3、Unstructured、HURIDOCS pdla、MinerU pipeline 后端、Docling StandardPdfPipeline
- 特征:**每个子任务一个独立小模型(<100M 参数)**,可逐项开关、可解释、零幻觉
- 优势:CPU 友好、显存低(PP-StructureV3 8–12GB vs VLM 31–77GB)、模块可替换、license 宽松(Apache 居多)
- 短板:活动部件多;阅读顺序/跨列表格/嵌套表格是难点;中文复杂长公式弱于顶级 VLM

**路线 B:OCR-free VLM(端到端视觉语言模型)**
- 架构:单一大模型直接把整页图像解码成 Markdown/HTML/JSON,无独立 OCR 引擎
- 代表:Surya(650M)、MinerU2.5-Pro vlm-engine(1.2B,基于 Qwen2.5-VL)、PaddleOCR-VL-1.6(0.9B,**OmniDocBench 96.33% SOTA**)、SmolDocling(256M)、Granite-Docling-258M、Qwen2.5-VL(3B/7B/32B/72B)、GOT-OCR2.0、dots.ocr(3.0B)、Chandra OCR 2(5.3B)、Infinity-Parser2-Pro(35.1B)
- 特征:**单模型统一处理 OCR+版面+表格+公式+阅读顺序+手写**,原生输出结构化 HTML(LaTeX 内联)
- 优势:管线简洁、端到端精度高(OmniDocBench 已破 96%)、版面语义强、跨栏阅读序天然
- 短板:显存吃紧(8GB+ VRAM,大模型多卡)、有幻觉风险、license 分层、Apple Silicon 吞吐低(Surya 仅 0.1 页/s)

**路线 C:Hybrid 混合(2025 新趋势)**
- 代表:MinerU hybrid-engine(95.30)、Marker `--use_llm`、Docling VlmConvert
- 思路:传统 pipeline 兜底零幻觉 + VLM/LLM 做难点增强(跨页表格合并、复杂公式)

### 关键认知:不是"VLM 一定赢"

实测数据显示两者不同场景互有胜负:
- **整页文档/复杂版面/学术论文**:VLM 已反超(PaddleOCR-VL 96.33%、MinerU vlm 95.39% vs PP-StructureV3 pipeline 86.47%)
- **纯数字/验证码/车牌/边缘部署/高吞吐**:轻量管线(PP-OCRv6 tiny 1.5M、RapidOCR、Tesseract)仍首选——快、轻、零幻觉
- **中文长公式**:顶级闭源 VLM(Gemini-2.5-Pro 0.439)略胜开源 pipeline(PP-StructureV3 0.535),但 PP-FormulaNet_plus 已支持多行+中文,差距收窄
- **版面定位精度**:VLM 仍有差距(SmolDocling mAP 0.231 vs 传统 DocLayNet 检测器 0.76+),几何切块传统模型更强

### 商用 License 三梯队(2026-07 实测)

| 梯队 | 项目 | 说明 |

## 二、按图像类型场景推荐(用户核心需求)

> 用户原始诉求:"图片中各块的识别,纯数字就识别数字,图表就识别数据"。下面按 8 类图像各给最佳方案 + 纯 JS 替代 + 商用最稳。

### 1. 纯数字图像(验证码/数字表盘/计数)
- **最佳(综合)**:PaddleOCR **PP-OCRv6**。明确优化数字显示屏、点阵字符、轮胎印、工业文字,tiny 档仅 1.5M 参数;验证码场景用 `use_doc_orientation_classify=false` 关版面开关,只跑 Det+Rec,毫秒级。
- **纯 JS**:**tesseract.js + 数字白名单**。`worker.setParameters({tessedit_char_whitelist:'0123456789'})` + `--psm 7`(单行)/`--psm 10`(单字符)。零依赖,4-6 位验证码甜区。
- **复杂兜底**:Qwen2.5-VL-7B。数字混在自然场景(仪表读数+单位+小数点+噪声),VLM 语义理解远胜 pipeline。
- ❌ 不推荐:MinerU/Surya/Marker 整页管线——大材小用。

### 2. 文档文字(中英文混排)
- **最佳**:PaddleOCR(**PaddleOCR-VL-1.6** 或 **PP-OCRv6**)。中文原生最强(百度),VL-1.6 OmniDocBench v1.6 **96.33% SOTA**,PP-OCRv6 简繁/拼音/竖排/生僻字全覆盖。Apache 2.0。
- **学术/科研(含公式+表格)**:MinerU vlm-engine high(95.39),OmniDocBench 90.67 超 Gemini-2.5 Pro/GPT-4o,中文 Ocean-OCR F1 0.965。
- **轻量离线**:RapidOCR。继承 PP-OCRv5/6 精度,无 PaddlePaddle 重依赖,pip 一行。
- **黑马**:OpenOCR。中英场景文本 SOTA,反超 PP-OCRv4 +4.5%,艺术字/手写/模糊/遮挡泛化更好。
- ⚠️ 避坑:Tesseract 中文是公认短板;docTR 有中文词表但**无生产级预训练权重**(issue #1699);EasyOCR 中文繁体/手写/生僻字落后。

### 3. 表格图片 → 结构化数据(HTML/JSON)
- **最佳(综合精度)**:PaddleOCR **PP-StructureV3(PP-TableMagic)** → HTML,OmniDocBench 表格 TEDS 88.22 / TEDS-S 92.38。
- **最佳(零幻觉+坐标)**:Docling **TableFormer**(52M,CDLA-Permissive)。TEDS 简单表 95.4 / 复杂表 90.1 / 全部 93.6,远超 Acrobat 65.3、Camelot 73.0,输出 OTSL token + 行列网格可入 pandas。
- **最强(跨页合并)**:Marker `--use_llm`。FinTabNet tree-edit-distance 0.816 → 加 LLM 0.907。
- **整页一体化**:MinerU vlm-engine。表格输出 HTML(非图片),跨页合并好。
- ⚠️ 注意:Docling TableFormer 有已知 bug(issue #2081 偶尔丢字/合并单元格);嵌套/空白对齐表格是所有工具弱项。

### 4. 图表图片 → 提取数据点
- **最佳(精度 SOTA)**:**Qwen2.5-VL-7B/32B**。ChartQA 89.5(GPT-4o 86.7),prompt 直接输出 JSON 数据点 + 绝对像素坐标。
- **最佳(工程专用)**:PaddleOCR **PP-Chart2Table**。柱/饼/折线图直接转表格,与 PP-StructureV3 一条流水线。
- **轻量 VLM**:SmolDocling-256M(chart TEDS 0.75)或 Granite-Vision-3B(chart TEDS 0.95,更强)。
- ❌ 不推荐:Tesseract/EasyOCR/docTR/RapidOCR——只读零散文字标签(轴标/图例),不做数据点提取。

### 5. 复杂版面(一张图多块混合:文字+表格+图)
- **端到端 SOTA**:MinerU vlm-engine high(95.39)或 PaddleOCR-VL-1.6(96.33)。一台 VLM 同时处理文本/表格/公式/图表/印章/版面/阅读顺序,直出 Markdown/JSON。
- **模块化可调**:PaddleOCR PP-StructureV3。五模块按 `use_table_recognition/use_formula_recognition/use_chart_recognition/use_seal_recognition` 逐项开关。
- **版面分块底座**:DocLayout-YOLO(若可接受 AGPL)+ 下游专精模型。85 FPS 切块,再分别送 OCR/公式/表格——这正是 MinerU 的做法。
- **企业 RAG 友好**:Docling。DoclingDocument + 内置 Chunker,原生接 LangChain/LlamaIndex/CrewAI。
- **精度天花板**:Marker(95.67 heuristic)。GPL-3.0 限制商用,但开源场景多栏/科学/法律/金融最强。

### 6. 手写
- **通用 VLM**:Qwen2.5-VL-7B。OCRBench-V2 成倍领先 GPT-4o,手写是其能力之一,中英都支持但非专精。
- **pipeline**:Surya(部分,非强项)、Marker(Handwriting block 非专精)、EasyOCR(英文手写尚可,中文差)。
- ⚠️ **专用 HTR 模型**:本批 15 个项目**没有真正的手写专精 SOTA**,硬指标需另寻 TrOCR、PaliGemma-HTR 或商业 API(Azure Document Intelligence / Google Vision)。

### 7. 数学公式
- **独立公式 SOTA**:PaddleOCR **PP-FormulaNet_plus**。token 长度扩到 2560,支持多行+中文公式,直接转 LaTeX。
- **整页一体化**:Surya OCR 2。整页 OCR 直接输出带 `<math>..</math>` 的 HTML,数学 KaTeX 兼容 LaTeX 内联,**无需独立 LaTeX OCR pass**。
- **学术 PDF**:MinerU vlm-engine。公式 CDM 88.46 超 dots.ocr 86.78、Gemini 85.71。
- **轻量替代**:LaTeX-OCR(pix2tex)/ Docling CodeFormulaV2 / SmolDocling(公式 F1 0.95 持平 GOT)。
- ⚠️ 复杂中文长公式:PP-StructureV3 Edit-Dist 0.535 弱于 Gemini-2.5-Pro(0.439)/Qwen2.5-VL-72B(0.434),建议上 VLM。

### 8. 票据/发票
- **端到端**:PaddleOCR **PP-StructureV3 + PP-ChatOCRv4**。版面+表格+印章(PP-OCRv4_seal)+ 关键信息抽取四合一,中文增值税发票/报销单/收据主战场。
- **拉丁语系收据**:docTR(CORD 训练)。CORD 上 Exact 95.56%,巴黎发票/小票顶级,中文需自训练。
- **强精度**:Marker 或 MinerU。表格+表单+公式+图片一体,复杂票据(多联单/报销单)。
- **企业托管**:Unstructured Platform(VLM Partitioner,包装 GPT-5-mini/Claude,SCORE-Bench 表格单元 #1,但按页付费、数据出域)。

## 四、2025-2026 前沿创新

### 1. OCR-free VLM 路线崛起——端到端取代三段式管线

核心叙事:**OCR-free VLM 正在精度上反超传统 pipeline**,且把 OCR/版面/表格/公式/阅读顺序合并到一个模型。

**代表模型(按参数量)**:
- **SmolDocling-256M**(IBM):256M 追平 27 倍大的 VLM,全页 F1 0.80 击败 Qwen2.5-VL-7B(0.72)/GOT-580M(0.69)/Nougat-350M(0.66);公式 F1 0.95 持平 GOT;推理 0.35s/页,仅 0.489GB VRAM。创新:**DocTags**(类 XML 标记,同时编码内容+结构+坐标)。
- **OpenDoc-0.1B**(复旦 FVL):0.1B 即达 OmniDocBench v1.5 90.57%,超许多 MLLM;走轻量专用对抗 MLLM。
- **PaddleOCR-VL-1.6**(百度):0.9B,NaViT 动态分辨率 + ERNIE-4.5-0.3B,**OmniDocBench v1.6 96.33% SOTA**。
- **MinerU2.5-Pro-1.2B**(上海 AI 实验室):基于 Qwen2.5-VL,OmniDocBench 90.67 超 Gemini-2.5 Pro/GPT-4o。
- **GOT-OCR2.0 / Dolphin**:General OCR Theory 路线,端到端把图像当"视觉 token 序列"直接解码;被 SmolDocling/PaddleOCR-VL/MinerU 对标。
- **Qwen2.5-VL**:开源 VLM 综合 SOTA,OCRBench v1 885、DocVQA 96.4、ChartQA 89.5、ScreenSpot 87.1(GPT-4o 仅 18.1)。后继 Qwen3-VL(2025 下半年,GUI/长视频更强)。

### 2. 关键架构创新
- **解耦两阶段(Decoupled Coarse-to-Fine)**(MinerU2.5):Stage I 下采样图做版面分析,Stage II 按版面从原图裁剪原生分辨率局部识别——规避 O(N²) 视觉 token 爆炸,降幻觉。**1.2B VLM 精度超 72B 通用 VLM 的核心**。
- **MRoPE(Multimodal RoPE)**(Qwen2.5-VL):位置编码拆时间/高度/宽度三维;视频动态 FPS 采样 + 绝对时间编码,支持小时级长视频 + 秒级事件定位。
- **OTSL Token 语言**(Docling TableFormer):为表格结构设计的自定义 token,52M 即 TEDS 93.6。
- **DocSynth-300K 合成预训练**(DocLayout-YOLO):把文档合成建模成"二维装箱问题",30 万张合成文档预训练,提升版面检测下游泛化。
- **CTC beats encoder-decoder**(OpenOCR SVTRv2,ICCV 2025):学术证明 CTC 识别在场景文本上可超过 attention,反向挑战"attention 必胜"。
- **Guided Layout(JSON-schema 约束解码)**(Surya):`SURYA_GUIDED_LAYOUT=true` 让 VLM 输出严格遵循 JSON schema。

### 3. 大 VLM vs 专用小模型 vs Hybrid
- **大 VLM**(Gemini-2.5 Pro/GPT-4o/Qwen2.5-VL-72B/Infinity-Parser2-Pro 35.1B):通用强,但重、显存吃、有幻觉、license 受限。
- **轻量专用**(SmolDocling 256M/PaddleOCR-VL 0.9B/MinerU2.5 1.2B/OpenDoc 0.1B):文档专项基准反超大 VLM,资源极低(0.489GB VRAM)。
- **Hybrid**(MinerU hybrid/Docling 双管线/Marker --use_llm):传统零幻觉 + VLM 高精度,按需切换或 LLM 兜底跨页表格。

### 4. Visual Agent / GUI 自动化
Qwen2.5-VL 把"图像识别"延伸到"图像操作":ScreenSpot 87.1、AITZ 移动端 83.2、AndroidWorld 35%,开源 GUI 自动化首选。这是 2025-2026 从"读图"到"用图"的范式扩展。

### 5. OmniDocBench(CVPR 2025)成为新事实基准
OmniDocBench v1.6 已替代 olmOCR-bench 成为文档解析主战场,PaddleOCR-VL-1.6(96.33%)、MinerU2.5-Pro vlm high(95.39%)、MinerU hybrid(95.30%)占据前三。**Rule of thumb:OmniDocBench > 90% 才算生产级**。

## 五、Node.js MCP server 集成路径

### 按"是否可在 Node 进程内原生跑"分类

**✅ 纯 JS/WASM 可在 Node 内跑(零 Python 依赖)**

| 项目 | npm 包 | 能力范围 | 限制 |
|---|---|---|---|
| Tesseract | `tesseract.js`(38.5k star) | 100+ 语种 OCR + 数字白名单 + 13 种 PSM | 中文弱;不支持表格语义/公式/手写 |
| PaddleOCR.js | `@paddleocr/paddleocr-js` / `ppu-paddle-ocr` | PP-OCRv5 文字检测+识别(中英强) | **不含 PP-StructureV3 版面/表格/公式流水线** |
| RapidOCR(自封装) | `onnxruntime-node` + 官方 .onnx | PP-OCRv5/v6 三段式 OCR | 需自写 DBNet 后处理 + CTC 解码,工作量大 |
| DocLayout-YOLO(自封装) | `onnxruntime-node` + 社区 ONNX | 版面切块 13 类 | 需自写 letterbox + NMS;**AGPL-3.0 阻断闭源** |

**🐍 必须 Python 子进程或 HTTP 远程调用**:MinerU、Surya、Marker、Docling、Unstructured、EasyOCR、docTR、OpenOCR、Qwen2.5-VL、HURIDOCS pdla

**🔌 已有官方/社区现成 MCP server**
- **MinerU**:官方 MCP server(接 Cursor/Claude Desktop/Windsurf/Cherry Studio)
- **Docling**:官方内建 MCP server(Python MCP)
- **PaddleOCR**:官方 `paddleocr-mcp`(Python FastMCP v2,支持 local/aistudio/qianfan/self_hosted 四种推理来源)——⚠️ stdio 模式多页 PDF 仅处理首页 bug(Issue #16755),建议 `--http`
- **Unstructured**:官方 Transform MCP server(支持 Claude Code/Cursor/Codex CLI)

### 四个核心 MCP 工具的推荐实现栈

#### `recognize_image(imagePath|imageUrl, prompt?)` — 通用图像理解
- **零依赖纯 JS**:❌ 不可行(无 Node 内可跑的通用 VLM)
- **最强(需 Python)**:Qwen2.5-VL-7B/32B via vLLM(OpenAI 兼容 HTTP),Node 端 `fetch('http://localhost:8000/v1/chat/completions', ...)`。Apache-2.0。
- **折中**:调阿里 **DashScope 商用 API**(Node 零模型加载,按 token 付费,免运维,数据出域)

#### `extract_text(imagePath|imageUrl, lang?, whitelist?)` — 纯文字提取
- **零依赖纯 JS(轻量)**:`tesseract.js` createWorker(lang) + recognize,支持 `tessedit_char_whitelist`。验证码/车牌/单语种印刷体。
- **最强(中文/多语/复杂版面)**:PaddleOCR(PP-OCRv6 或 PaddleOCR-VL-1.6)via `paddleocr-mcp --http`,Node 当 HTTP 客户端。
- **折中**:`@paddleocr/paddleocr-js`(全运行时,PP-OCRv5 ONNX),中文强无 Python,但仅检测+识别

#### `extract_table(imagePath|pdfPath, outputFormat?)` — 表格 → HTML/JSON
- **零依赖纯 JS**:❌ 不可行
- **最强**:PaddleOCR PP-StructureV3(PP-TableMagic)或 Docling(TableFormer TEDS 93.6)。都有官方 MCP/HTTP。
- **折中**:Docling `docling-serve` Docker(:5001),Node POST 文件,输出 OTSL + pandas 网格

#### `analyze_chart(imagePath, outputFormat?)` — 图表 → 数据点
- **零依赖纯 JS**:❌ 不可行
- **最强**:Qwen2.5-VL-7B via vLLM(ChartQA 89.5),prompt = "Extract all data points as JSON {x, y, label}";或 PaddleOCR PP-Chart2Table
- **折中**:DashScope API(Qwen2.5-VL 商用托管,Node fetch,免本地 GPU)

### 三档推荐架构(按运维成本)

**档位 1:零依赖纯 JS(个人/轻量/原型)**
- 仅 `tesseract.js`,4 工具全由它兜底:extract_text 用 recognize;extract_table/analyze_chart 退化为"提取图表文字标签"(无结构化);recognize_image 弱化为 OCR
- ✅ npm 一行装,无 Python/Docker/GPU ❌ 中文弱、无表格/图表/版面语义

**档位 2:混合架构(推荐生产,平衡成本)**
- `extract_text` → tesseract.js(轻量印刷)+ PaddleOCR HTTP(中文/复杂)
- `extract_table`/`analyze_chart`/`recognize_image` → 远程 Qwen2.5-VL(vLLM 自托管 或 DashScope)
- ✅ 按需付费/拉起,全覆盖 ❌ 两个后端要维护

**档位 3:最强 Python 栈(企业/批量)**
- 全走 PaddleOCR(PP-StructureV3 + PP-OCRv6 + PP-Chart2Table + PP-FormulaNet + PP-ChatOCRv4)+ Qwen2.5-VL-32B(vLLM)
- Docker Compose(paddleocr-mcp + vllm + nginx)
- ✅ Apache 全可商用、SOTA、中文最强、覆盖全 7 类 ❌ 8GB+ VRAM,运维重

### 避坑提示
1. **PaddleOCR.js 仅 PP-OCRv5**:别误以为 Node 内能跑完整 PP-StructureV3,需另起 Python HTTP
2. **Docling 老版面 CC-BY-NC-4.0 陷阱**:Docker 镜像可能仍带 docling-layout-old,生产前必须确认切到 heron
3. **RapidOCR 纯 JS 路径工作量**:DBNet 后处理 + NMS + CTC 解码要在 JS 侧重写,非"import 即用"
4. **DocLayout-YOLO AGPL-3.0**:即使只做版面切块,整个 Node MCP server 也被传染;闭源请换 PP-DocLayout-plus 或 LayoutLMv3
5. **vLLM 是 Node 接入 VLM 的关键桥梁**:Surya/MinerU/Qwen2.5-VL/PaddleOCR-VL 都通过 vLLM 暴露 OpenAI 兼容 HTTP,Node 侧 `fetch` 即可
6. **MCP stdio 多页 PDF bug**:PaddleOCR 官方 MCP stdio 模式仅处理首页(Issue #16755),用 `--http`

## 七、待验证 / 存疑的点

### 未深挖但频繁被引用(可作后续调研)
- **GOT-OCR2.0 / General OCR Theory**:SmolDocling/PaddleOCR-VL/MinerU 多次对标,本批无独立深挖。License/中文精度/Node 接入待补。
- **Dolphin**:OCR-free VLM,被引用,未深挖。
- **dots.ocr / dots.mocr(3.0B,83.9%)**:olmOCR-bench 高分,商用 license 与部署成本未评。
- **Chandra OCR 2(5.3B,85.9%)**:datalab.to 闭源,Marker 背后下一代,商用授权价未知。
- **Infinity-Parser2-Pro(35.1B,87.6%)**:olmOCR-bench 最高分,35B 生产部署成本未评。
- **MonkeyOCR-Pro-3B**:MinerU 报告对比项,未深挖。
- **PaliGemma / PaliGemma-HTR**:手写识别常被提及,本批未覆盖。

### 技术细节存疑
1. **PaddleOCR.js 在 Node 服务端实测性能**:3.5.0(2026.04)刚发,ONNX Runtime Web + WebGPU,但纯 Node.js(无浏览器 WebGPU)下的推理速度/内存/PP-OCRv5 之外模型支持均未实测。
2. **RapidOCR + onnxruntime-node 自封装工作量**:报告说"工作量大",未给 LOC 估算。Docling 内置 RapidOCR 适配器可参考,移植 JS 代价待评。
3. **MinerU 署名义务对白标 SaaS 的影响**:"必须显著标注使用了 MinerU"对白标产品是否阻断,法律口径需确认。
4. **Docling 依赖链 AGPL 是否彻底清除**:3.0+ 已移除 doc-layout-yolo/mfd_yolov8(AGPL)与 layoutreader(CC-BY-NC-SA),但生产商用前建议 `pip-licenses` 扫一遍。
5. **Qwen3-VL vs Qwen2.5-VL 实际差异**:Qwen3-VL(2025 下半年)GUI/长视频更强,OCR/文档精度是否进一步提升未实测;OCRBench 真实分需复核(此前线索曾把 InternVL 854 误记为 Qwen)。

### License 风险点
1. **Surya/Marker OpenRAIL-M 阈值**:$5M(Surya)/$2M(Marker)是"融资 OR 营收"任一超过即触发,已被投 $5M 即使营收 0 也需授权。
2. **Qwen2.5-VL 3B "商用须申请"**:Research License 措辞严格,**选型优先 7B 或 32B(Apache)**。
3. **Marker 商用自托管**:"Commercial self-hosting requires a license"——即使接受 GPL-3.0,商用自托管仍需额外授权,易踩坑。

### 场景能力存疑
1. **手写识别**:本批 15 项目没有真正手写专精 SOTA。Qwen2.5-VL/Surya/Marker 都"支持但非强项",中文手写可能需另寻 TrOCR、PaliGemma-HTR 或商业 API。建议补手写专用模型报告。
2. **票据中国本土合规**:PaddleOCR PP-ChatOCRv4 + PP-StructureV3 适合增值税发票,但报销自动化的"发票查验/真伪/重复报销检测"需另接税务 API,OCR 仅第一步。
3. **复杂中文长公式**:PP-StructureV3 Edit-Dist 0.535 弱于 Gemini-2.5-Pro(0.439)/Qwen2.5-VL-72B(0.434),PP-FormulaNet_plus 最新表现是否追平未实测。

### 未覆盖的相邻领域
1. **版面修复/去噪/去水印**:本批聚焦"识别","图像预处理"(去印章/去水印/纠偏/增强)是识别前关键步骤,缺独立工具对比。
2. **多模态嵌入/向量化**:RAG 场景识别后的 chunking + embedding 未涉及。
3. **实时视频流 OCR**:Qwen2.5-VL 支持长视频,但流式 RTSP/摄像头实时 OCR 工程方案未评。
