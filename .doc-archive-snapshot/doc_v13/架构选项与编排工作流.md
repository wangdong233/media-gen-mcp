## 二、与既有 ppt MCP 关系定位三选一裁决

### 2.1 两个 MCP 的能力真相

**media-gen-mcp(0.12.1,20 工具,MIT)**——纯「素材/产物生成 + 识别 + 渲染」引擎。`grep -rci "pptx\|python-pptx\|powerpoint\|slidev\|marp\|reveal" src/` → **全 0 命中**。产物全是单张图/单段视频/单文件 HTML/SVG/PNG/TXT(叶子素材,非容器文档)。

**ppt MCP(python-pptx 系,32 工具)**——「PPTX 容器 + 原生元素 + 模板/主题」组装器。能力分 5 类:

| 类 | 工具 | 性质 |
|---|---|---|
| 容器/结构 | create_presentation / open_presentation / save_presentation / add_slide / create_presentation_from_template / create_presentation_from_templates(模板序列→整套 deck) / create_slide_from_template / apply_slide_template | PPTX 文档组装 |
| 元素放置(英寸坐标) | add_text / manage_text / add_bullet_points / **add_chart**(原生可编辑) / add_table / add_shape / add_connector / populate_placeholder | 逐元素摆位 |
| 图片 | **manage_image**(image_source **必填**+filter:亮度/对比度/模糊) | **消费图片,不生成图片** |
| 样式/主题 | apply_professional_design(modern_blue/corporate_gray/elegant_green/warm_red 四套) / manage_slide_masters / manage_fonts / format_table_cell / manage_hyperlinks / manage_slide_transitions / optimize_slide_text | 主题化 |
| 自动生成/自省 | **auto_generate_presentation**(include_images **默认 false**,无 provider/key 参数) | 文本模板填充(零 AI 生图) |

### 2.2 四个判读性结论(决定关系定位)

1. **`auto_generate_presentation` 无 AI 生图能力**:`include_images` 默认 false + 无 provider/key 参数 → 本地 python-pptx 按 topic 填模板文本(可能含简单启发式/占位图),**不调 AI 模型生成写实图**。这正是 media-gen-mcp 的互补缺口。
2. **`add_chart` 是原生可编辑图表**:categories+series 进 python-pptx 原生 chart 对象,PowerPoint 里可改数改型。**media-gen-mcp 的 generate_chart 反过来产 SVG/PNG 烤制美图(不可改数但视觉更精致)**——两者互补不冗余。
3. **`manage_image` 是图片消费者**:必填 `image_source`(文件路径/URL),自身不生成。**天然接 media-gen-mcp 的 generate_image/render_svg 产物**。
4. **全是坐标式手动摆位或模板驱动**:没有「AI 懂布局」——布局智能要么靠 Claude,要么靠 template。

### 2.3 三种关系定位对比

| 关系 | 含义 | 优点 | 致命问题 |
|---|---|---|---|
| **(a) 整合**:media-gen-mcp 内部调 ppt MCP 组装 | 对用户一个入口 | 需要 MCP-to-MCP 调用(MCP 规范无标准 server→server,要么子进程要么硬耦合);**破坏两 MCP 独立演进**;编排藏进工具(同选项1 缺点) |
| **(b) 差异化自建**:media-gen-mcp 自己出 PPTX | 单一 MCP 全包 | **重造 python-pptx 轮子**(media-gen-mcp 零 PPTX 代码);违 §4 核心身份;和 ppt MCP 内耗;6+ 人日 |
| **(c) 互补** ★ 推荐 | 两 MCP 各管一摊,Claude 按需选 | 零重复;各守核心能力;Claude 是唯一编排者(契合 MCP LLM-first);独立升级 | 需用户/Claude 知道何时用谁(skill 解决) |

### 2.4 裁决 + 精细化分工协议

**推荐 (c) 互补**:

| 层 | 归属 | 工具 |
|---|---|---|
| **PPTX 容器 + 原生可编辑元素 + 模板/主题** | **ppt MCP** | create_presentation / add_slide / **add_chart(原生)** / add_table / add_shape / add_connector / manage_text / apply_professional_design / create_presentation_from_templates / save_presentation |
| **AI + 结构化视觉素材(叶子产物)** | **media-gen-mcp** | generate_image / generate_card / generate_chart(烤制) / generate_diagram / generate_formula / generate_icon / generate_qrcode / render_svg / render_video / generate_interactive_diagram |
| **编排(选谁、怎么拼、布局)** | **Claude(可选 PPT skill 引导)** | tool call 序列 |

**五条理由**:
1. **能力集几近不相交(零内耗)**:生产者→消费者天然流水线,无一处重叠。
2. **原生图表 vs 烤制图表互补不冗余**:同概念两种价值无法互替。
3. **守 media-gen-mcp 核心身份**:不向应用组装扩张(§4)。
4. **Claude 是 MCP 间天然编排者**:MCP 规范无标准 server-to-server 调用,(a) 整合需丑陋耦合。
5. **`generate_card` 是唯一应保留的「准幻灯片」差异化**:一张 Satori card ≈ 一张设计感幻灯片,定位类似 Gamma AI 单页——出图/HTML,不做 PPTX 组装,与 ppt MCP 错位共存。

## 三、Claude 编排工作流 5 阶段设计(主引擎)

### Phase 0:意图捕获

Claude 从「做份 X 的 PPT」解析出:
```
{topic, slide_count(默认 8-10), audience, editability_need, format_pref}
```
- **editability_need 是决定 Path A/B 的根参数**。
- **无法探测时显式问用户而非猜**(「这份 PPT 后续需要在 PowerPoint 里改字吗?发给谁?」)。

### Phase 1:outline 生成(防 LLM 漂移)

Claude 产出结构化大纲数组,每 slide spec:
```json
{
  "index": 0,
  "type": "cover | section | content-bullets | data-chart | arch-diagram | quote | formula | closing",
  "title": "...",
  "content_hint": "...",
  "asset_needs": ["hero-card 1920x1080", "bar-chart vega", "arch-diagram d2"],
  "editability_flag": "baked | editable"
}
```
- **outline 先行**(对应 ppt-master spec_lock 防 LLM 漂移)——不让 LLM 边做边漂。
- outline 定稿后才进 Phase 2。

### Phase 2:素材并行生成

- Claude 按 `asset_needs` 并行调 media-gen-mcp(同 deck 多张图可 dispatch_parallel_agents 并发)。
- 每张素材落盘到约定工作目录:`./ppt-proj/{assets/, slides/, deck.pptx}`(见 skill 协议 5)。
- SVG 资产(card/chart/diagram/formula/icon/qrcode)若要进 PPTX,**先经 render_svg 预光栅化成 PNG 再嵌**(pptxgenjs Node SVG 缺口闭环)。

### Phase 3:组装

**Path A(可编辑)**:
```
ppt MCP: create_presentation / create_presentation_from_template(选模板)
  → 逐 slide add_slide
  → manage_image 放烤制资产(generate_image/chart/diagram 产的 PNG)
  → add_text/add_chart/add_table 放可编辑元素
  → apply_professional_design 统一主题
  → save_presentation → .pptx
```

**Path B(烤制图集)**:
```
N × generate_card(1920×1080, 同 accent/font/bg)→ 收集 PNG
  → ppt MCP 全屏图 slide(N 张 PNG 当 background)
  → 或 puppeteer page.pdf() 直接出 PDF
```

**Path C(HTML 幻灯片,技术放映场景)**:
```
复用 generate_interactive_diagram 的 D2→单文件 HTML viewer DNA(P0-5A)
  扩成多页 + 键盘翻页 viewer(零新依赖,借鉴 oh-my-ppt HTML-first 设计)
```

### Phase 4:审视与微调

- 某张图不满意 → **单独重调 generate_image,不重建整 deck**。
- 某页布局挪 → 改 ppt MCP 坐标或 template。
- doc_v12 范式 C 的「AI 对话微调 + 重生成」对 PPT 同构适用,**叠加在原生可编辑 PPTX 之上做增效线不互斥**(双轨最稳:文件原生可编辑兜底 + AI 对话微调增效)。

## 四、核心决策框架:何时 card 整图 / 何时 pptxgenjs/python-pptx 可编辑

### 4.1 决策树两问定路径

```
第一问:用户/受众是否需要在 PowerPoint 里改文字?
│
├─ YES(发老板改/协作编辑/客户二次编辑)
│    → Path A 可编辑:
│       文本 → ppt MCP add_text(原生文本框,英寸坐标)
│       图表(客户改数)→ ppt MCP add_chart(原生 OfficeChart)
│       配图 → generate_image → manage_image
│       架构图 → generate_diagram → render_svg → manage_image
│       (图本身烤制,但周围文字可编辑)
│
├─ NO(一次性定稿/线上放映/PDF 分享/视觉 pitch deck)
│    → Path B 烤制图集:
│       N × generate_card(同 accent/font/bg)→ 收集 PNG
│       → ppt MCP 全屏图 slide 或 PDF
│
└─ UNKNOWN(最常见歧义,「做份汇报不知改不改」)
     → 默认 Path A
     【关键原则】不可编辑是单向不可逆损失(老板双击改不了字=产物废),
                 可编辑在所有场景都不致命(就算不改也不影响)。
                 故歧义时保守选可编辑。

第二问(仅在 Path A 内部分流):图表客户会改数吗?
│
├─ 会改 → ppt MCP 原生 add_chart(数据数组进 python-pptx,双击改数改型)
└─ 不会改/终稿展示 → media-gen-mcp generate_chart(Vega-Lite 烤制美图,视觉更精致但死图)
```

**阈值规则化进 skill,不让 Claude 每次现判。**

### 4.2 generate_card 当「整张幻灯片」的可行性裁决

**物理可行,编辑性不可行——故必须按 slide 类型分流,不能一刀切全卡路线。**

**三组硬证据**:

**(A) 物理前提成立**
- card.ts:543-544 width/height 完全自由,传 1920×1080 即标准 16:9 slide。
- Satori 渲染确定性(同输入永远同输出,无 AI 抽奖)。
- CJK 内置 Noto Sans SC 子集自动回退(card.ts:95-137),中文免配置。
- WCAG 对比度自动 warning(card.ts:555-573)防白底白字。
- 渐变背景/辉光/logo/emoji 全内置。

**(B) 编辑性硬边界**
- 文字经 Satori→resvg 栅化成字形路径或像素(card.ts:683-714),导出后**不可选不可改**(Satori 范式本性,非 bug)。
- 仅 4 文本槽(title/subtitle/body/footer)+ 1 logo 位(card.ts:233-270),**无项目符号列表/多段落/per-run 字体/表格**。
- 5 固定模板(og/quote/minimal/hero/panel)各会丢弃部分字段并发 warning(card.ts:657-665),版式自由度低。
- **无多元素同框**(放不下「标题+3 要点+图+小图」)。

**(C) 裁决**
card 当 slide 适合 **4 类固定视觉页**:
- 封面 hero
- 章节 minimal
- 金句 quote
- 收尾 panel

这 4 类**本来就不需要用户改字**。

**不适合**:内容页/数据页/对比页(用户高频改字)。

**结论**:全卡路线(Path B)只对「一次性定稿 pitch deck/线上分享/PDF 图集」是优势(防误改跨设备一致),对「协作编辑 PPTX」是硬伤——两类必须分流,不能一刀切。

## 六、零新代码 skill 引导层(PPT skill 协议 6 条)

skill 文件位置建议:`.claude/skills/ppt-builder/SKILL.md` 或 doc_v13/ recipe(纯 markdown 零代码)。内化 6 条协议:

### 协议 1:outline schema 规范

每 slide 必标:`type` + `asset_needs[]` + `editability_flag`(该 slide 走烤制还是可编辑)。outline 先行,定稿后才进素材生成。

### 协议 2:素材→工具映射表

见 §五矩阵。LLM 选材零歧义:按 slide type 查表。

### 协议 3:可编辑 vs 烤制决策树

见 §四两问。**意图不明默认 Path A**(不可编辑单向不可逆,可编辑不致命)。

### 协议 4:主题一致性协议(全 deck 最难的工程问题,必须钉死)

**问题**:generate_card 是 per-call 独立传 bg/accent/color/font,无 deck 主题对象;ppt MCP apply_professional_design 有四套 color_scheme 但与 card 色值不自动对齐。若不约束,Claude 每张 slide 现选色 → 20 张 slide 配色混乱。

**解法三层**:
- **(a) skill 协议 4 规定**:outline 阶段就定一套 deck-level theme 对象:
  ```
  {primary_accent(hex), bg_from/bg_to(渐变), title_color, body_color, font_family}
  ```
  所有后续 generate_card 调用强制传同一组参数,所有 ppt MCP add_text 传同一 font/color,apply_professional_design 选最接近的 color_scheme。
- **(b) 复用 interactive-html 三杠杆条件展开范式**(interactive-html/index.ts:19-22,darkThemeID 全大写/noXMLTag/salt,传了才覆盖不传 byte-identical)——deck theme 同样「传了才覆盖 per-slide 默认」,保最小加性。
- **(c) 复用 card.ts:555-573 的 WCAG contrastRatio 自动 warning** 做全 deck 无障碍兜底,标题/正文/背景三者对比 <3:1 自动 warn 拦截「白底白字」事故。

**未决待 spike**:generate_card 批量一致性未实测(同 deck 连跑 10× generate_card 同参数,titleGradient+glow 互斥等约束是否跨调用稳定,字体缓存/emoji CDN 是否抖动)——需第 2 步端到端 10-slide 实测确认。Satori 确定性本质预示应该稳。

### 协议 5:assets 落盘约定

项目级 PPT 工作目录:
```
./ppt-proj/
  ├── assets/        # media-gen-mcp 产的 PNG/SVG/MP4
  ├── slides/        # 中间产物(每页 JSON spec)
  └── deck.pptx      # 最终产物(ppt MCP save_presentation)
```
避免 Claude 每次乱放。目录规范属项目层非 MCP 层。

### 协议 6:失败恢复与 fallback(跨 MCP 编排级容错)

**单 slide 失败不重建整 deck,标 retry。** Fallback 链规则化,不靠 LLM 现场发挥:
- `generate_image` Agnes 限流 → 自动 fallback 智谱 cogview(P0 已实现 providers/registry.ts 的 submit 可 fallback、poll 路径绝不 fallback 铁律)→ 仍失败 → `generate_card` 当视觉占位(Satori 确定性不调 AI 模型,永远可用)。
- 图表失败 → 退化 ppt MCP add_chart 原生(丑但可编辑)或反之。
- 架构图 D2 语法错 → enhanceD2Error(P0-2 错误契约 14 patterns)给 LLM 可读 hint 自动改。

**关键边界**:media-gen-mcp 有 provider fallback 但**跨 MCP 的编排级容错**(如 generate_image 全 fallback 失败后是否改走 ppt MCP 占位文本框)目前靠 Claude 判断——skill 应给明确 fallback 链规则化。

**与 ppt MCP 分工的 NEXT 句导流**(对应 P0-1 cross-ref 范式):media-gen-mcp 出初稿素材,ppt MCP 改细节避免功能重叠,工具 description 加「NEXT: 组装成可编辑 PPTX 走 mcp__ppt__」。

## 八、冲突点名 + 诚实边界

### 8.1 对调查结论的纠偏

1. **inv:output-format-ux 的 Path C(全格式默认 editable-pptx)** 越 §4 界,与主报告推荐冲突——**否决,改走 TIER 1**。
2. **inv:pptx-libs 推荐 pptxgenjs 作主引擎**:对「可编辑 PPTX」场景正确,但若 media-gen-mcp 采用其 addText 出原生可编辑文本框 = **越界**;**pptxgenjs 在 media-gen-mcp 内仅可用于 addImage 装订图片底**(TIER 2b),addText/editable 路径归 ppt MCP。
3. **inv:ai-ppt-repos 的「路线 B 自建 PPTX 组装必须 reimplement 不能 import(避 AGPL/GPL)」**:结论正确但主报告更进一步——**不自建,重组装**,从根上规避 license 雷区。
4. **inv:mg-reuse-map 说 card 仅 4 槽放不下 bullets 故不能当 slide** vs **inv:output-format-ux 说默认可编辑 pptx**:解法是 **hybrid 按 slide 类型分流**(cover/section/quote/closing 走 card,content/data 走 editable),不是非此即彼。
5. **inv:output-format-ux 推荐 Path B 图像 MVP(~1.5 人日)守界** vs **inv:orchestration 推荐零新代码 skill**:实则两者对齐——**skill-first 是零代码起步,图像 MVP 是 skill 不够时的下一步**,不是二选一。

### 8.2 诚实边界(不理想化)

1. **auto_generate_presentation 是否 LLM 增强未读源码确认**——工具签名 include_images 默认 false + 无 provider/key 参数,强推断是 python-pptx 本地启发式模板填充零 AI 生图,但「文本内容是否调 LM」需实测一次确认。
2. **pptxgenjs Node 下 SVG 返回 IMG_BROKEN**(gen-media.ts 源码硬证据)对 media-gen-mcp 不阻塞因已有 render_svg 预光栅化闭环,但 **AI 摘要谎称 Issue #963 已修不可信**(master 源码仍返回坏图)。
3. **MCP 间 Claude 编排要求两个 MCP 同会话加载**——若用户只装了 media-gen-mcp 没装 ppt MCP 则 Path A 不可用;skill 应探测能力自省(复用 list_vision_capabilities 范式)缺 ppt MCP 时降级 Path B 并诚实告知。
4. **PPTX 是 zip 不可 git diff**——若 TIER 2b 落地,应同步落 slides JSON 大纲作 source-of-truth,.pptx 当 derived(同 doc_v12「DSL 是源 HTML 是 derived」范式)。

### 8.3 可落地性排序

```
skill(零代码,立即可做)> Path B 图像 MVP(1.5 人日,守界)> Path C 全格式含 editable-pptx(4-6 人日,越界进文档生成需用户拍板)
```
