# 快速生成 + 快速微调 工作流范式调研

> 范围:`generate_interactive_diagram`(src/interactive-html/,8 文件)生成后的"微调"工作流。
> 用户原话:**"如果能够快速出一个动态的图,并且我可以做出快速的微调,应该还是挺实用的。"**
> 立场红线(必须守):① 单文件自包含 HTML(零外链、零 node_modules、离线可看、可嵌 GitHub README);② 纯免费(MIT/Apache 优先);③ 同输入同输出可入 git;④ 向后兼容不破坏;⑤ GitHub README 嵌入场景(JS 受限、无后端可保存)。
> 调研边界:只读 media-gen-mcp 源码;不动其源码,产物只写 doc_v12/。

---

## 0. TL;DR + 裁决

**裁决:推荐 范式 C(AI 自然语言微调)+ 混合增强(视觉点击选择 → 对话修改),不推荐范式 B(视觉拖拽编辑器)。**

三条硬证据:

1. **D2 SVG 已内嵌节点 ID,零改 D2 即可往返**(本次调研最大发现)。
   - 实证:`test/golden/expected/interactive-html/architecture.golden.html` 内的 D2 SVG,每个节点的外层 `<g class="...">` 是节点 ID 的 **base64 URL 编码**:
     - `<g class="Y2xpZW50">` = `base64("client")` → `client`
     - `<g class="Z2F0ZXdheQ==">` = `base64("gateway")` → `gateway`
     - `<g class="KGFwaSAtJmd0OyBjYWNoZSlbMF0=">` = `base64("(api -> cache)[0]")` → 边也带 ID
   - 源码确认(D2 上游 `d2renderers/d2svg/d2svg.go`):
     - L8:`"encoding/base64"` 显式 import
     - L1012(边):`classes := []string{base64.URLEncoding.EncodeToString([]byte(svg.EscapeText(connection.ID)))}`
     - L1627(节点):`classes := []string{base64.URLEncoding.EncodeToString([]byte(svg.EscapeText(targetShape.ID)))}`
     - L1663:`<g class="shape...">` 是内层视觉形状;外层 `<g class="BASE64">` 才是 ID 载体
   - **结论**:这不是偶然,是 D2 故意烤进去的稳定标识符;同一 DSL 多次渲染字节同(golden byte-compare 已证),可作为"点击 → 取 ID → 回喂 Claude"的可靠往返桥梁,**无需 D2 任何改动**。

2. **范式 B(视觉拖拽)与 5 条立场全部冲突**,且 ROI 极差(详见 §6):
   - 与 auto-layout 冲突(D2 自动布局,拖了也会被下次重排冲掉);
   - 持久化难(单文件 HTML 不能自写磁盘,browser sandbox;localStorage 不入 git,破立场 ③);
   - 单文件天花板(reactflow/tldraw 都要 React runtime + asset bundle,破立场 ① ②);
   - 自研成本 ≥ 5 人日,复用 Claude 能力为 0。

3. **范式 C 是 MCP 场景的"原生打法"**:
   - 用户已对着 Claude,无需额外编辑器;"把支付服务移到右下 / 加 redis 在订单和 db 之间"这类话 Claude 本来就能改 DSL;
   - 实现成本趋近 0(已有 `generate_interactive_diagram` + D2 重渲染能力,只缺"把上次 DSL 钉在上下文"的记忆约定);
   - 混合增强:viewer 里给节点加 click → 读 base64 class → 解码出节点 ID → 自动把"用户点了 X"塞进对话上下文 → Claude 改 DSL → 重生成。**视觉选择 + 对话修改,零拖拽**。

## 2. 三范式对比

### 2.A 重写 DSL 重生成(当前范式)

**流程**:用户改 D2 DSL → `generate_interactive_diagram` 重渲染 → 新 HTML。

**技术实现**:已有,零新增。

**UX 优劣**:
- ✅ 同输入同输出,天然入 git(守立场 ③)。
- ✅ 单文件自包含不破(守立场 ①)。
- ✅ 向后兼容(守立场 ④)。
- ❌ **小改也要重写 DSL**:挪个节点 = 找到 DSL 里那行 → 改 `a -> b` 顺序或加 `direction` → 重生成。用户脑子要在"视觉"和"DSL 文本"两个表示系之间反复切换。
- ❌ 不知道节点对应 DSL 哪行(尤其大图,30+ 节点)。
- ❌ 用户原话"只切主题不算交互图"即指此——重生成 ≠ 微调。

**立场契合度**:① ② ③ ④ ⑤ 全守。但**没解决用户核心诉求**。

**何时够用**:DSL 作者本人、图小(<10 节点)、改的是结构不是位置。

---

### 2.B 视觉拖拽编辑(自研编辑器)

**流程**:在 HTML 里拖节点 / 双击改标签 / 加节点 → 导出修改后的 DSL 或 HTML。

**技术实现路线**(按重量排):

| 路线 | 实现 | 单文件自包含? | 立场冲突 |
|---|---|---|---|
| B1. 原生 DOM + `contenteditable` | click 节点 → 浮 `<input>` 覆盖在 `<text>` 上(用 `getBoundingClientRect()` 定位)→ blur 写回 `textContent` | ✅ 可以 | 仅标签编辑,不能拖位置 |
| B2. SVG 直接拖拽 | pointerdown on `<g.shape>` → 改 `transform="translate(x,y)"` | ✅ 可以 | 与 D2 auto-layout 冲突;保存难 |
| B3. reactflow / tldraw / drawio embed | 引入 React runtime + asset bundle | ❌ 破立场 ① ②(外链或体积爆炸) | 全破 |

**B1 标签编辑(contenteditable)可行性**:技术可行(SVG `<foreignObject>` 或 HTML `<input>` 浮层都是标准工艺),~80 行 viewer JS。**但只能改标签,不能拖位置、不能加节点、不能改连接** —— 用户要的是"挪个节点",B1 满足不了。

**B2 拖位置的根本矛盾**:
- D2 是 auto-layout DSL,节点位置由布局算法(ELK/Dagre)算出,不是用户指定的;
- 用户拖了 `transform`,下次重生成(任何小改)布局重算,拖拽结果**直接被冲掉**;
- 要持久化就得让 D2 接受"用户指定的固定坐标",D2 有 `near` / `top` / `bottom` 等连接关系关键字,但没有"绝对像素坐标"原语(因这违反 diagram-as-code 的宣言);
- 退路:把拖拽结果序列化成 D2 能吃的 `direction` / `near` 约束 —— 这是"视觉操作 → DSL 约束"的逆向编译,本质是在 viewer 里重写一个 D2 前端,**ROI 极差**。

**B3 现成编辑器为什么不能用**:
- **reactflow**:要 React 运行时;CDN 打包进 HTML 可行但体积 ~500KB+ 且有外链(asset bundle);无原生"存回自包含 HTML"。
- **tldraw**:embed 导出存在,但完整编辑器要其 asset bundle;可序列化为 snapshot,重新进编辑态要 tldraw runtime;图片/字体 blob 存储是痛点。
- **draw.io / diagrams.net**:最接近(有"Embed / Export as HTML"出单文件,内嵌 diagram XML 可往返)。但它是 GPL/Apache 双协议的大块编辑器,不是"轻量增强",**把 drawio 嵌进我们的 HTML 等于把整个产品换成 drawio 套壳**,偏离 media-gen-mcp 定位。
- **共同软肋**:浏览器沙箱不让 JS 自写磁盘,所有"保存"都只能 localStorage / IndexedDB(不入 git,破立场 ③)或"下载新 HTML"按钮(用户得手动覆盖原文件,UX 等同重生成)。

**立场契合度**:B1 部分守(只标签);B2 守 ① 但破 ③(持久化);B3 全破。

**结论:范式 B 整体 ROI 极差,不推荐。** 详见 §6。

---

### 2.C AI 自然语言微调(MCP + Claude 的杀手锏)★ 推荐

**流程**:用户对 Claude 说"把支付服务移到右下" / "加个 redis 缓存在订单和 db 之间" → Claude 改 D2 DSL → `generate_interactive_diagram` 重生成 → 新 HTML。

**技术实现**:**几乎为零**。所需能力全部已具备:
- Claude 已能读写 D2 DSL(D2 是文本,语法简单);
- `generate_interactive_diagram` 已能 DSL → HTML;
- 只缺一条**工作流约定**:把上次的 DSL + 上次的 HTML 路径钉在对话上下文(或落盘一份 `.d2` 源文件随 HTML 一起出),用户说"改 xxx"时 Claude 读旧 DSL → patch → 重渲染。

**UX 优劣**:
- ✅ **零额外编辑器代码**(复用 Claude 能力,这是 MCP 的原生打法)。
- ✅ 用户说人话,不用学 DSL 语法、不用在两个表示系之间切换。
- ✅ 同输入同输出可入 git(每次 Claude 改完 DSL,DSL 本身就是 source of truth,入 git;HTML 是 derived)。
- ✅ 单文件自包含不破(产物还是同一个 HTML 形态)。
- ✅ 向后兼容(不改现有工具契约,inputSchema 零 diff)。
- ✅ 大改小改都能做:"改标签"="改个字符串";"挪节点"="加 `direction` / `near` 约束";"加节点"="加一行 DSL";"换布局"="改 `direction: right`"。
- ❌ **需要 Claude 在环**(无 Claude 时退化为范式 A)。这与 MCP 定位一致:MCP 工具就是给 LLM 用的。
- ❌ "绝对像素位置"类纯视觉微调仍做不了(但 D2 本来就不鼓励,见 §2.B 末)。

**立场契合度**:① ② ③ ④ ⑤ 全守,**且真正解决用户核心诉求**。

**为何这是 MCP 场景最优解**:MCP 工具的差异化不在"我有一个编辑器",而在"我有一个能听懂话的 LLM 在前面"。自研拖拽编辑器是在和 drawio / tldraw 正面竞争红海;AI 对话微调是 drawio **做不到**的(drawio 没有 LLM 在前)。**复用 Claude 能力 = 零成本差异化**。

## 3. 混合范式设计(视觉选择 + 对话修改)★ 强推荐(C + 轻量视觉增强)

**动机**:纯范式 C 有个摩擦点 —— 用户得用语言指代"哪个节点"。"用户点了 X,想改它"比"把 ID 是 api 的节点改一下"自然得多。

**设计**:在 viewer 里给节点加 click 监听 → 读外层 `<g>` 的 base64 class → 解码出节点 ID → 把"用户点了 X"塞进对话上下文 → Claude 改 DSL → 重生成。**视觉选择 + 对话修改,零拖拽**。

### 3.1 实现骨架(viewer-min.ts 增量,~30-50 行 JS)

```js
// 增量,不替换现有 viewer。挂在 stage 上(事件委托,避免给每个节点绑)。
stage.addEventListener('click', function(e){
  // 1. 忽略 toolbar 上的点击(已有 .closest('.mgm-actions') 模式)
  if (e.target.closest('.mgm-actions')) return;
  // 2. 找最近的外层 <g class="BASE64-ID">(节点或边的包装层)
  var g = e.target.closest('#mgm-stage svg > g[class]');
  if (!g) return;
  var raw = g.getAttribute('class').trim().split(/\s+/)[0];
  // 3. base64 URL decode → DSL 节点 ID(如 "client"、"(api -> cache)[0]")
  var id;
  try { id = decodeURIComponent(escape(atob(raw.replace(/-/g,'+').replace(/_/g,'/')))); }
  catch(err){ return; }  // 不是节点(可能是 mask/legend),静默忽略
  // 4. 把选中的节点 ID 暴露给宿主(三种通道,按场景选):
  //    a) URL hash:location.hash = '#sel=' + encodeURIComponent(id)  —— GitHub README iframe 里也能读
  //    b) window.postMessage({'mgmSelect': id}, '*')                  —— 嵌入页可收
  //    c) 可视反馈:g.classList.add('mgm-selected') + tooltip "已选中:client,回 Claude 说怎么改"
  g.classList.add('mgm-selected');
  showSelectionChip(id);  // 小浮层:"已选 client。回对话窗口说:把它改成 ..."
});
```

CSS 增量(`animations.ts` 或 `theme.ts` 末尾,~10 行):
```css
g.mgm-selected > .shape { filter: drop-shadow(0 0 8px var(--mgm-accent)); }
.mgm-sel-chip { position: fixed; bottom: 12px; left: 50%; transform: translateX(-50%);
  background: var(--mgm-toolbar-bg); border: 1px solid var(--mgm-accent);
  border-radius: 999px; padding: 6px 14px; font-size: 0.85rem; }
```

### 3.2 三个通道的取舍(守立场 ⑤ GitHub README 嵌入)

| 通道 | GitHub README 里能用? | 单文件自包含? | 入 git? |
|---|---|---|---|
| a) `location.hash` | ✅(iframe 内 hash 可读) | ✅ | ✅(可复制粘贴给 Claude) |
| b) `postMessage` | ❌(README iframe sandbox 通常拦) | ✅ | ❌(运行时事件) |
| c) 仅可视反馈 + 用户口述 | ✅ | ✅ | ✅(用户肉眼读节点名) |

**推荐组合**:**c(默认,零依赖)+ a(增强,GitHub 友好)**。b 留给嵌入页场景(非 README)。

**关键**:这个增强**不破任何契约** —— S2(无外链 `<script src=`)守:JS 还是 inline;S4 双调色板守;S6 体积守(+~1KB);S9 motion governor 守(只是加了个 class);新增的只是 click 事件和可视反馈。**inputSchema 零 diff**(立场 ④)。

### 3.3 用户实际工作流(目标态)

1. 用户:`generate_interactive_diagram` 出图(当前能力,零改)。
2. **同时落盘 `.d2` 源文件**(微调入口,~5 行 handler 改动;或 Claude 直接从对话历史拿上次 DSL)。
3. 用户在浏览器看图,click 某节点 → 浮"已选 client"。
4. 用户回 Claude:"把这个移到右下"(指代清晰:Claude 上下文里已有"用户刚点了 client")。
5. Claude 改 DSL(`client: { ... }; client.near: gateway` 或调 `direction`)→ 重生成 → 新 HTML。
6. 循环 3-5 直到满意。**全程零拖拽、零编辑器、零持久化难题**。

## 5. ROI:混合范式 vs 自研拖拽编辑器

| 维度 | 混合范式(C+) | 自研拖拽编辑器(B2/B3) |
|---|---|---|
| 用户核心诉求("挪节点 / 改标签 / 加节点") | ✅ 全覆盖(通过对话) | ✅ 拖位置 / ❌ 加节点仍要 DSL |
| 与 D2 auto-layout 兼容 | ✅(Claude 生成 D2 布局约束) | ❌(拖拽 vs 自动布局根本冲突) |
| 单文件自包含(立场 ①) | ✅ | B3 ❌(React runtime);B2 ✅ |
| 可入 git(立场 ③) | ✅(DSL 是 source of truth) | ❌(拖拽位置不入 DSL 除非逆向编译) |
| GitHub README 嵌入(立场 ⑤) | ✅ | ❌(编辑器要后端 / iframe sandbox 拦 postMessage) |
| 复用 Claude 能力(MCP 原生) | ✅ 100% | 0%(在重造 drawio) |
| 差异化 vs drawio/tldraw | ✅(它们没 LLM 在前) | ❌(正面对位,且更差) |
| 实现成本 | **0.5 人日** | 5+ 人日 |
| 维护成本 | 低(改 viewer ~50 行) | 高(编辑器长期演进) |

**ROI 判决**:混合范式用 0.5 人日拿到 90% 用户价值;自研拖拽用 5+ 人日拿到 60% 用户价值且破 3 条立场。**10× 差距,方向明确**。

## 6. 推荐 + 落地路径

### 推荐:**范式 C+ 视觉选择(混合),归入 P0-5B cleanup PR。**

### 落地路径(三档,按优先级)

**P0(必做,0.2 人日)** —— "AI 对话微调"工作流约定:
1. `generate_interactive_diagram` handler 在落盘 `.html` 旁同时落盘 `<name>.d2`(把 `req.code` 原样写文件)。用户/ Claude 后续微调时读这个 `.d2` 而不是从对话历史抠。
2. 工具 description 加 NEXT 句:"要微调?告诉我改哪里(如'把 X 移到右下'/'加 redis 在 Y 和 Z 之间'),我改 .d2 重生成本图。" —— 把"对话微调"能力显式化给 LLM。
3. 零 viewer 改动,零 inputSchema diff。

**P1(推荐,0.3 人日,累计 0.5)** —— viewer 视觉选择增强:
1. `viewer-min.ts` 加 click → base64 decode → `location.hash` + 可视 chip(§3.1 骨架)。
2. CSS 加 `.mgm-selected` 高亮 + `.mgm-sel-chip` 浮层。
3. 新增 1 个契约断言(可选):"click 监听已挂"(grep `addEventListener('click'`)。
4. 跑 golden byte-compare:**HTML 字节会变**(新增 JS/CSS),需更新 golden + 重跑 10 次确定性审计(P0-3 已建基建,复用)。

**P2(可选,0.3 人日)** —— hover 详情卡(轻量增强,不是微调):
1. hover 节点 → 浮卡显示节点 ID + 邻居 + DSL 片段(从 base64 class 解码 + 扫同 SVG 内连接此节点的边)。
2. 不与 P1 冲突,可并行。
3. 解决"图大了不知道哪个节点是哪个"的辅助认知,非核心。

## 7. 开放问题

1. **`.d2` 源文件落盘的命名/覆盖策略**:`<name>.d2` 与 `<name>.html` 同目录?用户重生成同名时覆盖(默认)还是版本号?—— 倾向覆盖(DSL 是 source of truth,git 管版本),但需确认与 `resolveOutDir` 既有命名规则不冲突(读 `src/render.ts` 的 `resolveOutDir` / 命名逻辑确认,本次未深入)。
2. **GitHub README 嵌入时 `location.hash` 通道的实测**:GitHub 渲染 HTML 时 iframe sandbox 是否允许读 `location.hash`?需真在 GitHub README 里嵌一个测试图点一下确认(本地不可复现,需线上验)。
3. **多图同 HTML 的 salt 与 click 选择冲突**:`salt` 已防 SVG ID 冲突,但 base64 class 不含 salt(只含节点 ID),多图同页时 click 会同时命中多个 stage —— 需在 click handler 里 `closest('#mgm-stage svg > g[class]')` 限定到当前 stage(骨架已这么做,但仍需多图场景测试)。
4. **边的选择 UX**:节点 click 已通,边(base64 = `(api -> cache)[0]`)同理可解,但边的 `<g>` 命中区是细 path,hit-test 难;是否给边加透明粗 hit 区(`stroke-width: 12; stroke: transparent` 叠在原 path 上)需评估视觉污染。
5. **DSL patch 还是全量重写**:Claude 改 DSL 时,是 patch(保留用户手写注释/样式)还是全量重写?倾向 patch(守立场 ④ 不破坏用户已有 DSL 资产),但 Claude patch DSL 需要稳定行号映射 —— 是否给 DSL 每个节点加 `// <id>` 注释锚点?这是个独立设计题。
6. **P0-5B 的 4 个 R2 medium(F11-F14)是否与本增强冲突**:F11 sentinel 碰撞校验、F12 darkTheme 空白串、F13 契约错归 d2、F14 resvg 前缀 —— 与 click/D2 base64 无交集,但同 PR 落地需排好顺序(建议 P0-5B 先合并 R2 4 medium,本增强 rebase onto it,参考 P0-5 规划 §"推荐落地顺序"的同款 rebase 策略)。
7. **是否需要"对话微调"的显式 MCP 工具**:例如新增 `edit_interactive_diagram({htmlPath, instruction})` 工具,Claude 调用它即"读 HTML 旁的 .d2 → 按指令改 → 重生成"。这会让 LLM 更倾向走这条路(工具化比约定更显眼),但多 1 个工具(21→22)且 handler 要读文件,成本与收益需权衡。**倾向不加**(约定足够,且守 inputSchema 零 diff 立场),列入 P2 候选。
