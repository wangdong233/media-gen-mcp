## 0. 一句话

media-gen-mcp 的抽象栈,从**功能分层**视角看是三层纵向堆叠:**上层是「谁在用」(用户接入层),中层是「能做什么」(业务能力层——三大功能域明确分割:生成 / 理解 / 结构化),底层是「靠什么做」(技术支撑与交付保障层——本地引擎 + 外部服务 + 横切质量)**。一条价值流自上而下穿过三层:用户一句话需求 → 调引擎/服务 → 返回产物 → 落盘交付回用户。点任一功能域 drill 进去看它的业务服务,再 drill 看技术实现,最深 drill 到模块内部。

> **为什么不是 C4 System Context?** 上一版试过把顶层做成 C4 Context(中心系统 + actors + 外部系统 + 价值流)。它讲清了「谁和谁换价值」,但**看不出功能域的分割与分层**——所有能力挤在一个系统黑盒里,边界糊。功能分层图直接把三大功能域作为中层独立 box 拆开,每域界限明确(虚线框 + 独立填色),更贴近行业架构图通行做法(参考:验证平台 / 业务核心层 / 引擎层 / 管理平台 这类纵向分层 + 域内分组)。

## 1. 为什么功能分层是顶层

### 1.1 分层架构 = 最通用的「系统架构图」范式

市面上绝大多数系统架构图都是**纵向分层 + 层内功能域分组**:把系统按关注点切成几条横向带子(band),每条带子是一个职责层,层内再用虚线框把相关模块圈成功能域。它一眼能看出三件事:**系统分几层、每层管什么、功能域边界在哪**。这正是本版 L0 的结构:

| 层 | 颜色 | 职责 | 内含 |
|---|---|---|---|
| **用户接入层** | 浅紫 | 谁 in / 谁 out | Claude Code 用户 · AI 助手 · 开发者(配置服务方) |
| **业务能力层** | 浅蓝 | WHAT——能做什么 | **生成域 ▾ · 理解域 ▾ · 结构化域 ▾**(三大功能域,界限明确分割) |
| **技术支撑与交付保障层** | 浅绿 | HOW——靠什么做 | 本地引擎(D2·Vega·MathJax·Satori)· 外部服务(Agnes·智谱·Flow·tesseract·PaddleX·vLLM)· **交付保障 ▾** |

三个功能域 + 一个横切质量域(交付保障)带 ▾ 可下钻;其余叶子(box)是各域的对外服务名片,drill 进去看背后。

### 1.2 与调研框架的对应

- **arc42 §3(系统黑盒)+ §5(建筑块分层)**:顶层用「谁在用 + 能做什么 + 靠什么做」三段式回答 arc42 的 context + container 两节——上层是 context(谁交互),中下层是 container 分层(建筑块按职责切层)。分层图把这两节压进一张图,比纯 C4 Context 多了「层」的维度。
- **C4 Container(非 Context)**:中层三大功能域 ≈ C4 Container 级(每个域是一个可独立演进的能力容器),比 Context 黑盒细一档,比 Component 粗一档——正好是「功能域界限」该有的粒度。
- **TOGAF/ArchiMate 的 Business + Application + Technology 三层**:用户接入层 ≈ Business actor/role;业务能力层 ≈ Business/Application capability;技术支撑层 ≈ Technology/Implementation。纵向三层与 TOGAF BDAT 的下三段同构。

### 1.3 三种视角的层级关系(调研结论 3、4)

| 视角 | 回答 | 抽象 | 本版对应 |
|---|---|---|---|
| **业务 / 用户接入** | 谁参与 | 技术无关 | **L0 顶层带** |
| **业务能力(功能域)** | WHAT 能做什么 | 技术无关、按域分组 | **L0 中层三大功能域** |
| **用户功能(4+1 Logical)** | 用户能 DO 什么 | 按用户场景分组 | drill 进 L1 的业务服务名片 |
| **技术(Implementation)** | HOW 实现 | provider/引擎/守门 | **L0 底层 + L2/L3** |

关键:**功能分层图把「业务能力」和「技术实现」放进同一张图的不同层**,用层边界把 WHAT 与 HOW 隔开(01 §2.3 what/how 分离)——上两层看不到技术词,底层才出现引擎/provider 名。这比纯业务视角(C4 Context 把技术彻底踢出顶层)多保留了「系统靠什么支撑」的一条带子,也更贴近工程团队日常画的架构图。

## 2. 三大功能域怎么划(L0 中层,调研结论 3)

把 README 全部能力按「业务在做什么」归类,正好落到三根柱,每根柱是一个**功能域**(中层独立 box,虚线框 + drill)。生成域当前接三家渠道:Agnes(默认免费)/智谱(中文 fallback)/Google Flow(本地 Chrome CDP,高质量视频,受 S000 硬门与计费确认门治理,drill `create-tech` → `flow-governance` 可见)。

### 2.1 生成域(WHAT:从无到有产出新内容)
把脑子里的画面变成可见成品。AI 写实照片/插画、AI 短视频、图标/品牌 Logo。解决「要一张图却不想装 N 个工具记 N 套参数」。AI 生成走外部服务,图标走 20 万矢量库即下即用。
→ drill `create`:L1 看生成业务服务 → L2 看外部服务方接入(Agnes/智谱/Flow)→ L3 看三层恢复链与 Flow 渠道治理(S000 硬门 + 计费确认门)。

### 2.2 理解域(WHAT:把图/PDF 反向变成数据)
文字识别(OCR)、表格→HTML、图表反推数据、看图问答/手写/公式、整份 PDF 抠字、能力自检。解决财务/法务/学术/教育「从截图发票合同论文反向抽数据」。
→ drill `understand`:L1 看理解业务服务 → L2 看多档识别服务 + PDF 异步管线 → L3 看后处理铁律。

### 2.3 结构化域(WHAT:把想法/数据组织成可发出去的成品)
架构/流程/数据图(静态·交互·嵌套)、分享卡/二维码/数学公式、高清特效图/动画视频。全本地引擎,免 Key、矢量高清、同输入永远同输出可入 git。
→ drill `structure`:L1 看结构化业务服务 → L2 看本地 WASM 引擎深核 + 确定性叶子渲染器 → L3 看嵌套图/交互图内部。

### 2.4 交付保障(横切质量,非第四根能力柱)
产物自动校验防崩、服务方失败自动切换、同输入永远同输出、计费路径绝不自动提交(确认门)。这是**横切所有功能域的正交质量属性**(01 §2.5 刻度四正交),不是第四根能力柱——所以它独占底层带的一个 drill 入口,而非挤进中层。
→ drill `deliver`:L2 看守门矩阵(三档 severity × 双 profile 决策)。

> README 反复强调的「能入 git、免费层挂了你无感、不会拿到坏图」就是交付保障这块。

## 3. 价值流怎么走(L0 层间箭头)

L0 四根箭头标了「换什么」(arc42 §3 通信伙伴换什么价值):

```
用户接入层 ──一句话需求──▶ 业务能力层 ──调引擎/服务──▶ 技术支撑层
     ◀──落盘交付──          ◀──返回产物──
```

- 用户一句话需求 → 业务能力层(选哪个功能域干活);
- 业务能力层 → 技术支撑层(调本地引擎或外部服务);
- 技术支撑层 → 业务能力层(返回图/视频/数据/卡片产物);
- 业务能力层 → 用户接入层(落盘交付回用户)。

价值流**纵向穿层**,功能域**横向并列**——一纵一横,既是分层又是分域。

## 4. drill 深度与功能域边界

每个功能域 drill 下去的层数按「业务→技术→内部」递进:

| 域 | L1(业务服务) | L2(技术实现) | L3(模块内部) |
|---|---|---|---|
| 生成 | AI 照片/视频/图标名片 | 外部服务方接入(Agnes/智谱/Flow) | 三层恢复链(resolve→retry→fallback)+ Flow 治理(S000/确认门) |
| 理解 | OCR/表格/图表/VQA/PDF 名片 | 多档识别服务 + PDF 异步管线 | 后处理铁律(剔除先于排版) |
| 结构化 | 图/卡/特效名片 | WASM 引擎深核 + 叶子渲染器 | 嵌套图/交互图内部 |
| 交付保障 | — | 守门矩阵 | — |

**功能域界限的「明确分割」体现在三处**:① 中层三大功能域各自独立 box,不共享容器;② 每域 drill 路径独立(L1→L2→L3 不串域);③ 交付保障作为横切质量独立于三大域,不混入任何一根柱。层边界(紫/蓝/绿带子)把「谁/做什么/靠什么」三段切开,域边界(中层三 box)把「能做什么」三切。
