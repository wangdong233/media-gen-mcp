## 二、#1 自动 Fallback — 架构决策

### 为什么放在 Handler 层(而非 Provider 层 / Router 层)?

| 方案 | 否决理由 |
|---|---|
| **Provider 层 fallback** | Provider 之间互相引用 → 循环依赖;且 provider 不该知道"还有谁" |
| **Router 层 fallback** | 仅 2 个 provider,新建路由层是过早抽象;且 router 缺 handler 上下文(warnings/fan-out/download/async hint) |
| **✅ Handler 层 fallback** | Handler 有完整请求上下文(mode/images/keyframes 做能力谈判、size/frames 重吸附、warnings 累积、activeProvider 防 hint 错位)。改动局部、依赖单向 |

### 核心数据流(submit 路径)

```
p.createVideo(req)  ──成功──→  activeProvider=p,走正常 poll/download
        │
      抛错 e
        │
   isFallbackWorthy(e)?  ──NO(业务4xx/配置/校验错)──→  throw e(保留原始错误给用户)
        │ YES(5xx/网络/401/403/429)
        │
   getFallbackProvider(p.name, modality, req)
   ├─ 排除 currentName
   ├─ 过滤 health.configured !== false
   ├─ 过滤 health.cooldown !== true(60s 熔断窗口)
   ├─ 过滤 capableOf(能力矩阵 + mode 推断)
   └─ tier 降序取首个
        │
   fb == undefined?  ──YES(两家都挂/无能力承接)──→  throw e(清晰报错)
        │ NO
        │
   重吸附(fb 自有规则):numFrames→nearestAllowed, frameRate→allowedSet, size→fb.snapImageSize, fbFrames→fb.maxFramesFor clamp
        │
   p.notifyUnavailable(e)  ← primary 进 60s 熔断
        │
   activeProvider = fb
   fb.createVideo(重吸附后的 req)  ──成功──→  走 poll/download(全用 activeProvider)
        │                          ──失败──→  fb.notifyUnavailable(fbErr); throw fbErr
```

### 铁律:Poll 路径绝不 Fallback

`get_video` / `waitVideo` 轮询路径**不 fallback**。原因:任务 ID 是 provider 私有的(Agnes 的 task_id 在 Zhipu 查不到)。一旦 submit 成功(无论原 provider 还是 fb),poll 必须锁定同一个 provider。

- submit 阶段 fallback → `activeProvider = fb`,后续 hint / `provider_used` / `waitVideo` 全用 `activeProvider`
- poll 失败 → 返回 handle(含正确的 `provider_used: activeProvider.name` + `hint: get_video(...)`)供用户复查,**不切换 provider**

## 三、#2 接口扩展(全 optional,零破坏)

```typescript
// src/providers/types.ts
export interface MediaProvider extends ImageProvider, VideoProvider {
  capabilities?(): ProviderCapabilities;   // 能力矩阵(fallback 谈判基础)
  health?(): ProviderHealth;               // { configured, cooldown, lastErrorAt }
  tier?(): number;                         // 优先级(大优先;agnes=10, zhipu=5)
  notifyUnavailable?(e: any): void;        // fallback 失败回调 → 设 60s cooldown + lastErrorAt
}

export interface ImageProvider {
  snapImageSize?(size: string): string;   // 按 provider 自有规则吸附(封装,去 handler 硬编码)
}
```

未实现这些方法的 provider → 保守默认(不承接 fallback)。**已有 provider 零改动即可继续工作。**

### 能力矩阵(两家自洽,与 supportsImageToImage/createVideo 行为一致)

| | textToImage | imageToImage | textToVideo | imageToVideo | keyframes | tier |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| **agnes** | ✅ | ✅ | ✅ | ✅ | ✅ | 10 |
| **zhipu** | ✅ | ❌ | ✅ | ✅ | ❌ | 5 |

**能力矩阵拦截**:agnes 挂 + 用户请求图生图 → zhipu 不支持 i2i → **无 fallback,清晰报错**(免静默丢图)。

| 4 | MEDIUM | `capableOf` video 推断忽略 image → 未来 t2v-only provider 会咬 i2v fallback | 推断加 `image` 字段,与 createVideo 内部一致 |

| 7 | LOW | `isFallbackWorthy` s=0 太宽,配置/校验错误触发 fallback + 60s 熔断 | 无 `.status` 仅认 `TypeError` |

## 六、#3 图像编辑 API 调研结论(延期)

**结论**:Agnes 与 Zhipu **均无免费图像编辑 API**。

| 厂商 | 图像能力 | 编辑能力 | 免费? |
|---|---|---|---|
| Agnes | 文生图 + 图生图(body.image) | ❌ 无独立编辑端点 | ✅ |
| Zhipu | cogview 文生图(纯) | ❌ 无编辑 | ✅ |
| SiliconFlow | Qwen-Image-Edit | ✅ | ❌ 付费 |
| Fal | FLUX Kontext | ✅ | ❌ 付费/自托管 |

**延期触发条件**:未来接入 SiliconFlow / Fal 等含编辑能力的 provider 时,顺势实现 `edit_image` 工具。当前维持纯免费 → 不做。

## 七、已知边界(设计约束,非 bug)

1. **配置错不 fallback**:`AGNES_API_KEY 未设置` / `image model 未配置` 等(无 `.status`)不触发 fallback——配置问题不会在 60s 内自愈,fallback 只会掩盖。用户直接看到原始配置错误。
2. **业务 4xx 不 fallback**:400/404/422 等(参数错/资源不存在)不 fallback——换一家同样会失败。
3. **两家都挂时清晰报错**:`getFallbackProvider` 返回 undefined → 抛原始错误 + fallback 路径诊断(warnings.slice + 首例错误)。
4. **Cooldown 仅影响 fallback 候选筛选**:primary 被 notifyUnavailable 后,60s 内不再被选为别人的 fallback 候选;但 primary 自身的直接调用仍会尝试(免得一家瞬时抖动就完全不可用)。这是有意为之。
5. **`(免费)` 文案**:fallback warning 硬编码"(免费)"——当前两家均免费,文案准确。未来若引入付费 fallback 候选需改为 provider 自报 `freeTier()`。
