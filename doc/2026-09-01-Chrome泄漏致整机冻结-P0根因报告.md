> **方法**：主 loop 白盒 scout + 8-agent 隔离对抗工作流（4 路隔离勘查 × 3 路红队否定反查 × 综合归因），全部结论带命令级证据
> **状态**：✅ 已止血（Load 680→2.5，机器复活）｜✅ **根治已实施（2026-09-01，§8.1+§8.2 → `src/browser-pool.ts` + `test/browser-pool.test.ts`）**｜⏳ 看门狗（§8.3）另行落地中

## 1. 事件概述

08-31 至 09-01 下午，本机（MacBookPro11,4，4核8线程/16GB）逐渐卡死。09-01 19:04 实测：**Load 137/593/680**（1/5/15min，85 倍过载）、swap 5.8G/7G 打满、CPU idle 仅 9%（sys 高达 39%）、**1145 进程/11499 线程/285 个同时 RUN**——连诊断命令本身都跑 2 分钟超时。

根因：**media-gen-mcp 渲染管线泄漏的 83 个 puppeteer 无头 Chrome 孤儿舰队**（+415 Helper +89 crashpad = 599 个 Chrome 族进程），烧掉 2.7-4.9 核 CPU 与 18.8GB 合计 RSS，击穿 16GB 物理内存引发 swap 风暴与内核 VM 饥荒。

## 3. 根因定性（代码级）

**泄漏点**：`src/render-svg.ts`（同模式 `export-png.ts` / `render-video.ts`）

- **L118 / L133**：每次渲染调用 `puppeteer.default.launch()` 一个**全新** headless Chrome（`--headless=new` + `about:blank` + `--remote-debugging-port=0` + `$TMPDIR/puppeteer_dev_chrome_profile-XXXXXX` + L85 `DETERMINISTIC_FLAGS` 八个旗标）
- **L80**：`const BROWSER_IDLE_MS = 30 * 1000; // 独立脚本渲染后最长 30s 释放 Chrome`——设计上靠空闲定时器关停
- **失效机制**：spawner（MCP server 进程）先被 **SIGKILL**（CC 会话结束/长渲染序列中断）→ 30s 定时器随宿主进程消亡 → **清理路径永不执行** → Chrome reparent 到 launchd（PPID=1）成为真孤儿

**定罪证据（指纹级）**：83/83 个孤儿的命令行尾部与 `render-svg.ts:83-92` 的 `DETERMINISTIC_FLAGS` **逐字且同序完全一致**（`grep -c` = 83/83）。反证穷尽：lasso 零进程、playwright 零进程、chrome-devtools-mcp 未安装（`~/.npm/_npx` 仅 1 个无关包）。

**泄漏节奏**：两天 83 发——08-31 共 24 发（13/15/19 时段），09-01 共 59 发（13:00-16:30 **平均每 3.7 分钟 1 发**，16:30 后停喷）。Chrome 150 来自系统 `/Applications`（puppeteer 默认 executablePath）。

## 4. 完整因果链（每环实测数字）

```
[源头·代码缺陷] render 三文件每次调用 launch 新 Chrome（不单例、无退出钩子）
      ↓
[泄漏机制] spawner 被 SIGKILL → BROWSER_IDLE_MS 定时器随宿主消亡 → 永不清理
      ↓
[累积·两天83发] 83 孤儿主进程 + 415 Helper（每族恰 5 个）+ 89 crashpad = 599 进程
      ↓
[资源吞噬] 舰队 CPU 2.7-4.9核（ps 衰减均值 489% / top 瞬时 267%，进程侧占比 76.1%）
           + 合计 RSS 18.8GB（全机内存需求 66.6%，20.4GB > 16GB 物理）
      ↓
[内存击穿] free 仅 60-146MB → compressor 塞 18.4GB（压进 2.71GB）
           + swap 打到 6.8G/8G（87% 近满）+ 换页风暴 11-54MB/s（5天累计≈620GB 换页流量）
      ↓
[内核饥荒] 内核 VM（换页/压缩/缺页服务）烧掉 sys 37.8%×800% ≈ 300 CPU 点（实际消耗的 51%）
      ↓
[表症] 全机 busy 86.5-90.2%，RUN 队列 285（85个为 Chrome 渲染器）
       → Load 137→680，一切交互排队卡死
[附带伤害] 83 条 ClashX 7890 僵死 ESTABLISHED 连接；tmp 积 114 个 profile 目录共 7.2GB
```

## 6. new-api usage-logs 慢的专项结论

- **DB 引擎无罪**：logs 表 180,923 行、15 个索引全走 SEARCH，30 天窗 GROUP BY 真库实测 0.086-0.135s；`/api/log/self` 列表带鉴权 36-41ms
- **慢在 stat 冷路径**：`/api/log/self/stat`（usage-logs 页面的统计端点）冷调用内禀 2.8-3.1s——机制 = SQLite `journal_mode=delete`（实测 PRAGMA，**非 WAL**）+ grpcfuse 挂载 68x 内禀惩罚（VM 页缓存一冷就要经通道读 ~55MB）
- **风暴期再放大 76 倍**（grpcfuse 被饿到 728kB/s）
- **对系统级 Load 贡献 <2%**（容器生命周期均值 ~9.4% 单核）

## 8. 防复发方案（1/2 已实施；3 另行落地；4/5 待办）

1. ✅ **根治泄漏源头（改单例，已实施 2026-09-01）**：新增 `src/browser-pool.ts` 进程级全局单例池，`render-svg.ts` / `export-png.ts` / `render-video.ts` 三处全部收敛接入——首次启动、后续复用（单飞锁防并发重复 launch）、**引用计数**（渲染进行中绝不空闲回收）、空闲 5 分钟（env `MEDIA_GEN_BROWSER_IDLE_MS` 可调）自动 close + 删 profile 目录。单元测试 `test/browser-pool.test.ts`（12 测）
2. ✅ **堵死 SIGKILL 孤儿路径（已实施 2026-09-01）**：(a) launch 成功即登记进程级 `liveForExit` Set，`process.on('exit')` **同步** best-effort 清理（SIGKILL Chrome 主进程 + `rmSync` profile，钩子内零 await），SIGTERM/SIGINT 异步 close 后退出（`MEDIA_GEN_NO_SIGNAL_HANDLERS=1` 可禁用，沿用旧开关）；(b) 渲染调用一律 `withBrowser`/acquire+release（try/finally 保证异常路径归还）；(c) launch 显式 `handleSIGTERM:true / handleSIGHUP:true / handleSIGINT:true` + `timeout:30s` 防挂死；close 失败兜底同步 SIGKILL。SIGKILL 宿主本身无解 → 由 3 看门狗兜底
3. ⏳ **看门狗兜底**：LaunchAgent 每 10-15min 清理存活超 10 分钟的孤儿 + 陈年目录；告警条件：Chrome 主进程 >10 或 swap used >4GB（落地中：`scripts/render-watchdog.mjs` + `src/render-selfcheck.ts` 渲染侧自省）
4. **new-api 两步**：(a) 平静期把 `/data/one-api.db` 迁 `journal_mode=WAL + busy_timeout`（🔴红线：内存耗尽时改 WAL 必坏 DB，有前科——只在机器健康时做）；(b) 把 /data 从 grpcfuse bind 挂载挪进 Docker named volume（消灭 68x 惩罚）
5. **MCP 浏览器生命周期通则**：凡 MCP launch 浏览器必须三件套——单例复用 + 退出钩子 + 固定可识别 user-data-dir 前缀（lasso 的 CDP attach 设计本来就对，保持）

**profile 前缀更名通告（根治实施同步变更）**：根治后 render 管线 Chrome 的 user-data-dir 从 puppeteer 默认临时名改为**固定前缀 `media-gen-mcp-render-<pid>-XXXXXX`**（`$TMPDIR` 下，由 browser-pool 显式传入）——归属一目了然，永不与其他 puppeteer 使用方混淆；`DETERMINISTIC_FLAGS` 八旗标逐字保留（确定性承诺不回归）。§9 自救命令已同步双前缀。

## 9. 附录

**复发时自救（已验证零误伤；2026-09-01 根治后双前缀——新代码 `media-gen-mcp-render`，旧残留 `puppeteer_dev_chrome_profile`）**：

**方法论沉淀**：浏览器泄漏归因必须靠**启动参数指纹逐字匹配**，不能按"谁在用浏览器"猜（lasso 曾被冤枉）；`ps %CPU` 是生命周期均值非瞬时值（本次两个 agent 都踩）；Load 包含不可中断 I/O 等待者，高 Load ≠ CPU 饱和，先看 `top` 瞬时 idle 与 RUN 队列构成。
