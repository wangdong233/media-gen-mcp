## 0. 执行摘要(先给结论)

**总裁定:GO(有条件)**。

1. **「能不能直接融合进去使用?」——能,且大多零/低改造**:NodeTool 对 MCP 是**原生双向支持**(stdio 挂入即 27 工具自动进画布 agent toolbelt,零改造);n8n/Langflow/Flowise 经一条命令的 HTTP 桥(supergateway/mcpo)即通;ComfyUI 反向消费需自建一个小 custom node(或经 mcpo REST 网关零代码)。唯一的前置补课=给 media-gen-mcp 加 Streamable HTTP 传输面(2-4 天,顺带解决多路并发)。
2. **「作为基底构建到这种软件中?」——方向修正**:不建议把画布塞进 MCP(范式相反);正确分工=**画布底座管编排+叙事数据 / media-gen-mcp 管渠道执行(API 渠道聚合引擎)/ ComfyUI 管本地 GPU 执行**。
3. **底座格局(27+ 候选四通道发现)**:开源事实标准=ComfyUI(13.5 万★,但作底座 4.5/10、作执行后端 9/10);**唯一带原生 MCP+导演台语义包(timeline/storyboard)的活跃开源底座=NodeTool(TS 重写,AGPL 传染是产品化红线)**;Flowy 已消失/Vibe-Workflow 引擎闭源/Diffusion Studio 停更+商用收费——种子候选大半被证伪,发现的新活口:SwarmUI/TongFlow/Velorn/Inline Studio(本地 H3)。
4. **多 Agent 隔离并发(白盒终论)**:media-gen-mcp 三层状态模型(进程内存/跨进程文件/账号级外部态)——进程级竞态全部在文档化可接受窗口内;真正需全局仲裁的只有**账号级配额挤兑(HF ZeroGPU/pixverse 积分)与 gemini 单会话串行**,两者恰好都该建在画布调度层(唯一能看到全局的位置);ComfyUI 单 worker 串行队列与 MCP stdio 单管道在「画布统一驱动」架构下从缺陷变特性。**融合不仅不恶化并发,反而把调度责任上收到正确层**。
5. **推荐两阶段**:阶段一零成本验证(supergateway→n8n 全链路 / NodeTool 本地体验 / 官方 Comfy MCP);阶段二按定位分叉——自用→NodeTool 魔改最快;产品化([[director-stage-project]])→自研壳+双引擎(media-gen-mcp+ComfyUI),护城河投入顺序=分镜数据模型>确定性重跑>一致性资产库>模型聚合(最后一项已持有)。

## 1. 需求定义(用户主诉求解构)

- **画布**:节点图(ComfyUI 型)或无限画布(Flora/Krea 型)——两种形态,取舍见 §3
- **AIGC 管线管理**:任务编排、复运行、缓存复用、确定性重跑(改一镜只重渲一镜)
- **导演台**:分镜→镜头→角色一致性→运镜→剪辑→成片的叙事级工作区(LTX Studio 型)
- **最新模型能力**:Wan2.2 / MiniMax-H3 / Seedance / Veo3.1 世代
- **本项目作为基底?**:media-gen-mcp 已有=渠道聚合(生成+识别)、确定性本地渲染(d2/vega/satori/card/render_video)、计费确认门、fallback、白名单路由;未有=画布 UI、管线 DAG 执行器、叙事数据模型

## 3. 开源白盒深析

### 3.1 ComfyUI(调研 agent:wb-comfyui,已回收;zread 快照+官方文档核验)

**架构文字图**:
```
外部驱动面(无 UI 可用)
  HTTP: POST /prompt(提交即校验) GET /queue /history /object_info /view
        POST /interrupt(支持定向 prompt_id) /free /queue
  WS:   /ws?clientId=xx → status/executing/executed/progress/execution_error/execution_cached
        ↓ aiohttp(server.py)
PromptQueue(execution.py:1198,heapq+RLock+Condition,front:true 负数插队)
        ↓ 🔴 唯一 daemon worker 线程(main.py prompt_worker)——prompt 级 FIFO 串行
PromptExecutor.execute → 每 prompt 一个事件循环 → 拓扑序逐节点
  缓存: HierarchicalCache(键=输入签名,跨 prompt 复用)/LRU/RAM压力/None
节点层: nodes.py + comfy_extras/ + custom_nodes/ + comfy_api_nodes/(云 API ~35 家)
前端: Comfy-Org/ComfyUI_frontend(Vue3+litegraph→Nodes2.0,GPL-3.0-only)
```

**并发模型(多 Agent 分析核心)**:
- 🔴 **单 worker、prompt 级串行**:多 Agent 并发提交=安全排队 FIFO,不并行(currently_running 恒 1);无「请求锁」概念——消费端天生单线程;真并行只能多进程多实例(官方 --port/--cuda-device/--database-url 分离)
- 提交侧并发安全:PromptQueue RLock+Condition;/prompt 即 validate_prompt 错误 400 带 node_errors(agent 友好)
- **异步节点可重叠**:云 API 节点 return PENDING 后台化(execution.py:546-553),与后续无关节点并行——「GPU 空转等云」已缓解
- **缓存=确定性重跑的现成机制**:输入签名键,未变子图直接命中并发 execution_cached 事件——导演台「改一镜只重渲该镜」在引擎层免费获得

**视频模型原生支持**:`comfy_extras/nodes_wan.py`(1541 行 20+ 节点:WanImageToVideo/**WanFirstLastFrameToVideo 首尾帧**/WanCameraImageToVideo 运镜)+ vae2_2.py(Wan2.2 VAE);Wan2.7 走 Partner Node;LTX-2(lightricks/ 三件套);HunyuanVideo/Cosmos/Mochi;**MiniMax H3=云端 API 节点族(comfy_api_nodes/nodes_minimax.py,H3/H3 Max/Turbo 免 GPU)——主仓 core 无本地 H3 推理代码**。

**API 面**:完全 headless 可驱动(官方 basic_api_example.py 纯 urllib);双格式(API 扁平格式 vs UI 画布 JSON,后端只认 API 格式);WS 事件按 client_id 定向推送(**多 Agent 各持 clientId 可分流事件**);/object_info 全量节点元数据发现。

**许可证(GPL 边界四条,产品化关键)**:主仓+前端均 GPL-3.0;①**独立进程+HTTP/WS API 调用不构成衍生作品→自研导演台客户端闭源可行**;②fork/嵌入再分发→整体 GPL;③GPL(非 AGPL)网络服务化不分发二进制无开源义务;④custom_nodes 独立程序各自选 license。

**MCP 生态**:官方 Comfy MCP 已存在(图/视/音/3D 生成+搜模型+跑 workflow,LLM→ComfyUI 方向已被验证且官方下场);反向(节点调外部)核心无通用 HTTP 节点(刻意留白)但 custom node 10 行可发请求,异步节点后台轮询不阻塞队列。

**导演台能力差距**:画布=数据流执行图非叙事工具。可复用积木:**SubgraphManager(子图=可复用镜头模板)+ 动态子图展开(execution.py:567-601,一个节点运行时生成整段子图=「镜头数参数化」的现成钩子)**+ OUTPUT_IS_LIST 批处理 + ~40 个 blueprints 模板;缺:镜头级状态管理/时码/多版本对比/资产一致性追踪——全要导演台自建。

**双路评分**:路线 A 作为底座(fork/嵌入)**4.5/10 不推荐**(双 GPL+前端重栈+画布范式与叙事范式错位);路线 B 作为执行后端(HTTP/WS/MCP 驱动)**9/10 强烈推荐**(API 完整+缓存免费确定性重跑+35 家云节点+进程隔离绕 GPL)。

### 5.1 宿主侧 MCP 消费现状

| 宿主 | 消费方式 | 传输 | 工具→节点映射 | 成熟度/坑 |
|---|---|---|---|---|
| **n8n** | MCP Client Tool(子节点)+ 独立 **MCP Client 核心节点**(可作普通工作流步骤) | 官方**仅 SSE+Streamable HTTP,不支持 stdio**(社区节点补 stdio) | 独立节点**自动拉取 tools/list**,一节点选一工具;含 Convert to Binary(图像/音频转二进制)+Timeout 参数 | 对生图/生视频 server 是**现成消费面** |

| **Langflow** | MCP Tools 组件 | **stdio/SSE/Streamable HTTP 三种全支持**(1.7 版) | 动态发现+勾选 | 画布里传输覆盖最全 |

| **LangGraph** | langchain-mcp-adapters(3658★)代码层注入 | stdio+HTTP 全支持 | 代码定义无画布拖拽 | 代码优先 |

**ComfyUI↔MCP 桥**:生态**几乎全是 LLM→ComfyUI 方向**(官方 comfy.org/mcp 云端+本地 comfy-mcp,含「agent 花积分前向用户确认」——与我们的 confirm-token 同构问题的官方解法;artokun/comfyui-mcp 762★ 活跃);**反向(ComfyUI 节点内消费 MCP)无成熟通用项目**——若底座选 ComfyUI,需自建 Python custom node 内嵌 MCP client。

### 5.2 MCP 规范并发语义(与本报告 §6 直接咬合)

- **stdio**:client 把 server 作子进程启动,一条管道=一个 client(spec 设计上一进程服务一 client);**并行分支共用一个 stdio 子进程会串行排队**
- **Streamable HTTP**(spec 2025-06-18):server 独立进程**可同时服务多 client**;单 endpoint POST+可选 SSE 流;可选 Mcp-Session-Id;**可恢复流**;天然支持并发多路复用;TS SDK 有 `statelessMode` 可水平并发

### 5.3 四种落地模式对比

| 模式 | 代表 | 改造成本 | 实时性 | 维护面 |
|---|---|---|---|---|
| a. 宿主内嵌 MCP client 节点 | n8n/Flowise/Langflow | 宿主已建好,**server 侧零改造**(须先解决传输) | 好 | 低;受宿主节点能力上限 |
| b. stdio 包一层 HTTP | supergateway(2864★)/mcp-proxy(2766★) | **一条命令零代码** | 好(并发经单管道串行) | 极低;鉴权自加 |
| c. MCP→REST/OpenAPI 网关 | **mcpo(4385★)**:tools/list 自动生成 REST 端点+OpenAPI+Swagger UI | 一条命令 | 好 | 低;覆盖一切有 HTTP Request 节点的软件(含 ComfyUI 的 HTTP 节点) |
| d. CLI 直调 spawn | — | 需 bin 入口 | 差(冷启动每次重付) | 低频场景 |

### 5.4 八个坑(融合设计约束)

1. stdio 在浏览器/Electron renderer 无法 spawn——必须后端进程;2. n8n 官方节点拒收 stdio(Docker 不能起任意进程);3. **两段式 confirm-token 在 DAG 的表达 = 节点对**(调用节点输出 {needConfirm, estimatedCost, confirmToken},确认节点以 token 为入参复调;token 10min TTL→工作流排队延迟会作废需重取;官方 Comfy MCP 的积分确认证明此问题在生图场景是**标配而非特例**);4. **工具描述的 LLM 触发语义(WHEN/AVOID/NEXT)在确定性画布里无用——inputSchema 才是画布侧的真正接口**(27 工具长描述变 tooltip 死重);5. 长任务须 submit/poll 节点对(我们已有的 handle 异步模式恰好匹配);6. 并发需 Streamable HTTP(statelessMode)非 stdio;7. 产物回传:REST 路径 base64 JSON 视频体积爆炸→需产物 URL 化/文件服务;8. 密钥留 server 侧,outDir 绝对路径依赖宿主环境一致。

### 5.5 推荐落地路径(对本项目 27 工具 Node stdio server)

- **路径 1(~0.5-1 天,零改动验证)**:supergateway/mcp-proxy 包成 Streamable HTTP+反代 Bearer → 立即被 n8n(独立节点)/Flowise/Langflow 原生消费;若愿改 server:原生加 `StreamableHTTPServerTransport`(TS SDK statelessMode,~2-4 天含测试)长期更干净
- **路径 2(1-2 天,广覆盖)**:mcpo 起 REST+OpenAPI 网关 → 覆盖非 MCP 原生画布(任意 HTTP Request 节点软件/自研画布/ComfyUI HTTP 节点);需补产物 URL 化
- **路径 3(1-2 周,产品化)**:薄适配层自有网关,把 27 工具收敛为**三类画布节点语义**(同步工具表单[inputschema 驱动]/异步 submit-poll 对/确认对),负责 token 生命周期+产物 URL 化+密钥托管——对接自研导演台的终极形态

## 6. media-gen-mcp 白盒:状态三层模型与多 Agent 隔离并发深析(作者亲析)

> 本章基于源码逐文件核验(证据=文件:行号)。结论先行:**本项目当前架构是「单用户本地单会话」威胁模型;多 Agent 并发=多进程 spawn,三层状态各有不同的隔离语义与竞态面**。

### 6.1 会话与传输层

- `src/index.ts:16` StdioServerTransport —— **一进程一 client**(MCP stdio 规范)。多 Agent 并发的天然形态 = 每 Agent spawn 一个 server 进程(CC 即此形态:N 个 CC 会话 = N 个进程)。
- 无 HTTP/SSE/streamable-HTTP 传输:画布类宿主(浏览器/Electron 前端直连)无法直接消费,须经后端代理或包装层(§5 路径)。

### 6.2 状态三层模型(隔离分析的核心框架)

| 层 | 状态 | 位置 | 多进程(N Agent)语义 | 竞态/风险 | 证据 |
|---|---|---|---|---|---|
| **L1 进程内存** | cooldownUntil(60s 软熔断)/lastErrorAt | provider 实例字段 | N 进程=**互不可见**,熔断只护本进程 | 失效渠道被 N 进程各打一次才各自熔断(放大 N 倍失败流量) | `agnes.ts:148,153`;`hfspaces.ts:185-189` |
| L1 | rateLimits(agnes,TTL 默认 7 天) | 实例内 Record | **限速计数被进程数稀释**(N 进程=N×配额) | 上游 429 风险放大 | `agnes.ts:95,108`;`config.ts rateLimitTtlMs` |
| L1 | dynamicCatalog 缓存(flow 10min)/confirmSecretCache | 实例内 | 只读缓存,各持一份无害 | 无 | `flow.ts` |
| **L2 跨进程文件**(~/.media-gen-mcp/,原子 tmp+rename) | *-confirm-secret(安装级密钥) | 文件 0600 | **刻意共享**:跨进程令牌可验证(2026-08-31 事故修复) | 无(同值) | `flow.ts:103`;`pixverse.ts:89` |
| L2 | *-confirm-consumed(单次消费表) | 内存 Map+文件双写;读时合并、写时并集 | 阻断**顺序**跨进程重放 | 🔴 **并发首消费毫秒级 TOCTOU**(已文档化诚实边界;多 Agent 高并发放大窗口,但重放需同 digest 同参数,后果=多扣一次积分) | `flow.ts:878-893` 注释块原文 |
| L2 | flow-project.json v2(scope→pid 映射) | 文件;**合并写**(重读盘取最新 map) | 防多场景互抹 | read-merge-write 本身有丢失更新窗(两进程同窗写不同 scope,后者覆盖前者的新键);窗口窄+键幂等,低危 | `flow.ts:1240-1255` |
| L2 | pixverse-cost-ledger | 文件;read-modify-原子替换 | entries 按 key 幂等 | 并发丢更新只影响观测值新鲜度(best-effort,失败不阻断) | `pixverse.ts:947-960` |
| **L3 外部账号级**(进程/文件隔离均无效) | HF ZeroGPU 配额(账号/IP,免费 5min GPU/天) | HF 侧 | **天然不可隔离**,N Agent 抢同一池 | 配额枯竭互相挤兑;data:null 拒绝 | `hfspaces.ts:194-195` |
| L3 | pixverse 订阅积分 / cloudflare neurons / siliconflow 余额 | 供应商侧 | 不可隔离;确认门防**单次误耗**,不防多 Agent 各自确认后合力烧干 | 需画布/编排层做全局配额仲裁 | `pixverse.ts` 确认门族 |
| L3 | 渲染浏览器(lasso render 档 attach) | 单实例共享(端口级) | 并发渲染争抢同一 Chrome | P0-29 已证多实例互杀;隔离=三 env 套装或串行 | 项目记忆 P0-28/29 |
| L3 | CDP 单页面渠道(flow 9223 / gemini 9225) | 单浏览器单页 | **结构性串行**:gemini S303 交错守卫拒绝并发第二提交 | 多 Agent 并发点 gemini 必撞 S303(设计如此,防烧配额) | `gemini-web.ts` S303 |

### 6.3 已内置的隔离旋钮(白盒确认,融合时可复用)

1. **`MEDIA_GEN_MCP_CONFIG` env**:每进程独立 config —— 白名单/密钥/策略可 per-Agent 配(测试 fixture 已大量使用该缝,`test/*.test.ts` 头部范式)
2. **flow scope = cwd 末两段**(flowScopeKeyOf):不同工作目录=不同 Flow 项目=资产天然分域(`flow.ts` v2 映射;AIGC 产线已用 `MEDIA_GEN_FLOW_PROJECT_ID` env 钉死通道)
3. **计费确认门两段式**:needConfirm→confirmToken→复调 —— 在编排层等价于「人工/上层审批 checkpoint」,画布可把它建模为节点间闸门
4. **providerStrategy=ordered + enabledProviders 顺序**:per-Agent 差异化渠道路由(0.23.0 新增)
5. **输出域**:默认 outDir=./output(cwd 级),不同 cwd 天然隔离;`name -2/-3` 避让有窄竞态窗(`download.ts:57` existsSync→createWriteStream 窗;同 outDir+同名+同刻双进程才触发,丢失更新形态=数据交错,建议融合时给画布层传唯一 name 或分 outDir)

### 6.4 多 Agent 并发判定矩阵

| 并发场景 | 现架构行为 | 隔离方案 | 融合进画布后 |
|---|---|---|---|
| N Agent 同渠道生图(agnes/zhipu 免费) | 各进程独立限速/熔断 → 失败流量放大 | 每 Agent 独立 config(可各自 key 池);或上层单宿主进程串行化 | 画布执行器天然全局队列 → **反改善** |
| N Agent 抢 HF ZeroGPU | 配额账号级,先到先得,data:null 拒后来者 | 无进程级解;需全局调度(建议:画布 DAG 层按配额预算排任务) | 画布可做配额预算节点 |
| N Agent 各自过确认门烧 pixverse | 各自确认合法 → 合力烧干订阅 | 账号级无解;上限策略(config pixverse.* 限额?)/编排层全局账本 | 画布做全局 credit 预算闸 |
| N Agent 并发首消费同一 confirmToken | 毫秒 TOCTOU 双放行(顺序重放已阻断) | 威胁模型内可接受;彻底封窗=mkdir 锁(文档已判过度设计,多 Agent 场景需重评) | 单宿主进程内 Map 即封窗 |
| N Agent 并发渲染(render_video 等) | 争抢 lasso render 单例 | LASSO_RENDER_PORT+三 env 隔离套装 / 串行 | 画布队列串行化最简 |
| N Agent 并发写 flow-project.json | 合并写防互抹,残余窄丢失更新窗 | per-Agent STATE_DIR 注入(测试缝已有,可产品化) | 单宿主进程消失 |

### 6.5 白盒结论

- **单 Agent 场景(CC 会话)**:现架构威胁模型完全覆盖,零改造。
- **多 Agent 并发(2-5 进程)**:L2 竞态均在文档化可接受范围;真正的痛点在 **L1 限速稀释** 与 **L3 账号级配额挤兑**——两者都不是「加锁」能解的,需要**全局调度者**。
- **关键洞察**:画布软件的 DAG 执行器恰好就是那个全局调度者。**融合不仅不恶化并发,反而把 L1/L3 的调度责任上收到唯一有权看到全局的地方**——这是「MCP 作为引擎、画布作为编排」架构的并发学论据。

| **ComfyUI** | ⚠️ 能但要自建一小块 | 反向消费 MCP 无成熟通用节点(生态全是 LLM→ComfyUI 方向)→ 自写 Python custom node 内嵌 MCP client(10 行起步,异步节点不阻塞队列) | 小(custom node)+可选 mcpo REST 网关替代(0 代码) |

**结论:media-gen-mcp 不需要为「融合」重写——需要的是补一个 Streamable HTTP 传输面**(原生或 supergateway),其余按宿主各有现成通路。当前 stdio 形态对 CC 生态(Claude Code)零改动继续服务。

### 7.3 多 Agent 隔离并发:架构级合成(§6 白盒 × §3 执行器白盒)

四层调度栈,各层职责由白盒证据唯一确定:

```
L3 账号级配额(HF ZeroGPU/pixverse 积分/单页 CDP) ← 唯一全局可见者=画布/编排层
      ↓ 只能在这里做配额预算闸、gemini 串行化(S303 对应排队)
L2 画布执行器(自研壳队列 / NodeTool Runner / ComfyUI 单 worker 队列)
      = 全局调度者:吞 N Agent 并发请求,产出确定性顺序
      ComfyUI:RLock FIFO+异步云节点重叠+输入签名缓存(确定性重跑免费)
L1 MCP server 实例(stdio 每进程一个 / Streamable HTTP statelessMode 多路复用)
      = 渠道聚合+确认门+fallback;L1 内存态(熔断/限速)在单实例下自然全局
L0 产物层(per-cwd outDir+唯一 name;远程画布需产物 URL 化)
```

- **白盒相互印证**:ComfyUI 的单 worker 串行队列与 media-gen-mcp 的 stdio 单管道,在「画布执行器统一驱动」架构下都从缺陷变成特性(天然互斥,无需分布式锁)
- **确认门在调度栈的落点**:confirm-token 两段式=画布节点对(官方 Comfy MCP 同构先例);10min TTL 要求画布确认节点不被长队列饿死(队列超时→自动重取 token)
- **真正的剩余风险**(非架构可解,需运营约束):账号级配额挤兑(N Agent 各自确认后合力烧干)——建议画布层加全局 credit 预算闸,这是唯一必须建在壳里的并发安全件

### 7.4 推荐路线(两阶段)

**阶段一:零成本验证(本周可做,互不排斥)**

3. ComfyUI 装官方 Comfy MCP,验证 CC→ComfyUI 驱动链(这是 LLM→ComfyUI 方向,与本项目反向互补)

**阶段二:按验证结果二选一**

## 8. 风险与红线

1. 🔴 **AGPL(NodeTool)/GPL(ComfyUI 双仓)边界**:进程隔离+API 调用=安全(白盒确认);fork/嵌入/魔改再分发=传染。任何「把 NodeTool 代码搬进自研壳」的想法直接封死
2. **API 节点断供前科**:ComfyUI Sora2 节点 2026-09 官方随 OpenAI 停服移除——云 API 节点生命周期风险;缓解=media-gen-mcp 的渠道抽象(渠道死→白名单摘除,工具面不变)
3. **Monterey 平台风险**:Diffusion Studio WebCodecs 路线在本机(与 Remotion compositor dyld 同域)可用性未验证——若采用其合成组件须先探针
4. **HF ZeroGPU 配额挤兑**(§6 L3):画布多任务并发 hfspaces 会互相 data:null——需壳层配额预算
5. **维护负担**:路线 B=三件套(壳+MCP+ComfyUI)长期维护;media-gen-mcp 已证明可持续(渠道工厂飞轮),壳是新负担
6. **伪开源坑重申**:hypit/waoowaoo(NOASSERTION)、Diffusion Studio v2(邀请制+非商用)、Refly(商用限制)——选型时 license 必逐条核验

## 9. 结论与建议

1. **可行性总裁定:GO(有条件)**——media-gen-mcp 与画布软件融合不存在架构障碍,正确定位=「渠道聚合执行引擎」:对 NodeTool 零改造直连;对其余宿主补 Streamable HTTP 传输(一条命令或 2-4 天)即通;对 ComfyUI 经 mcpo/自建节点可达。
2. **「作为基底构建导演台」的裁定**:不建议把画布塞进 MCP(MCP 是 LLM 工具协议,画布是确定性 GUI,范式相反);正确分工=**画布底座管编排与叙事数据,MCP 管渠道执行,ComfyUI 管本地 GPU**。
3. **底座建议**:产品化走路线 B(自研壳+双引擎,许可干净、与确定性管线方法论/统枢经验全部衔接);纯自用可先 NodeTool 快速兑现(阶段一第 2 项的实证再定)。
4. **对本项目的最小行动集**(若采纳):①server 加 StreamableHTTPServerTransport(2-4 天,statelessMode,顺带解决多 Agent 并发多路复用);②产物 URL 化改造(远程画布消费前提);③confirm-token 的画布节点对语义文档化(已有 token 生命周期,只缺文档)。
5. **多 Agent 隔离并发终论**:三层状态模型(§6)证明进程级竞态全部在文档化可接受窗口内;真正需要全局仲裁的只有账号级配额与 gemini 单会话串行——**两者恰好都该建在画布调度层**,这是融合架构的并发学必然性,不是可选优化。
